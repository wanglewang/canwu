# 规格体系（specs/）

> 这个目录管「规格怎么产出、怎么往下传、怎么被审查」。它是规格驱动开发（SDD）在本项目的落地。
> 方法论背景见 `docs/40-engineering/09-review-driven-development.md`，产品意图见 `docs/00-foundation/01-product-vision.md`。

## 一、链条是有向的

四层，从人开始，逐层派生：

```
人提出意图
    ↓  AI 起草成文、人纠正确认
S  规格（Spec）        承诺什么、底线是什么、不许做什么
    ↓  派生（每条契约变成一个测试场景）
T  测试（Tests）       用哪些场景校验 S
    ↓  派生（每个场景落成一段实现）
D  实现（Development） 真正跑出来的代码
    ↓  各层提取一份覆盖度
Rₛ / Rₜ / Rᴰ          三层各自的「覆盖了哪些场景」集合，供机器比对
```

方向不可倒过来：**先有 S 才有 T，先有 T 才有 D**。反过来让代码或测试去定义规格，
就是让实现者给自己出题判卷——AI 写的代码看起来天然符合它自己读过的规格，判断与实现同源。

## 二、每一层谁产出、谁认领

| 层 | 谁产出 | 谁点头 | 不许做什么 |
| --- | --- | --- | --- |
| **S 规格** | 人提出意图，AI 起草成文 | **人纠正确认** | AI 自己定规格又自己验收 |
| **T 测试** | AI 按 S 派生场景 | 人认领覆盖范围，尤其「未覆盖风险」 | 按错误实现生成测试；只断言「没抛异常」 |
| **D 实现** | AI 按 T 写代码 | 机器每次校验，人只看差集 | 绕过 S/T 自己加行为 |
| **R 覆盖度** | AI 从本体提取，机器比对 | 人只审三份对不齐的地方 | 读代码猜出来的 Rᴰ（必须靠跑） |

关键在第一行：**规格的源头是人**。AI 会写规格，但「什么算对」由人定；AI 起草后必须经人纠正。
这不是形式——全链 AI 生成 + AI 自检只能证明三份产物互相自洽，证明不了符合人的要求。

## 三、审核反馈：问题在哪显现，不等于根因在哪

人审的是 R（覆盖度），但**不能直接改 R**——R 是从本体提取的视图，直接改它下次提取又被覆盖。
发现问题要改本体，再重新提取。这是「规格是真相源、覆盖度是派生视图」的必然结果。

关键一条：**问题显现在哪份 R，是表象；根因在 S / T / D 哪一层，要诊断。审任何一份 R，三层都可能要改。**
不要按「审 Rₛ 就改 S、审 Rₜ 就改 S+T」那种查表法预设根因——问题在哪被看见，和问题从哪来，是两件事：

- 审 Rₛ 觉得某条契约不对，根因可能是 S 真写错了，也可能是测试验错让人误读了规格，还可能是实现跑偏暴露出契约本就含糊。
- 审 Rₜ 发现覆盖缺口，根因可能是 S 契约不清让测试无从派生，可能是 T 派生漏了，也可能是 D 压根没实现这个场景所以测试没写。
- 审 Rᴰ 看到行为偏离，根因可能是规格错、测试漏、实现偏——三处任一，或叠加。

所以 AI 每接到一份 R 的意见，都要过一遍 S、T、D，判断这次到底改哪几层（可能只改一层，也可能三层全动），
而不是按被审的那份 R 决定改哪里：

| 人审的是 | 表象（在哪看见） | AI 要诊断并可能改的本体 |
| --- | --- | --- |
| Rₛ | 契约、底线、禁止项看着不对 | S / T / D 任一或全部 |
| Rₜ | 覆盖漏了、验错了 | S / T / D 任一或全部 |
| Rᴰ | 真实行为偏离契约 | S / T / D 任一或全部 |

改完以后，**三份 R 全部重新生成**——不管这次改的是哪一层。因为 S→T→D 是有向链：
改了 S，T、D 及三份覆盖度全部失效；改了 T，D 与 Rₜ、Rᴰ 失效；改了 D，Rᴰ 失效。
只重出被审的那一份，另外两份会留着旧视图，下次对照就是假告警。全量重出是保持一致的最省事做法。

三点机理：

- **不直接改 R**：改 R 是改症状。R 由本体提取，本体不动，下次提取还是老样子。
- **诊断不预设**：审 Rₛ 不等于只动 S。问题在哪显现和根因在哪是两件事，先诊断再动手。
- **改一层，三份全重出**：依赖链牵一发动全身，只换被审的那份会留下新旧混杂的旧视图。

闭环是这样合上的：人审任一份 R 提出意见 → AI 诊断 S/T/D 根因、改该改的层 → 重新生成全部三份 R → 交回人再审。
每一轮都重新给全套，人不用记上一轮改了哪层。

## 四、目录分工

| 文件 | 是什么 | 记什么 |
| --- | --- | --- |
| `S.md` | 规格本体 | 行为契约、不变量、禁止项、边界、开放问题。数值只指真源 |
| `T.md` | 测试规格 | S 每条契约对应哪个测试文件、哪组场景；明确未覆盖风险 |
| `D.md` | 实现规格 | T 每个场景对应哪段真源、哪个模块；只做导航，不抄代码 |
| `coverage/Rs.md` | 从 S 提取的覆盖度 | 规格承诺了哪些场景（按 09 §2.1 七维度） |
| `coverage/Rt.md` | 从 T 提取的覆盖度 | 测试覆盖了哪些场景、漏了哪些（按 09 §2.2 六维度） |
| `coverage/Rd.md` | 从 D 提取的覆盖度 | 代码跑出哪些场景、和规格差在哪（按 09 §2.3 六维度，靠跑不靠读） |

**T.md / D.md 只做映射导航**，不复制测试断言细节和代码实现——那样会变成第二套要维护的真相。
具体断言在 `tests/`，真源在 `data/*.js`，两份 R 的提取维度在 09 文档，这里都不重复。

## 四、三份覆盖度怎么比对

统一场景 ID 是命门：同一个场景在 S/T/D 里必须叫同一个名字（如 `SC-COMBO-CAP`），
机器才能做差集。当前状态如实记在 `coverage/` 各文件里——**场景 ID 表和差集告警脚本都还没建**，
不许假装有覆盖度集合。这是欠账，不是完成项。

三层对齐模仿编译器前端：源码（S）、测试用例（T）、运行结果（D）互相校验，任何一端改了，
另两端要跟着重算。人只看差集（漏测、代码缺、超范围、跑失败），全齐的部分折叠掉。

## 五、维护纪律

- **改行为先改 S**：实现与规格冲突时，先判断是规格错了还是实现错了；改规格要连同 T、D 一起重算。
- **每条契约要有会红的守卫**：写一条行为就问「哪条断言会在它被破坏时报红」；答不出就补断言。
- **写完断言要反证**：故意把实现改坏一次，确认断言真的红；不红说明空转（项目铁律）。
- **数值只指真源**：本目录不存第二套数字；改数值看 `docs/50-balance/02-numbers-reference.md` 与根 README 三处同步。
- **S 的改动要人确认**：AI 可以起草，不能自己点头；开放问题的取舍要人拍板。
