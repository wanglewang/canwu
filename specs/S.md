# S · 系统规格（Spec）

> 这份文档回答一个问题：**《参悟》这个系统对玩家承诺了什么，哪些底线绝不能破。**
> 它是规格驱动开发（SDD）里的规格（Spec）——先有它，再谈实现与测试。
> 只写「做什么」和「不许做什么」，不写「怎么做」；数值一律指真源，这里不另存一份。

## 一、这份文档的位置

规格驱动开发（Spec-Driven Development，SDD）把规格当作唯一真相源：代码和测试从它派生，
改行为先改这里，再让实现跟上。它与 RDD 的关系见 `docs/40-engineering/09-review-driven-development.md`——
RDD 管需求还在探索的那段，需求稳定后收敛到这里。

**这条链是有向的**：`S → T → D`，三层各派生一层覆盖度 `Rₛ / Rₜ / Rᴰ`。
S 是起点，由**人提出意图、AI 起草成文、人再纠正确认**——AI 不能自己定规格然后自己验收
（判断与实现同源就是自证）。T 从 S 派生，D 从 T 派生；链条方向见 `specs/README.md`。

三样东西不要混：

| 文档 | 回答什么 |
| --- | --- |
| `01-product-vision.md` | 为什么做这个游戏、给谁玩、体验目标是什么 |
| **本文（Spec）** | 系统承诺的行为、不变量、禁止项、边界——可测的契约 |
| `data/*.js` 与 `scripts/verify.js` | 数值的唯一出处，以及守住这些契约的断言 |

**规则**：本文出现数值的地方只写「见真源」，不写具体数字。谁在这里抄了一个数，
下次改 `data/*.js` 时它就过期，规格反而成了误导。唯一例外是纯结构性事实（比如「五段」「十五门」），
因为它们本身写在真源常量里，且由断言钉住。

## 二、范围与非目标

**范围内**：一门功法从开局到走通的一整趟参悟——选门、扣灵力、盘面判定、评级、熟练度与段位推进、
结算、存档、教学、皮肤、说明。

**明确不做**（Non-goals，写在这里防止实现者好心多做）：

- 不做签到、连续登录、体力恢复和任何制造回访焦虑的机制。
- 不做排行榜、社交与多人实时对战。
- 不做内购；灵石只能从玩法获得，兑换只开「灵石→灵力」一向。
- 不把长篇规则铺到主页面首屏；解释只在点进去之后。

非目标不是物理定律，是当前的默认取舍。翻案要走人审，判据见 `01-product-vision.md` §5 的约束分层框架。

## 三、行为契约

用可测的句式写：什么条件下、系统必须或不得发生什么。每条末尾给出**守卫**——哪条断言或测试会在它被破坏时报红。
守卫找不到，就要补断言，不许把这条留成口号。

### 3.1 一局参悟

- **开局前必须先报代价**：进局之前就要显示这一局耗多少灵力、还剩多少，不能打完才说钱不够。
  **守卫**：`tests/layout.test.js` 首屏文案约束 + `data/copy.js` 的提示真源。
- **付不起不许开局**：灵力不足时开不了局，且不能扣到负数。
  **守卫**：`utils/game/` 的开局校验 + `tests/game.test.js`。
- **一局只推一关**：每次参悟只推进当前这一关，不跳关、不批量结算。
  **守卫**：`data/practice.js` 的推进逻辑 + `scripts/simulate.js` 的「一局一关」前提。
- **主动结束与失败是两个结论**：中途退出不算失败结论，但必须打断连击；真正的失败要明确告知原因。
  **守卫**：`utils/game/settle.js` 的 `breakCombo()` 与 `fail` 真源。

### 3.2 熟练度与段位（两条独立的线）

这是全项目最容易被写混的地方，规格必须写明它们是两套系统。

- **熟练度有硬顶**：每门功法各自累计，到顶后不再增长，但纪录照记、灵力照扣。
  **守卫**：`data/world.js` 的 `PROF_MAX` + `tests/rank.test.js` + `scripts/simulate.js` 两条曲线断言。
- **段位只看关数**：走通第几关决定段位，与熟练度、品阶无关。
  **守卫**：`data/levels.js` 的 `stageIndexOfCleared` + `tests/rank.test.js` 的段位边界断言。
- **两个名字不许混用**：熟练度那套叫「火候」，段位那套叫「段位」，名字一个字都不能重合。
  一条判据里出现段位词，先问清这个数是关数算的还是熟练度算的（C6、C7 两次踩坑）。
  **守卫**：`scripts/verify.js` 的术语扫描 + `docs/50-balance/04-open-issues.md` C6/C7。
- **每一段都要换规则**：段界必须改变玩法本身，不能只换秒表或缩尺寸；段内变化要让玩家察觉得到。
  **守卫**：`npm run audit:gap` + `data/practice.js` 的 `AXIS_*` 九类方向账 + `verify` 的逐格断言。

### 3.3 灵力经济

- **两笔钱分清楚**：灵力是每局消耗的油，灵石是买东西的钱，二者不可混算。
- **兑换单向**：只允许灵石换灵力，反向永远不开。
  **守卫**：`data/economy.js` 的 `QI_PER_STONE` 与文件头理由 + `scripts/verify.js`。
- **每局耗气有定价表**：按段位取值，六项连乘、有下限，付不起不开局。
  **守卫**：`data/economy.js` 的 `RUN_QI` 与 `qiCap` 公式 + `scripts/simulate.js` 耗气断言。
- **熟练度不产资源**：参悟只推进火候与关数，不掉落灵石。

### 3.4 存档与异常路径

- **老存档能升级**：新字段补默认值，不改版本号也能读旧档；超出上限的值在读档时夹平。
  **守卫**：`tests/store.test.js` + `normalizeState`。
- **局中切页作废**：离开参悟页后该局不保留，回来要重新开始。
- **领奖不许因装不下而整份拒绝**：按空位收多少算多少，并告诉玩家散掉多少。

### 3.5 页面、导航与视觉

- **一趟参悟两屏**：主页与静室，入口统一；新页面必须在 `app.json` 注册。
  **守卫**：`data/navigation.js` 真源 + `scripts/verify.js` 注册断言。
- **返回路径唯一**：结算卡次按钮与终局底栏都回本门准备屏，只有冲关局去功法页。
  **守卫**：`verify` 的返回路径断言。
- **每页都要同步皮肤**：昼夜三档，跟随系统或手选；原生栏只作用当前页。
  **守卫**：每页 `theme.syncPage(this)` + `scripts/verify.js` 扫描。
- **彩色只传信息**：颜色绑系统，不用于并排罗列的同类文字。
  **守卫**：`styles/tokens.wxss` 唯一真源 + `verify` 裸色值扫描。

### 3.6 教学与说明

- **每段都有教学盘**：首段两步，段界一到三步；判据是走完能说清「这一段变了什么」。
  **守卫**：`minigames/teach-kit.js` + `tests/layout.test.js` 的 `TEACH_*[5]` 断言。
- **教学态接管全部输入**：tap / longpress / move / swipe 都转给教学控制器，不只转 tap。
- **说明只讲玩家规则**：设计文档内容不进 `data/help.js`，术语口径与白话一致。
  **守卫**：`verify` 对 `data/help.js` 的体裁字扫描。

## 四、不变量（无论怎么改都必须成立）

- 熟练度不为负、不越过硬顶；连击有层数上限；对局退出则连击清零。
- 段位只由走通关数决定；十五门功法各有独立的内核，不做通用特效层（判重见 `tests/minigames.test.js`）。
- 灵力不能反向兑成灵石；参悟不产灵石；灵力最低 1 点，不许扣成负数。
- 「全部 / 集齐」的门槛读 `SKILLS.length`，不写字面量。
- 评级线只有一个出处 `lines()`；有失败态必须给 `fail` 结论。
- 符号一律 CSS 画，不许用会变彩色 emoji 的字符；用色只认令牌真源。

## 五、开放问题（未定，不许实现者替玩家决定）

这些是悬而未决的取舍，实现时**不得自行选一个做掉**，要以人为准。完整清单与背景在
`docs/50-balance/04-open-issues.md` 的 D 类；此处只列会造成行为分叉的几条：

- 后三段的关卡密度是否撑得住（D11）——直接决定「熟练度先毕业还是关卡先毕业」。
- 身法属性在中前期是否生效（D1）——决定要不要改属性出口。
- 熟练度封顶后仍要烧气继续练，这条是否保留——决定第 3.2 节「到顶后照扣」是否翻案。

## 六、维护纪律（防规格漂移）

SDD 最大的失败模式不是没写规格，是规格和代码悄悄脱节，然后 AI 照着过期规格自信地改错。
因此：

- **改行为先改这里**：实现与本文冲突时，先判断是本文错了还是实现错了；改本文要连同守卫一起改。
- **每条契约都要有会红的守卫**：写一条行为，就问「哪条断言会在它被破坏时报红」；答不出就补断言。
- **写完断言要反证**：故意把实现改坏一次，确认断言真的红；不红说明断言空转（项目铁律）。
- **数值只指真源**：本文不存第二套数字；改数值看 `docs/50-balance/02-numbers-reference.md` 与根 README 三处同步。
- **翻案走人审**：非目标和开放问题的改动要人点头，不能因为「实现起来更顺」就悄悄改口径。
