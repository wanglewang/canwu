# 玩法设计完备性自检清单

> 适用：任何一门功法对应的对局玩法（阵法·星罗点灯诀、心法·澄心默诵诀、刀法·开锋破军诀、阵法·九宫补缺诀……），以及改了规则之后的老玩法。
> 用途：设计评审、开发前自检、上线前验收。**这是交付门槛，不是灵感清单**——写「这一门做完了」之前，第一节的十二个维度必须条条有答案；二期项可以空着，但要知道自己空着。
> 每一条都带三样：设计要回答什么、理论依据、现实或工程依据。最后多一列「在本仓库怎么算过」，能指到文件、能指到断言——这是它和通用模板最大的区别：**能验证的才叫清单，靠记的只是提醒。**

## 〇、先纠正七处通用口径

这份清单的骨架来自一份通用模板。模板里有七处写法与 `参悟` 已定的框架冲突，**照抄会打穿框架、还会向玩家说谎**。逐条纠正如下，写设计时以本表为准。

| 通用模板写法 | 本项目口径 | 为什么不能照抄 |
| --- | --- | --- |
| 评级 `C/B/A/S/SS/SSS` | 只有 **S / A / B / C / F** 五段，`F` 是失败（结束 / 溃败）；单局基础 `34 / 23 / 15 / 10 / 0` 点，S 另按**连 S 叠倍率**放大（第 10 连封顶 1307 点），`GRADE_FACTOR 1.5 / 1.2 / 1.0 / 0.6 / 0` 只用于 buff 段位判定，既不进熟练度也不进资源；**F 是「没走完」，不是「最低一段」**，零收益且断连 | 评级名在 `data/copy.js` 的 `GRADE_TITLE` 是一份真源，被结算、称号、成就、连 S 叠倍率全站共用。多两段，改动面比做一个新玩法还大 |
| 熟练度 = 基数 × 难度系数 × 评级系数 | **两条线分开**：熟练度只由「评级 + 连 S 层数」决定（C 10 / B 15 / A 23 / S 34 / F 0 点，连续 S 每局 ×1.5、最多十层、每局独立四舍五入），前段只折「基础值」、不碰连击收益；**参悟不再是产出，而是消耗**——单局耗灵力 = `economy.practiceQiCost()`：五段基数 **7 / 11 / 17 / 24 / 32** × 本门时长系数（0.85–1.30）× 品阶（1.00 / 1.15 / 1.30 / 1.45）× 境界超限 1.5 ×（1 − 心法省气，封顶 0.5）÷ 悟性系数（1 + 悟性/200，≤ 1.6）× 触类旁通 0.92，取整最低 1 点。**灵石可单向兑灵力（1 枚 = 100 点），灵力换不回灵石**：灵力从闭关（洞府可随时「打坐」收，不必退出重进）、份例与灵石兑换来、只往运功去；灵石从切磋秘境来、只往功法、破境与兑灵力去；参悟里那 1.2% 的机缘只出残卷，不产任何资源 | 熟练度的语义是「这一门练得多熟」，是投入刻度，不是功法身价；让天阶功法练得快 3.2 倍，低阶功法在成长线上直接被淘汰。参悟若既产灵力又产灵石，等于花时间印钱：灵力成过路财、灵石成计件工资，玩家一直在攒钱却感觉不到钱有分量 |
| 关卡：一门 1000 关五段，走通段界关才进下一段 | **段位整组退役**，一门功法就是一条 1–1000 的长线，段名就是玩家理解的进度：未入门 1–10 / 入门 11–50 / 小成 51–200 / 大成 201–500 / 圆满 501–1000，走通第 1000 关即大圆满。段界关 10 / 50 / 200 / 500 / 1000 是**晋阶关**——走通它当场进下一段（`levels.STAGE_GATES`）。存档只有 `skills[id].cleared`（本门走通了几关，0–1000），段位由 `stageIndexOfCleared()` 算，**与熟练度无关**。一局只推一关：`advanced = 未失败 && 打的是本门当前关 && 未满 1000` | 老版「简单/普通/困难/极难/绝境」不是难度选择器，是「你在第几关」的别名：一条熟练度轴同时管三件事（能打哪档 / 当前第几关 / 段位加成），玩家看到「解锁普通难度」其实是「刷够 300 分」。现在只有一条线，玩家只需要理解一件事：走通当前这一关 |
| 圆满之后不再增加熟练度，只衰减灵石 | 圆满（24000）开绝境，到**大圆满 99999** 才封顶；到顶后纪录照记、熟练度不再涨，但**灵力照扣**——此时再练就是纯烧气，该换门了。境界超出功法可修上限，只把**单局耗气**抬到 **×1.5**，熟练度照给 | 归零等于这门功法死了，玩家只能换门；×1.5 的意思是「还能练，但该换了」，和「只奖不罚」的养成基调一致；资源已不在参悟里产出，所以这条衰减只能落在消耗侧 |
| 结算三按钮：再来一局 / 返回 / 下一难度 | 金按钮 **「再来一局」**（打完的人多半想连刷）；次按钮「返回」；「留在本页」是下方文字链，且留的是**刚打完那一屏盘面**（`boardHeld`，控制器摘掉、底栏换终局三项），不是退回准备页 | 结算遮罩不能把玩家推走，也不能把人丢回准备页后没有下一步；三处去向都要在同一屏里看得见 |
| 对局提示、求解辅助 → 归入二期增强 | **辅助是刚需，但必须有明码代价**：星罗点灯诀的阵眼感应（每看一眼算 2 步）与复原本局（每局一次、封顶 A）、滑块让路的复位封顶 A、移石归阵诀的撤销不退推数、循数勘禁诀的勘位、太虚照见诀的入定。判据不止「提示」——凡是不改盘面、只抹掉已付出计数的操作（复位 / 撤销）都算 | 问题从来不是「有没有提示」，是「用了提示还宣称 S 公不公平」。辅助要么不给，要么把代价写在按钮上 |
| 分步新手引导弹窗、动画教程 → 二期 | **首局做「盘上手把手」，不做「读完再玩」的弹窗**：一门功法第一次开局，先给一盘不计步的小阵，两手之内把核心规则演完，随时可跳过，跳过或走完都记「看过」，之后永不再出现；没写教学脚本的玩法直接跳过 | 新手确实需要引导，但需要的是「带着点一次」，不是读三页字再开始——解谜类的规则，说一百遍不如让他看见点一格会翻五格。弹窗盖住盘面，恰好挡住要教的东西；它一旦成了每次开局的过场，又和「少文字、点进去展开」的基调打架 |

另外三条本项目的硬约束，通用模板里没有，必须自己补：

1. **盘面不写汉字**。方向靠箭头、形状、颜色、图案表达（刀路箭头、步法卷轴的 ↑↓↗⟳、八卦牌的三爻纹、五行环的元宝 / 嫩芽 / 水波 / 火苗 / 土山）。文字只出现在 HUD、按钮和说明里。盘面图案分三支：灵纹牌纹 `crest`（26 格：果器 8 + 甜点 / 海洋 / 灵兽 各 6，连连看按四套主题 × 六族骨架取、消消乐按序号取前 N）、卦象器物纹 `emblem`（其余原本写汉字或用 dingbat 的玩法）、数字与形状盘保留数字但统一补纸纹角花 + 一次性命中金圈。`✦ ✿ ◆` 这类字形在部分安卓上会被换成彩色 emoji，同一盘面两台手机会长得不一样，一律不用。
2. **恒定深色仙箓皮肤，只允许一支强调色**。页面挂 `.pg--imm`，颜色全取 `styles/tokens.wxss` 的 `var(--*)`，页面 wxss 不写裸色值。玩法盘面色板（`scene.wxss` / `practice.wxss`）是白名单例外——「盘面是墨玉台 + 暖玉牌、其余是墨」。
3. **文案不许写在 WXML 里**。状态与按钮取 `data/copy.js`，术语取 `copy.TERMS`，长解释取 `data/help.js`，玩法规则取 `data/guides.js`。

## 一、定位与叙事

| 检查项 | 依据 | 在本仓库怎么算过 |
| --- | --- | --- |
| 玩法品类明确，与已成功法机制不重复、不换皮 | 自我决定理论：多样化挑战维持内在动机 | `tests/minigames.test.js` 断言「15 门功法对应 15 套互不重复的玩法」「同类功法（刀法/阵法/心法/神识）也各用各的玩法」「每门功法的独有机制互不重复」 |
| 叙事包装与机制同源，不是文案贴皮 | 叙事沉浸理论：机制与故事统一才有记忆点 | `data/skills.js` 的 `desc` / `flavor`、`minigames/theme.js` 的主题名与浮字，讲的是同一件事（阵灯翻转 ↔ 阵眼感应；刀路 ↔ 刀光） |
| 目标用户、适合与不适合的场景写清 | 用户分层设计：避免同时要求强记忆 + 极限手速 | 设计文档里写明「适合推演型 / 不适合竞速型」，并对应到 `STAGES` 的段位设计（星罗点灯诀给足步数预算，就不该再叠倒计时） |
| 品类归属到模板大类 | 模板化复用：同类功法复用引擎 | 在 `data/practice.js` 的 `game` 字段与 `minigames/index.js` 注册表登记；文档里写清它属于点阵联动 / 记忆序列 / 滑动判定 / 走位预判 哪一类 |

**判断标准**：把这一门的文案全删掉，只看盘面和判定，玩家能不能分辨出这是另一门功课？分不出，就是换皮。

## 二、核心对局规则

| 检查项 | 依据 | 在本仓库怎么算过 |
| --- | --- | --- |
| 胜利条件一句话说得清 | 心流理论的前提：玩家知道怎么才算成功 | `minigames/*.js` 里只有一个 `finish()` 出口；`data/guides.js` 的 `goal` 一行写完 |
| 失败条件与边界明确 | 操作性条件反射：有边界的惩罚才形成闭环 | 失败必须走 `finish()` 并落 `F` 或 `C`，不许出现「无限僵持」的局；`tests/minigames.test.js` 的整局驱动会断言每门都能跑到结算 |
| 基础操作与响应规则确定 | 一致性交互原则 | 控制器只实现 `create()` 约定的接口（`tap` / `swipe` / `press` / `undo` / `hint` / `reset`）；页面事件方法必须在同名 js 里有定义（`tests/layout.test.js`） |
| 试错与重置机制 | 认知心理学：解谜的探索不该被惩罚 | **可逆，但反悔必须留痕**。按「已走 / 最优」评级的门（阵灯推演、滑块让路、推石入位）一律：复位本盘封顶 A，且**限次**（阵灯推演只许一次）；推石入位的「撤销」只退位置、不退推数。盘面固定 + 复位清零是一对危险组合——不封顶就能「走一步 → 复位 → 再走」把最优解白试出来，S 变成「肯反复重来」的奖励（原理与堵法见 `00-foundation/02` 第九节）。只靠扣资源当惩罚的门（灵纹照纹、三秀重排）不另加封顶 |
| 中途退出规则 | 事务一致性：未完成的局不产生收益 | 结束走二次确认（`tests/layout.test.js` 守着「参悟局内结束放在屏幕上方且带二次确认」），退出不进结算：无熟练度、连 S 归零，起手烧掉的灵力不退，与全部功法一致 |
| 代价句必须常驻且只说一次 | 减少认知负荷：代价要在玩家付出之前出现 | `tests/layout.test.js` 断言「局内两行不说同一句话：tip 讲代价，inline 讲操作」「局内代价句用阿拉伯数字」 |

**判断标准**：玩家第一次输，能不能仅凭局内提示说出「我为什么输」。说不出，就是失败条件没交代。

## 三、难度系统

| 检查项 | 依据 | 在本仓库怎么算过 |
| --- | --- | --- |
| 难度控制变量全部参数化 | 认知负荷理论：可控梯度加载压力 | 变量只写在 `data/practice.js` 的 `params`，玩法层读 `buildParamsAt(method, 关号)` 的输出，不自己写死 |
| 递增曲线平缓，无断崖 | 最近发展区：难度略高于当前能力 | 相邻段之间的参数差要能解释（星罗点灯诀：盘面 3→3→4→5→5，最优步数 2–3 ／ 4–5 ／ 4–5 ／ 6–7 ／ 8–9，余量一律 +7）。`tests/rank.test.js` 断言相邻两段至少有一条轴真的动了——同尺寸的两段不许区间重叠 |
| 解锁规则全站唯一 | 心流门槛管控：别让新手直接撞高难 | 一律按「走通一关推一关」判，不新增第二套解锁；`STAGES` 里没有 `need` 也没有 `open`，熟练度不是段的门槛 |
| 盘面尺寸不随段位缩放 | 工程约定：尺寸是玩法身份，不是难度旋钮 | `tests/rank.test.js` 与 `scripts/verify.js` 断言功法表里写死的 `grid / cols / rows / size` 在 `buildParams` 里不被乘 pace / goal。**例外是三张显式规格表**（`LIGHTS_LEVELS` 3×3→5×5、`SUDOKU_LEVELS` 4→6→9 宫、`SCHULTE_SIZES` 4→5→6），它们的 `params` 本来就是空的，规格由整表按段注入，属于「规格本身是难度」的另一种设计，不参与通用缩放 |
| 关只能往回翻，不能往上挑 | 心流：挑战与技能同步。第 12 关是走通 11 关换来的，不是刷分换来的；还能往上点，等于让玩家自己选难度，最后一定选最简单的 | 进度只由「走通当前关」推进（`utils/game.js` 的 `advanced`：非失败、打的是本门当前关、未满 1000）。默认停在「已通 + 1」；`onLevel` 只能往回翻到已走通过的关，没有「挑段」这个动作。`tests/rank.test.js` 断言走一关推进一关、失败/回关不推进、满 1000 不越界 |
| 五段要真的分得开，不许只改分数线 | 认知负荷理论 + 公正感：盘面、时限、容错全不变而只抬 S 线，等于把同一局结算时乘个系数；玩家打完说不出这一段难在哪 | `npm run audit:diff` 逐门列出五段里会变的玩家可见参数与评级线种类；判据是「至少两个可见参数 + 评级线或盘面规格随段变」。**首轮审计 15 门里 9 门不足，本轮全部补齐，现为 0 门**：三秀同收换整表（`MATCH_LEVELS`），所有限时玩法共用 `TIME_LEVELS` 逐段收时辰，勘禁 / 丹道 / 神识 / 机关四门各补一个玩法层真读的参数（心神盏数 / 起手块数 / 点错罚秒 / 推数预算系数），循纹递推与循数勘禁诀的说明行补上本段盘面事实。`tests/rank.test.js` 有同名常驻断言逐门复算，不再只靠人跑脚本 |
| 评级线按本段实测标定，不许拍脑袋每段 +150 | 质量—奖励匹配：10×10 / 7 色 / 60 息的 950 分，比 6×6 / 5 色 / 68 息的 1900 分更难拿；同一把尺子量不同盘会骗人 | 三秀同收旧版只有 `flashMs` 与 `S = 620 + depth×150` 在变，真控制器 + 假时钟跑 12 局/段/三种玩家：高手五段 12/12 全 S、常人绝境 10/12 S，等于同一局打五遍。现按分位数标定为 `1900 / 1750 / 1400 / 1300 / 950`（盘面越难线反而略低），准备页与说明页明写「盘面越难，同样分数越难得」。`tests/rank.test.js` 断言花色不减、时辰递减、罚息不减、S 线递减 |
| 阶段便利必须有明码代价 | 十二原则第十一节：阶段新法要加规则，不是减难度 | 三秀同收「照畦不扣息 / 重排不扣息」改为「各少扣 1 息但仍要付」，连锁加成改为第 3 层起才生效；`tests/layout.test.js` 与 `data/guides.js` 同步 |
| 回关有明码折减，连 S 只在本门当前关生效 | 激励经济学：关能往回翻之后，回关不能既便宜又给满分；连击不该被「停在某一关反复刷」养起来 | **回关折减 = 本关 ÷ 本门当前关**（`profByLevel()`，四舍五入一次）：本门第 800 关时回打 800 → ×1.00、400 → ×0.50、100 → ×0.125。只折基础熟练度，耗气按本关所在段报价、不跟着折。**连 S 只在本门当前关叠**：回关局不叠层、不砍已有层数。分母能回到「当前关」是因为**走通必推进**——想停在第 N 关只能每局失败，而失败给 0 分，老版「只刷第 1 关」的入口在结构上没了。`tests/rank.test.js` 逐关复算系数与单调性，`npm run sim` 断言只刷低关不反超逐关进 |
| 连 S 叠倍率取代三连 S 晋级 | 熟练度只由评级与连续 S 决定，单一曲线替掉「定额 + 补额」两套机制；10 层封顶防无限膨胀 | 第 1～10 连 S 每局 `34/51/77/115/172/258/387/581/871/1307` 点（`round(34 × 1.5^(k-1))`，每局独立取整、`.5` 进位，第 3 连 76.5 → 77 与 A 的 22.5 → 23 同向），一轮 3853 点，第 11 连起锁死 **1307**。C / B / A、失败、**主动结束**都归零（`breakCombo()` 堵住中途退出保连）；`state.sCombo` 按功法计，存档 v6。全程不断 S 84 局毕业，全 C 10000 局。`tests/game.test.js` 逐局复算 1～14 连，`tests/rank.test.js` 守曲线常量与封顶，`npm run sim` 复算两条毕业曲线 |

## 四、激励、经济与熟练度

| 检查项 | 依据 | 在本仓库怎么算过 |
| --- | --- | --- |
| 评级判定指标明确、可解释 | 质量—奖励匹配原则 | 指标可以因门而异（星罗点灯诀按步数、三秀连收诀按总分、澄心默诵诀按轮数、顺序点格按用时），但必须一句话讲清且写进 `guides.scoring`。统一的是**五种评级的名与系数**，不是判定指标 |

## 十五、验收口径

一道功法算「做完」，要同时过三关：

1. **设计关**：上面十二个维度条条有答案，二期项明确空着。
2. **静态关**：`npm run check` 全绿（verify + test + sim + lint），新行为有断言守着，不是靠记忆。
3. **产品关**：真机看过。**没有任何一条真机证据时，只能说「静态层完成」**——颜色在真实屏幕上是否分得开、热区在 4.7 寸上够不够、动画会不会掉帧、震动与音效是否撞手感，这些断言替不了。

## 附录 B：十二维现状核对（15 门整体）

上面那份是单门示范。这里是**全站口径**：十二个维度逐条回答「现在满足到什么程度、证据在哪、缺口是什么」。核对的时点是 15 门全部做完之后。

结论分三段：**过**（有断言守着）/ **部分**（结构对了，但有关键一环只能真机看）/ **未验**（完全靠人看）。

| 维度 | 结论 | 证据 | 缺口 |
| --- | --- | --- | --- |
| 一、定位与叙事 | 部分 | 15 门 15 套内核、同类功法也不共用，有断言；`skills.js` 的 `desc` / `flavor` 与本门机制同源 | 「把文案删掉只看盘面还认得出是哪门」这条判断标准只能人看；叙事与机制是否同源也靠人。本轮修掉一处不同源：移石归阵诀的 `flavor` 说「推错了就推不回来」，而撤销退得回来 |

### 逐条核下来真正不满足的三处

| # | 违反哪一维 | 设计上的根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 二、十一 | 「复位 / 撤销」不改变盘面、只抹掉已付出的计数，但没有一条通则要求它们付代价。阵灯推演做了，另两门漏了 | 复位封顶 A（让路、入位）；撤销不退推数（入位）。判据写进 `00-foundation/02` 第九节 9.3 |
| 2 | 二 | 代价句写「推不回来」，而 `undo` 把推数一起退了——文案与机制互相否认 | 机制先改（只退位置），文案跟着改成「推错可退一步，推数照算」；七处字面同步 |
| 3 | 五 | 置灰只判「够不够格」，没判「备不备得齐」，玩家跨一页才知道原因 | 两件事分开判、分开提示，按钮同时置灰 |

### 两条方法论

1. **这一轮的三处问题没有一处是新功能的错，全是「同一个判据只在部分门落地」。** 阵灯推演的封顶写了、另两门没写；置灰判了一半；代价句只对了一半的行为。所以核对十二维不能只看「有没有这个机制」，要看**这条机制是不是每门都执行了**——前者静态能查，后者只能逐门数。
2. **清单里凡是写「每门都……」的句子，都要问一句「断言在哪」。** 这一轮抓到两条空口：第十二节的「辅助使用后的评级封顶」与「难度五段各生成一局」，原来都只写在清单里、没有任何断言。补完之后才敢在上面这张表里写「过」。
