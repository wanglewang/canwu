## 读卡前：几个词的意思

不用先读方法论文档，这里把卡里出现的词翻译成人话：

| 词 | 人话 |
| --- | --- |
| **要求（L2）** | 你真正要的东西，也就是「这个游戏该是什么样的」。它最稳定，只有你想改主意的时候才需要重审。 |
| **规则（L1）** | 把要求落成可执行的约定，比如「一局只推一关」「门面词必须是正名的子串」。 |
| **实现（L0）** | AI 写出来的代码。机器每次都会查，你不用读。 |
| **守卫** | 一条机器断言。谁把事情改坏了，它就会报红。所以「有守卫」的意思是：这件事机器替你盯着。 |
| **落点** | 这条要求由哪个文件、哪条断言守着。顺着点进去，就能看到它到底怎么守。 |
| **R<sub>S</sub> / R<sub>T</sub> / R<sub>D</sub>** | 规格、测试、代码各自「覆盖了哪些场景」的清单，不是文字摘要。三份对得上，才算没跑偏。 |
| **覆盖度** | 「覆盖了哪些场景」的集合。集合可以做差集比对，摘要不行——所以摘要会骗人，集合不会。 |
| **场景 ID / 差集告警 / 保真度** | 三份覆盖度共用的场景编号；对不上的地方就是告警，比如漏测、代码里缺、超出规格、跑失败。**差集由 `npm run audit:alerts` 机器产出（真跑 check/gap），本轮四类全 0；保真度由 `npm run audit:fidelity` 查 R<sub>S</sub>→S 正反、R<sub>T</sub>→测试文件正向，各告警全 0。** |
| **A–E 欠账** | `docs/specs/tasks/05-待修欠账.md` 等四份台账里按性质分的五类问题：必修、该修、缺口、待拍板、待验收。 |
| **真源** | 唯一权威的出处。本卡只是导读，数字和完整定义一律以真源为准，不另存一套真相。 |

三档状态是这么判的。标成**有守卫**，意思是这件事有一条机器断言盯着，每次运行检查都会查一遍，改坏了就报红；
标成**部分**，意思是断言有，但只覆盖了这件事的一部分，剩下的得靠文案真源或者人眼；
标成**未验**，意思是压根没有机器断言，只能靠真机或者人来判断——这一类是你最该留意的。

## 一、要求清单（你真正要的东西 · L2）

来源真源：`docs/specs/constitution/01-产品定位与体验目标.md` 的 §4 体验目标、§5 约束分层、§6 成功判据。

### 1.1 体验目标（6 条，优先级从高到低，冲突时上面的压倒下面的）

| # | 要求 | 这条在说什么 | 靠什么守住（落点） | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 一眼看懂现在该做什么 | 这一条想让玩家打开游戏就知道该干什么。主页第一屏只放境界卡、六宫格、一行「去练哪门」的提示和一个主按钮，不能出现说明句、页脚口号或者公式。 | `tests/layout.test.js` 里有一份黑名单，第一屏一旦冒出说明句、口号或者公式，测试就会报红。 | 有守卫 |
| 2 | 国风沉浸，不像小程序 | 这一条想让游戏读起来像修仙，而不是套了层皮的小程序。名词沿用修仙设定，像功法、境界、灵力；句子说现代白话，像「换一门」「退出」。不能出现「小游戏」「资源」「通关」这类产品词，也不能写成「暂且退去」那种仿古句。 | verify 里写了禁词断言，产品词和旧名一出现就报红；昼夜皮肤靠 `styles/tokens.wxss` 里的令牌守着。至于语气像不像修仙，机器守不住，得靠文案真源 `data/copy.js` 和人眼。 | 部分（语义那半靠文案真源，机器只守得住词表） |
| 3 | 每一局的钱都花得明白 | 这一条想让玩家在开局前就知道这一局要花多少。按钮上直接写明消耗多少灵力、还剩多少，结算时也要写清扣了多少、不退。不能等打完了才告诉玩家其实钱不够。 | `tipFor()` 是代价句的唯一点，verify 断言钉住按钮必须引用它，文案改了或者漏了就会报红。 | 有守卫 |
| 4 | 努力有可见回报 | 这一条想让玩家每次进步都看得见。功法特效从初窥火候的 25% 开始逐级兑现，一直到通玄的 100%，每升一档火候面板上都有变化。不能让玩家苦练到精纯才发现特效。 | `EFFECT_TIER_SCALE` 这个数组写成 `[0,.25,.5,.75,1,1]`，verify 有断言核对每一档火候的兑现比例。 | 有守卫 |
| 5 | 不惩罚离开 | 这一条想让玩家离开之后不被惩罚。不设日常任务链、连续登录奖励，也不搞「体力不足请明天再来」那一套；闭关回来一键就能收。不能用制造焦虑的办法逼人回访。 | 设计约定里写了不设日常链，但 verify 没有专项断言。只能靠人盯着，看有没有谁偷偷把它加回来。 | 未验（你最该留意的一条） |
| 6 | 解释放在点进去之后 | 这一条想把解释推迟到玩家真正需要的时候。第一屏只留标签、数值和按钮，长解释放到右上角「说明」里按节折叠。不能一屏铺满规则。 | `data/help.js` 按节折叠，verify 有一条断言禁止说明页泄漏设计文档的内容。 | 有守卫 |

> 第 5 条属于第三层「默认值」，不是不可动的身份约束。要松绑的话，方向是「今日机缘」这类修仙事件，
> 不是通用签到领奖，而且得连带重新审视灵力恢复的节奏。这也是它出现在第四节待点头的原因。

### 1.2 成功判据（7 条）

## 二、三层覆盖全景（S / T / D 是什么，现在到哪一步了）

RDD 的核心想法是：先有**本体**，也就是规格、测试、代码；再从本体各提取一份**覆盖度**，也就是「覆盖了哪些场景」的清单；三份对得上，才算没跑偏。

三份覆盖度的文件都建在 `docs/reviews/` 目录（与 `docs/specs/` 平级，都在 `docs/` 下）。2026-11-24 按存档 v10 全部重出：R<sub>S</sub> / R<sub>T</sub> / R<sub>D</sub> 各 31 个场景 ID；`verify` 的文档新鲜度断言守住「篇数对得上、R 卡路径存在、ID 跨两卡一致、退役 ID 不复活」。`npm run audit:alerts` 真跑 `npm run check` 与 `npm run audit:gap`，按 R<sub>D</sub> 的挂接表匹配输出，机器产出四类告警——本轮实测 31 个 ID 全命中、四类告警全 0，四类各反证过一次。

| 层 | 这层是什么 | 本体在哪 | 谁产出 | 现在到哪一步 |
| --- | --- | --- | --- | --- |
| **S 规格** | 约定了什么、底线是什么、哪些行为绝不允许。 | `docs/specs/` 按 SDD 四层组织：总纲在 `constitution/`，六份行为契约（对局、成长、经济、存档、界面、教学）在 `spec/`，共 7 份，各自带会红的守卫；数值指 `data/*.js`。 | 你认领，AI 可以起草。 | 七份规格齐了；R<sub>S</sub> 31 个现行 ID（v10 退役 4、新增 6），宪法不变量与开放问题状态已同步。 |
| **T 测试** | 准备用哪些场景去校验规格。 | `tests/` 下五个文件：game 管养成、store 管存档、minigames 管玩法、rank 管品阶难度、layout 管布局。 | AI 产出，你认领覆盖范围。 | 363 项断言全绿；`tasks/01` 已细化到场景 ID 映射，R<sub>T</sub> 31 个 ID 全挂，其中 2 个只有静态守卫。 |
| **D 代码** | 代码实际跑出来的行为。 | `minigames/` 下 15 门玩法、`pages/` 下的页面，还有 `utils/game/` 里的内核。 | AI 产出。 | `npm run check` 四段全绿；R<sub>D</sub> 31 个 ID 已逐场景挂到真实输出（1000 局 / 22020 点 / 全 S 全 C 同值），观测全命中。 |

**一句话**：三层本体 + 三份覆盖度 + 机器差集 + R<sub>S</sub>/R<sub>T</sub> 保真度都齐了；现在人只看告警，不用重读全集。
但保真度的反查只做到 R<sub>S</sub>→S，R<sub>T</sub> 只做正向、R<sub>D</sub> 靠挂接表命中；三份若一起把某条测试/观测写软，仍看不见。
