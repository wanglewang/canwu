# 难度区分度审计

## 一句话

用一份脚本回答静态断言回答不了的问题：五档「简单 / 普通 / 困难 / 极难 / 绝境」对某一门功课来说，**究竟改了什么**。

## 目标与非目标

**目标**

- 揪出「五档只换了个结算系数」的功法。这类功法在存档里看起来有五个档，玩家玩起来只有一档。
- 让「新增玩法必须真的分档」这件事有一个可执行的判据，而不是靠写的人自觉。
- 把每门功法「哪两个可见参数在变」写下来，改数值的人一眼知道动哪个键才有意义。

**非目标**

- **不判「变得够不够难」。** 那是收益曲线、真机手感、评级分布的事，静态脚本判不了。
- **不判「变得合不合理」。** 比如顺序点格曾把后三档全放在 6×6 上、只差 1–3 秒 S 线（见下文特例三），审计照样判「过」——因为它确实在变，只是变的幅度小于随机布局的波动，玩家感受不到。这类问题要靠专门的断言与真机，见特例三末尾。
- **不进 `npm run check`。** 见最后一节。

## 判据

脚本 `scripts/difficulty-audit.js` 对 19 门逐一跑，两条同时满足才算「过」：

| # | 判据 | 意图 |
| --- | --- | --- |
| ① | **每档至少两个玩家看得见的参数在变**（盘面 / 预算 / 容错 / 节奏） | 一个参数变，玩家感觉不到那叫难度，只叫「慢一点」或「少一点」 |
| ② | **评级线随档变，或盘面规格随档变** | 否则说明页五档写同一行字，玩家没法对照自己该打多少 |

第 ② 条留了「盘面规格随档变」这个替代出口，是因为有一批功法（九宫、阵灯、目术、滑块、推石、开锋）的难度**写在盘上，不写在数字上**——4×4 变 5×5 没有任何数字参数变化，但玩家一进去就知道紧了。

**第三列「主轴跨度」不参与判定，只提示。** 跨度小可能是物理限制（时间轴压不动），也可能是设计没做完（时间轴本不该当主轴）——审计分不清这两者，所以只标 `*` 不报错。真正该拦的写在 `tests/rank.test.js` 里，按门逐个标定。

### 参数怎么被判定为「变」

对每门功法调 `practice.buildParams(method, key)` 拿五份参数，逐键去重，只留「五档里出现过两种以上取值」的键。被排除的键只有一类：

```js
const INTERNAL = new Set(['depth', 'gear', 'sBase', 'sStep']);
```

`depth` 是「第几档」（0–4），任何按档注入的整表都靠它取行，它必然在变，但它不是玩家看得见的东西。其余三个名字——`gear`（`normal` / `hard` 两值，给玩法分难度用的）、`sBase` / `sStep`（历史遗留的评级线基数与步长）——**在当前 `buildParams` 的返回里都不存在**。实测 19 门所有档位合并起来共 50 个参数键，`gear` / `sBase` / `sStep` 一个都没有。

也就是说 `INTERNAL` 这个集合实际只过滤了 `depth`；另三个是留给「以后真加了这几个键」的保险。这不影响结论（多排除一个不存在的名字不会让任何功法误判为「过」），但名字挂着容易让人以为有机制在背后，属可清理的欠账。

### 五档参数是怎么来的

审计读的是 `buildParams` 的输出，所以必须先知道这个函数的施加顺序，否则会误读表里的数字。顺序是：

1. 复制功法自带的 `params`；
2. **`PACE_KEYS` 十项**（含 `life` 与判定窗 `window`）× `pace`（`1.18 / 1 / 0.88 / 0.78 / 0.7`）；
3. ~~`WINDOW_KEYS` 一项（`life`）× `windowPace`~~ —— 已退役。`life` 并回第 2 步，那个空数组与
   `DIFFICULTIES.windowPace` 字段都删了：五档写了一列数却无人消费，正是「生成了没生效」；
4. **`GOAL_KEYS` 十项** × `goal`（`0.85 / 1 / 1.12 / 1.22 / 1.32`），并夹在 `capFor(key)` 上限内；
5. `duration` / `timeLimit` × `TIME_LEVELS`（`1 / 0.97 / 0.94 / 0.91 / 0.88`），最低 8 秒；
6. 透传 `depth`，再由**六份按档整表覆盖**（三秀 / 阵灯 / 九宫 / 滑块各一份，加上四门「补第二个参数」的单值注入）；
7. `steps` 每档 +1；`speed` 除以 `pace`（越快档 speed 越大，方向与其他键相反）。

顺序决定了一件事：**整表覆盖发生在缩放之后**，所以三秀同收的 `duration`（68/60/58/55/52）不是 `base × TIME_LEVELS` 算出来的，而是表里直接写的。改的时候要改表，不是改系数。

`TIME_LEVELS` 的用意也在注释里写着：时辰收紧是「这一档到底紧在哪」最直白的一条，玩家一进局就看见倒计时在少。

## 主轴跨度：审计的第三个数

前两列（可见参数、评级线）回答「有没有变」，第三列回答「变了多少」。

原来的判据只有前者，于是 `滑格相合` 的 8 倍和 `顺光扫斩` 的 1.15 倍得到同一个结论「过」——可玩家感受完全不同，前者每档都在换目标，后者五档几乎一个手感。**这是旧审计最大的盲区：它守得住「压根没变」，守不住「变了跟没变一样」。**

### 为什么是 2 倍这条线

玩家的难度可辨阈值约 5%：相邻两档的参数差不到 5%，玩家说不出「这档更难」，只会觉得「差不多」。

- 跨度 **1.7 倍**摊到四段间隔，每段 14%——能明确分辨；
- 跨度 **1.15 倍**摊到四段，每段只有 3.6%——落在阈值下，等于五档一个手感。

所以 `<2 倍` 标 `*`。**这不是报错，是提示**：它说明这一门的承重轴压不出量来，该换一根轴了。

### 9 门标 `*`，但只有 1 门是真问题

9 门里 8 门的最大跨度都恰好是 **1.69 倍**，这不是巧合——它们的承重轴都是时间类参数，而时间类统一走 `PACE_KEYS × pace`，`pace` 表本身就是 1.18 → 0.70（1.69 倍）。**这是全站统一的节奏曲线，不是疏漏。**

时间轴压不上去是物理限制，不是设计懒：

| 轴 | 现在的简单档 | 再压 2 倍会怎样 |
| --- | --- | --- |
| 时限 | 15 秒 | 7.5 秒——连盘都看不完 |
| 间隔 | 1180ms | 590ms——来不及读 |
| 停留 | 826ms | 413ms——只能靠猜 |

**所以时间轴的结论是「够用了，别再往下拧」**，不是「再加把劲」。

真正该动手的是把承重轴换到复杂度 / 信息 / 规模上，这三根轴的物理上限高得多：

| 轴 | 19 门里已用 | 上限 | 为什么高 |
| --- | --- | --- | --- |
| 复杂度 | 5 门 | 6–8 倍 | 加规则不占屏幕、不逼手速 |
| 信息 | 5 门 | 5–6 倍 | 挖洞、缩短观察窗，纯认知 |
| 规模 | 3 门 | 4 倍 | 受屏幕尺寸限制（每格 ≥25px） |
| 速度 | 5 门 | 3–4 倍 | 生理上限（反应 200ms） |

### 三门换轴的对照

这一轮把「看起来没问题、实际压不出量」的三门从时间轴挪到了规模 / 复杂度轴：

| 门 | 改前主轴 | 改后主轴 | 时间轴怎么变 |
| --- | --- | --- | --- |
| 顺光扫斩 | 速度 2.86×（343→120ms） | **盘面 2.78×**（3×3→5×5）+ 刀路 2.67×（3→8 桩） | 2.86 → **2.17×** |
| 数格辨禁 | 禁制 1.60×（5→8） | **盘面 2.25×**（6×6→9×9）+ 禁制 2.40×（5→12） | 时间线跟着格数**放宽**（25→56 秒） |
| 步法连环 | 段数 1.67×（且两对档位重复） | **段数 + 键位重排**（12→39 步，困难起每段重排） | 时间**放宽**（20→23 秒） |

三门的共同点：**时间一项都没收紧，反而放了两门。** 多出来的难度全落在「要想的东西变多」上——刀路更长要记路、盘更大推理链更长、键位重排必须读符号。

这也是往下走的模板：**先问这门该练什么，再看哪个轴能体现它**，而不是「高档就把数字调小一点」。

- **`flashMs` / `gapMs` / `shuffleMs` 带 .8 / .6 这类尾数**：它们是 `倍数 × pace × 1000` 取整到三位的结果，比如灵纹连线 `flashMs` 900 × 1.18 = 1062，成对翻牌 850 × 1.18 = 1003。准备页显示时会折成「1.06 秒」这种，不显示毫秒原值。
- **九宫填数的 `timeLimit` 在难 / 极 / 绝三档都是 420 秒**：因为它是整表覆盖，表里就写死 420；这三档的收紧靠 `holes`（32 → 40 → 46）与三条评级线（`tS` 170 → 190 → 210）承担，不靠时钟。
- **`startLen` / `decoys` / `kinds` 这类整数在相邻档重复**：它们过了 `goal` 倍率后被 `Math.round` 折叠，比如 `decoys` 2 × 1.32 = 2.64 → 3，所以只有绝境档真的多出一个。这是刻意的——整数参数天然只有几个台阶，硬要每档都变只会让简单档变成 1。
- **节律判定的 `window` 与 `speed` 是反向的一对**：表上两列各自 1.68× / 1.69×，可玩家感受到的是 `window ÷ speed`——判定带从 ±325ms 收到 ±115ms（2.8×）。这一门的「主轴跨度 1.69×」只是单列数字，两列相乘才是难度；五个数由 `minigames/tempo.js` 的 `metrics()` 复算，见 `20-minigames/05-absorb-tempo.md` §4。**凡是「越小越难」和「越大越难」各占一个参数的玩法，审计的单列跨度都会低估难度**（本门是唯一一门）。

## 四个特征门

### 特例一：阵灯推演——评级线只有 1 种，仍然判「过」

`lights.lines()` 返回的是**纯步数比例**：

```
S：正好最优步数 | A：多 2 步以内 | B：不超过最优的两倍 | 其余为 C
```

这四句与盘面大小、步数预算都无关，所以五档拼出来是**完全相同的字符串**，`lineVariants = 1`。它靠第 ② 条的替代出口过关：`size` 从 3 变到 5、`capSteps` 从 9 变到 22，盘面规格确实随档变了。

三条判据里它满足两条：

| 判据 | 结果 |
| --- | --- |
| ① 参数 ≥ 2 在变 | ✅ 3 个 |
| ② 评级线随档变 | ❌ 五档同一行 |
| ② 替代：盘面规格随档变 | ✅ `size` 3→5、`minSteps` 2→5、`capSteps` 9→22 |

**这是设计选择，不是漏改。** 阵灯推演是一门「按步数比例评级」的玩法：盘大好办还是盘小好办，取决于最优步数；写成「S ≤ 16 步」反而会在 3×3 盘上给出一个白送的 S 线。用比例表达，五档共用一把尺子，玩家学会的是「贴着最优走」，而不是背数字。

代价是**说明页五档会显示同一段评级文字**。这一点由准备页的 `brief` 补上：阵灯推演的 `brief` 不走通用的「时间类字段」拼装，而是单独说清 `size×size 盘 · 最优 N 步起 · 预算 M 步`（`diffDetail` 里对 `lights` 有专门分支，注释写明「按时间类字段拼 brief 只会拼出一句『入门基准』」）。

### 特例二：数格辨禁——时间线随盘面走，不是五档一张表

评级只看用时，而三条线按格数算（`gradeLine(n)` = 25 秒 × 格数 ÷ 36），所以盘面一变、线就跟着动：

| 档 | 盘面 | 格数 | 禁制 | 密度 | 心神 | S | A | B |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 简单 | 6×6 | 36 | 5 | 14% | 3 | 25 秒 | 45 秒 | 75 秒 |
| 普通 | 6×6 | 36 | 6 | 17% | 3 | 25 秒 | 45 秒 | 75 秒 |
| 困难 | 7×7 | 49 | 8 | 16% | 3 | 34 秒 | 61 秒 | 102 秒 |
| 极难 | 8×8 | 64 | 10 | 16% | 2 | 44 秒 | 80 秒 | 133 秒 |
| 绝境 | 9×9 | 81 | 12 | 15% | 2 | 56 秒 | 101 秒 | 169 秒 |

旧版盘面恒 6×6，三条线五档一模一样（25/45/75），只有禁制数与心神在变。当时记的疑问是「玩家对照五档会看到时间线完全一样」。这条疑问现在解决了——但**不是靠收紧时间，而是靠放大盘面**：线变长了，是因为要做的事变多了。

这一门的难在推理链长度，而推理链长度由格数与密度决定。36 格 8 处禁制，约束传播两三步就推到底；81 格 12 处禁制，要跑好几轮，中途还得回头补推。**同样的推理能力，在 9×9 上要做十倍的功。**

所以时间绝不能跟着收：9×9 若卡在 25 秒，玩家只剩「猜」，而这门刻意做了**无猜保证**（布完禁制用约束传播验过可解）——逼人猜等于把设计前提推翻。

密度稳在 14–17% 也是同一个道理：太高是「无处下脚」，玩家只能猜；太低是空盘，没有推理可做。密度是本门最该守的一条线，`tests/rank.test.js` 里有一条断言直接卡这个区间。

### 特例三：顺序点格——后三档曾挤在同一个 6×6（已修）

审计第一次跑出来的表是 4/5/6/6/6：后三档同一个 36 格，档与档只差 S 线 34 / 32 / 29 秒，
其余全按 `PER_CELL` 的固定倍数现算。它过了审计（可见参数有 `size` 与 `penaltySec`，
评级线也确实五档不同），但三项静态判据都抓不到它真正的问题：

1. **档差小于方差**。同一尺寸换个随机布局，成绩本来就波动 3–5 秒（公开舒尔特参照
   自己也这么写），而这里三档只差 2 秒与 3 秒。三档在体感上是同一局。
2. **困难 34 秒宽于极难 32 秒**。原因是 `PER_CELL` 乘以格子数、而格子数在困难档跳到
   36 后不再变；玩家横向对比会觉得「降档反而更难拿 S」。这不是标定失误，
   是「同一盘面只收秒表」的必然结果——只要两档同盘面，就一定出现这种反向。
3. **一个旋钮，四条线**。`A = 1.45S`、`B = 2.1S`、`时辰 = 1.35B`，改 `PER_CELL`
   等于同时改四个数，五档实际只有一维。

修法不是压 `PER_CELL[2]`（那只把反向差挪到别处），而是**让每档换点东西**：
4 / 5 / 6 / 6 / 7，中间那一对同盘面的档改用规则分开——极难起点过的格不再退场。

| 档 | 盘面 | 点过的格 | 罚时 | S | A | B | 时辰 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 简单 | 4×4 | 退场 | 2 秒 | 16 秒 | 22 秒 | 28 秒 | 38 秒 |
| 普通 | 5×5 | 退场 | 3 秒 | 24 秒 | 33 秒 | 40 秒 | 54 秒 |
| 困难 | 6×6 | 退场 | 4 秒 | 33 秒 | 44 秒 | 56 秒 | 74 秒 |
| 极难 | 6×6 | **不退场** | 5 秒 | 32 秒 | 43 秒 | 56 秒 | 72 秒 |
| 绝境 | 7×7 | **不退场** | 6 秒 | 43 秒 | 56 秒 | 73 秒 | 95 秒 |

同盘面的困难 → 极难现在只看两件事：S 线紧 1 秒、时辰短 2 秒——都不是难点；
难点全在「盘面不退场」上。这三档的秒表差故意留得很小，因为**同盘面的两档
靠秒表分不开**（方差大于档差），分得开的只有规则。

审计仍然判不出「档差够不够大」——它只数「变了几个参数」。这条得靠
`tests/rank.test.js` 的「同盘面必须差一条规则」与 `verify` 8b-7 的「每格预算
必须递减」两条专门断言兜。

### 特例四：滑格相合——只有 2 个参数、4 种评级线

`target` 128 / 256 / 256 / 512 / 1024 与 `startTiles` 2 / 2 / 3 / 3 / 4。评级线 4 种而不是 5 种，因为困难与普通共用 `target = 256`，评级文字相同。

这一门刚过判据下限（2 个参数）。它的难度其实主要来自「起手块数」——从 2 块起手（每步只有 2 个方向有意义）到 4 块起手（棋盘几乎满，可走的方向极少），这个变化比 `target` 更明显，但只有 4 个台阶。若以后要加码，优先加第三个参数（例如棋盘边长或新块生成概率），不要动 `target`——`target` 一抬，单局时长就跟着涨。

## 四门「补第二个参数」的补丁

`buildParams` 末尾有这么一段注释与四行注入：

```js
// 四门原本只有一个可见参数在变：把第二个数按档注入，玩法层逐个读走（见上方表注释）。
if (method && method.game === 'mines') out.hearts = MINES_HEARTS[d.depth];
if (method && method.game === 'merge') out.startTiles = MERGE_START_TILES[d.depth];
// 顺序点格后来又补了第三个：点过的格退不退场（极难起不退，盘面始终是满的）。
if (method && method.game === 'schulte') {
  out.size = SCHULTE_SIZES[d.depth];
  out.fade = SCHULTE_FADE[d.depth];
  out.penaltySec = SCHULTE_PENALTIES[d.depth];
}
if (method && method.game === 'pushbox') out.capFactor = PUSHBOX_CAP_FACTORS[d.depth];
```

这四门是审计第一次跑出来时的「欠」档门。当时的状况：

| 功法 | 原本只有 | 补上的第二个参数 | 补后可见参数 |
| --- | --- | --- | --- |
| 数格辨禁 | `mines`（5→8） | `hearts` 3/3/3/2/2 | 2 |
| 滑格相合 | `target` | `startTiles` 2/2/3/3/4 | 2 |
| 顺序点格 | `size` | `penaltySec` 2/3/4/5/6（后又补 `fade` 与 7×7） | 3 |
| 推石入位 | `level` | `capFactor` 2.2→1.6 | 2 |

四条补丁的选型原则一致：**补的那个参数必须改变「容错」「起手条件」或「看得见的盘面」，不许只是让同样的操作变慢。** 心神减一、起手块加一、罚时加一秒、预算系数收紧、点过的格不再退场，都是玩家一进局就感受得到的；如果当初补的是「时长 ×0.9」，审计会过，但玩家感受不到。

这几张表与模块内的兜底值必须同源（`tests/rank.test.js` 逐门复算），改一处要改两处。

## 为什么审计不进 `npm run check`

`check` 的四步（`verify` → `test` → `sim` → `lint`）都必须是**确定性断言**：给定代码，输出恒定，红就是错。审计不是。

- **它判的是设计口径，不是代码正确性。** 「3 个参数在变」是对的，「2 个参数在变」也是合法的（滑格相合就是 2），差别在设计意图。把它挂进 `check`，会让「我就想只改一个参数」变成一次构建失败，逼着人先去改审计。
- **阈值是经验值，且会随玩法增加而调整。** 判据 ① 的 `>= 2` 是下限而非目标；以后一门新功法若天然只有 2 个可用参数，改判据是正常维护，不该牵连提交。
- **它回答的是「有没有变」，静态断言已经回答了「机制是否自洽」。** 两者的失败处理方式不同：前者要人判断，后者要人修代码。

`tests/rank.test.js` 里保留了一份**轻量复算**（内部档位键名单 `['depth','gear','sBase','sStep']` 与审计脚本同一套），用来守住「哪些键算内部键」这个口径本身不被随手改掉；具体某门有几参数在变，仍交给 `audit:diff` 人工看。

跑法：

```bash
npm run audit:diff
```

输出后要人工确认三件事：① 有没有 `★ 欠`；② 新增功法的「会变的字段」是否真的是玩家看得见的；③ 评级线的种数是否符合预期（比例评级类如阵灯会是 1 种，这是对的）。
