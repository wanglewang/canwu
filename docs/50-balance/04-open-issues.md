# 已知问题、待验收与待拍板

## 一句话

把散在 66 篇文档里的「待验」收成一份清单，并分成**必修（代码写错了）/ 该修（代码里躺着的死东西）/ 缺口（断言没守住）/ 待拍板（要人决定）/ 待验收（要真机证据）** 五类——因为这五类的处理方式完全不同。

## 口径

| 类别 | 判据 | 谁来处理 | 能不能在 `npm run check` 里发现 |
| --- | --- | --- | --- |
| **A 必修** | 代码/文案与设计真源不一致，玩家能看见 | 下一步就改 | ❌ 现在发现不了 |
| **B 该修** | 死代码、遗留方法、名不副实 | 找时间改 | ❌ |
| **C 缺口** | 断言存在但门槛过低，或该守的没守 | 补断言 | ❌（它本身就是断言的事） |
| **D 待拍板** | 两种做法都成立，需要人决定 | 决策 | ❌ |
| **E 待验收** | 只能靠真机 / 真人数据 | 真机跑一遍 | ❌ |

**这五类全都不在 `check` 里。** 这是当前的实际情况：`verify` 11 段 135 处断言守的是「结构完整、公式复算、文案不退化」，守不了「这句话说反了」「这个方法没人调」「这个阈值太松」。所以才有这篇文档——它是 `check` 绿了但项目仍然有欠账的那部分。

## A. 必修：玩家能看见的错

### A1. 指南把身法的换算写大了 10 倍

| 位置 | 说的是什么 |
| --- | --- |
| `pages/guide/guide.js:55` | 「身法**每 30 点**把切磋波动下限抬 1%（封顶 10%）」 |
| `utils/game.js:367` 注释 | 「身法给的切磋波动下限：**每 30 点** +1%，封顶 +10%」 |
| `utils/game.js:370` 代码 | `const SHEN_FLOOR_PER = 1 / 300;` |

实际是 **每 300 点 +1%**。身法 30 点只抬 0.1%，不是 1%。

后果：玩家照指南去堆身法，堆到 30 点以为拿到了 1% 的波动保护，实际只有 0.1%；堆到 300 点才拿满 10%，而 300 点在当前属性成长下几乎不可达（开局 11 点，靠功法加成能到的量级需要核算，见 `10-systems/09-attributes.md` 待验第三条）。**这项属性的独立出口事实上等于不存在**，指南却在承诺一个它没给的东西。

修法有两个方向，必须选一个，不能只改字：

1. **改代码**：`SHEN_FLOOR_PER = 1 / 30`，让指南成真。但这样一来 300 点身法会给出 10% 封顶，属性收益会被放大，要重跑平衡。
2. **改文案**：指南与注释都改成「每 300 点」，同时承认这项属性在中前期基本不生效——那就该重新设计它的出口（比如改成「身法直接折算成切磋波动下限的绝对值」，而不是线性累加）。

倾向第 1 种：设计意图（`utils/game.js` 注释写着「四个属性若都只进战力，玩家练哪门都一样，练功就没有方向」）明显是「每 30 点 +1%」，`1/300` 更像是敲错了一位。

### A2. 推石入位说「推不回来」，其实撤销得回来 —— **已修**

| 位置 | 修前 | 修后 |
| --- | --- | --- |
| `minigames/pushbox.js` 的 `costText` | 「推不回来：推错方向只能重来」 | 「推错可退一步，推数照算；复位后本盘最高 A」 |
| `minigames/pushbox.js` 的 `undo()` | 把 `boxes` 与 `pushes` **一起**回退 | 只回退位置与走步数，**推数照算** |
| `data/practice.js` 的 `tip` | 同上旧句 | 与 `costText` 同句 |
| `data/guides.js` 第 2 步 | 「推错方向只能复位重来」 | 「推错方向要绕一圈补回来，绕不回来就复位重来」 |
| `data/skills.js` 的 `flavor` | 「推错了就推不回来」 | 「推错了退得回来，账退不回来」 |

玩家读到「只能重来」，就会在推错一次后直接放弃本局——而实际上按撤销就能救回来。这句文案把一个可用功能说成了不存在。

**修的时候发现它不是单纯文案问题**：`undo` 把 `pushes` 一起回退，意味着推错可以无损反悔，一张固定的图能被白试出最优解。所以「改文案」不够，机制一起改了——现在撤销只退位置不退推数，文案才说得通（「推数照算」是真的）。同一类漏洞在滑块让路上是「复位清零回同一张图」，那门用封顶 A 堵，判据见 `00-foundation/02` 第九节 9.3。

**顺带清掉一处自相矛盾**：`guides.js` 的步骤列表原来第 2 步说「只能复位重来」、第 4 步说「可以撤销」——同一份说明里两句话打架。

### A3. 根 README 的难度门槛表比代码低一档 —— **已修**

| 位置 | 简单 | 普通 | 困难 | 极难 | 绝境 |
| --- | --- | --- | --- | --- | --- |
| 根 `README.md`（修前） | 0 | **400** | **1000** | **2500** | 6000 |
| 根 `README.md`（修后） | 0 | 300 | 1500 | 6000 | 24000 |
| `data/practice.js:289-293` | 0 | 300 | 1500 | 6000 | 24000 |

中间三档全错，绝境差 4 倍。同一段的段位标注也错了（写「普通 = 小成」，实际普通是**入门**档，`data/world.js` 的 `TIERS` 里 300 点正是「入门」）。已连同段位名一起改正。

**同一批修掉的还有两处数字**：这段后面写「逐档升 7305 点 / 退一档 6945 点」，`npm run sim` 实测是 **7290 / 6937**（`tests` 与 `sim` 的断言本来就是按 7290 / 6937 写的，只有 README 那一句是旧的）。第 118 行那份 sim 说明里抄了同样的三个数，一并改。

教训：这张表的真源只有 `data/practice.js` 的 `DIFFICULTIES[].need` 与 `data/world.js` 的 `TIERS[].threshold`，文档不许另立一套。而 `verify` 只核对「README 里的静态项数」与「README 指到了 checklist」，**不核对数值表**——所以它能漂很久不被发现。

### A4. 说明页分享丢参数，转出去的是一份泛稿 —— **已修**

`pages/help/help.js:22` 读三个参数：

```js
const topic = q.topic === 'practice'
    ? helpData.practiceTopic({ method: q.method, game: q.game, diff: q.diff })
    : helpData.topicOf(q.topic);
```

但 `onShareAppMessage` / `onShareTimeline` 只拼了 `?topic=`：

```js
const q = this.topicKey ? '?topic=' + this.topicKey : '';
```

后果：`topic=practice` 的分享点开后，`method` / `game` / `diff` 全是 `undefined`，`practiceTopic` 退化成一份不带功法名、不带本档 S/A/B 门槛的通用说明。而 `30-ui/06-page-skills-practice.md` 承诺的正是「说明页按链接带的 `diff` 列出本档 S/A/B/C 门槛」。

**修法（已落地）**：`onLoad` 里把三个参数记到 `this.topicQuery`，新增模块级 `shareQuery(page)` 统一拼串，两个分享钩子都走它。`onShareTimeline` 的 query 不带 `?`，所以函数只拼 `k=v&k=v`、由调用方决定要不要前缀。

**守卫**：`scripts/verify.js` 的 1d 段新增一条——`pages/help/help.js` 里必须同时出现 `method=` / `game=` / `diff=`，否则红。这条能拦住「以后又只拼 topic」，但拦不住「拼了却拼错值」，那一层只能靠真机点一次。

### A5. 突破按钮只判「能不能突破」，不判「灵石够不够」 —— **已修**

```js
onBreakthrough: function () {
    if (!this.data.ov || !this.data.ov.breakthrough.available) { return; }   // 修前
    wx.navigateTo({ url: '/pages/practice/practice?mode=breakthrough' });
}
```

`available` 是「境界到了、前置条件满足」，`stoneReady` 是「灵石够」。清单里两行分别画 ✓/✕，但按钮只挡了前一个。灵石不够时玩家点进去，会在参悟页被拦下来（那里会拒开局），等于白跳一次。

**修后**：`profile.wxml` 的按钮 class 与 `onBreakthrough` 同时判两件事，两件事分开给提示（「条件未齐」/「布阵灵石还差 N 枚，去切磋或秘境挣」）。这条对应 `docs/checklist-puzzle.md` 第五节「置灰与不可点有解释」——置灰必须灰在真实的原因上，而不是让玩家跨一页才知道为什么。

## B. 该修：代码里躺着的东西

### B1. 蓄力停区有两支永远走不到的分支

```js
const width = (hard ? 11 : 16) + (perks.easy ? 6 : 0);
const start = 42 + randInt(30);
const end = Math.min(96, start + width);
```

| 分支 | 为什么走不到 |
| --- | --- |
| `hard ? 11 : 16` 的 `11` 那一支 | 突破局 `difficulty` 恒为 `easy`，`difficultyOf('easy').gear` 恒为 `'normal'`，`hard` 永远 false |
| `Math.min(96, ...)` 的上限 | `start` 最大 71，`width` 最大 22（16+6），`71 + 22 = 93 < 96` |

第二支留着无害（是保险），第一支是**误导**：读代码的人会以为「突破也有难档」，进而去找那个难档在哪，找不到。

修法：把 `hard ? 11 : 16` 简化成常量 `16`，并在注释里写明「突破局只有一档，`perks.easy`（元婴起）是唯一的宽度变化」。或者反过来——如果本意是「元婴之后要有难档」，那就该真的把 `gear` 传进去，这是设计决策，不是清理。

### B2. 滑块让路的复位可以无限次免费用 —— **已修**

`reset()` 原本只清 `moves`，既不清「本盘复位次数」，也不消耗任何预算。玩家可以每走一步就复位一次，慢慢试出通路，然后按一次最优走法拿 S。

`minigames/lights.js` 对同一件事早有处理：用过阵眼感应或重置本盘，**最高只到 A**。两门同类玩法两套规矩，是遗漏而非选择。

**修法（已落地）**：`reset()` 置 `resetUsed`，把原来散在 `syncHud` 与 `finishOnce` 调用处的三处评级表达式收成一个 `gradeOf()`，见 `resetUsed` 就把 S 压到 A；`lines().items` 补第五条「复位过本盘，最高只到 A」，说明页照抄。复位次数仍不限——不限对走死的人是必要的，封顶已经把「反复重来」与「一步没浪费」分开。

**同时修掉的同根问题**：推石入位的 `undo` 把 `pushes` 一起回退（见 A2）。同一漏洞的另一种表现，堵法是「撤销不退推数」。

**守卫**：`tests/minigames.test.js`「按最优步数评级的三门」把阵灯 / 让路 / 入位各跑两遍（干净局必 S、先复位必 A）。

倾向第 1 种：跨玩法行为一致，玩家不用学第二套规矩。

### B3. `index.js` 的 `onBreakthrough` 没有任何绑定

`pages/index/index.js:196` 定义了 `onBreakthrough`，但 `index.wxml` 里搜不到 `onBreakthrough`。主页境界卡的突破行只显示文字与数值（`突破 战力 45 / 75`），点击不跳转——突破入口在人物页。

这是详情页时代留下来的方法（`pages/cultivate` 已删）。修法：删掉，或改成「点了跳人物页」。留着最差：下一个人会以为主页能突破。

### B4. 审计脚本的 `INTERNAL` 里有三个不存在的名字

```js
const INTERNAL = new Set(['depth', 'gear', 'sBase', 'sStep']);
```

实测 19 门全部档位的参数键共 50 个，`gear` / `sBase` / `sStep` **一个都不在里面**，只有 `depth` 真的被过滤。`tests/rank.test.js:787` 抄了同一份名单。

修法：收成 `['depth']`，两处同步改。名字挂着会让人以为背后有机制。

### B5. `recordError('error', error)` 会记成 `[object Object]`

```js
this.recordError('error', error);                        // app.js:83
this.recordError('promise', reason && (reason.message || reason));  // app.js:90
```

`promise` 那支取了 `message`，`error` 那支直接传对象。`recordError` 内部若做字符串拼接，得到的是 `[参悟][error] [object Object]`——真机上排查时这条日志等于没有。

修法：改成 `error && (error.stack || error.message || String(error))`。

### B6. 界面上「息」与「秒」两个单位混用

局内文案写「扣 1 息」「换不出少 2 息」，难度说明写「罚 10 秒」（九宫填数、顺序点格）。两者是同一个单位。

约定是「叙事用息、罚时用秒」（`00-foundation/04-voice-and-copy.md`），但玩家读不出这个区分，会觉得是两种计时。要么全用「息」，要么在术语表里明写「本门以息计时，一息为一秒」。后者更省事，也保住了门规口吻。

## C. 缺口：断言守不住的地方

### C1. 按压反馈的断言门槛是 5 处，实际有 48 处

`tests/layout.test.js:842`：

```js
assert.ok(total >= 5, '按压反馈覆盖不足：' + total + ' 处');
```

这个断言原本的作用是「新增页面别忘了挂 `.pressable`」，门槛 5 意味着**删掉 43 处也不会红**。它守的是「样式类存在」，不是「覆盖完整」。

修法：改成按页面断言——每个 WXML 至少 N 处，或总数随页面数算（`>= WXML.length * 2`）。硬写一个更大的固定值（比如 40）只能拖时间，加页面时又要改。

### C2. 隐私守卫只数 `guard(`，不数 `ensure(`，且只覆盖两页

`verify` 的隐私段按「调用数 ≤ 守卫数」核对剪贴板调用，但：

- 只数 `wx.setClipboardData` / `wx.getClipboardData` 这类显式调用，`privacy.ensure()` 的调用点不在核对范围；
- 只扫 `pages/secret` 与 `pages/battle` 两页，其它页面若新增剪贴板调用不会被发现（`pages/profile` 的存档码、`pages/board` 的战力码都在别处）。

修法：改成扫全项目 `wx.setClipboardData|getClipboardData|chooseAvatar` 的出现，逐处要求同一函数体内有 `guard(` 或 `ensure(`。

### C3. 19 门功法的 id 在两张表里没有一一对应断言

`data/skills.js` 的 `PRACTICE_METHODS`（功法）与 `data/practice.js` 的 `PRACTICE_METHODS`（玩法）是两份独立列表，靠 `skillId` 关联。没有断言检查「`skills.js` 的每个 `practiceId` 都能在 `practice.js` 里找到」，也没有反过来的检查。

漏一个的后果是：功法在谱系里显示「未习得」但点进去准备页拿不到参数，或者反过来——图鉴里有、参悟页白屏。这类错 `check` 全绿也拦不住。

修法：在 `verify` 里加一段双向核对（与页面注册那段同一个套路）。

### C4. 审计不校验「参数被注入后有没有被玩法读走」

`buildParams` 注入 `hearts = 2`，`mines.js` 若不读，审计照样判「过」。目前靠 `tests/rank.test.js` 逐门复算兜——但那只验算参数值，不验「参数在盘上生效」。

这一条**短期内无法用静态断言解决**（要跑游戏、读 vm），记在这里是让下一个人别以为「审计过了就等于参数生效了」。

### C5. 裸色值白名单是手工维护的

`styles/tokens.wxss` 之外写裸色值要进白名单（12 个文件）。新增一个带盘面色板的玩法时，容易忘了把文件加进白名单——或者反过来，加了白名单却没人核对它是否真的需要例外。

修法：白名单条目加一句理由（`// 盘面色板由 minigames/theme.js 注入`），并在 `verify` 里要求每条白名单都有一行注释。弱约束，但能让人停下来想一秒。

## D. 待拍板：两种做法都成立

### D1. 身法这项属性要不要存在（见 A1）

改代码让 30 点 = 1%，还是承认它在中前期不生效、重新设计出口。**这是本文档里唯一需要先定方向再动代码的一条。**

### D2. 数格辨禁的评级时间线要不要随档收紧

五档共用 `25 / 45 / 75` 秒，难度全压在禁制数（5→8）与心神（3→2）上。好处是不逼玩家猜；坏处是说明页对照五档时看不出「这一档更赶」。见 `50-balance/03-difficulty-audit.md` 特例二。

### D3. 顺序点格困难档的 S 线比极难宽

困难 34 秒 > 极难 32 秒，是「盘面在困难档跳到 36 格后不再变」的副作用。是否压 `PER_CELL[2]`（0.95 → 0.92）消除反向差，见 `50-balance/03` 特例三。

### D4. 灵石缺口靠重复切磋补，要多少场

全盘一次性收入 466 枚 vs 需求 783 枚，缺口 317 枚靠切磋（首胜 8 枚 + 当日衰减）。衰减取的是「当日第几场**胜利**」，而文案例写「当日第 n 场」——连败不消耗衰减额度。这是有利的松绑还是文案该改，未定。见 `10-systems/01-currency.md` 待验第二条。

### D5. `GRADE_DIST` 从未用真机校准

所有成长曲线结论（10000 局 / 84 局 / 6000 点预算五个方案）都建立在 `GRADE_DIST` 这张假设的评级分布表上。真人打出来的 S 率若与假设差一倍，`84 局毕业` 就变成 `42 局` 或 `168 局`。

这一条不阻塞开发，但它决定了 `50-balance/01-progression-curve.md` 里**每一个数字的可信度**。校准方法：找 5–10 个人各打 20 局，记录评级，替换分布表，重跑 `npm run sim`。

### D6. 「套壳」：玩法与功法之间还没有必然联系

有人玩过之后的原话是「一堆小游戏套了个修仙壳」。这个判断可以用一条测试复现：

> **换皮测试**：把 19 门功法的名字全换成「第 1 关…第 19 关」，玩法体验会不会变？
> 变了 → 玩法与设定有必然联系；不变 → 换了皮也不影响，那就是壳。

现在这条测试**在盘面上仍然通过**，但切磋 / 秘境这一路已经不通了（见下方「已补的第二半」）。盘面上的三处证据：

| 位置 | 事实 |
| --- | --- |
| `pages/practice/practice.js` | `qi` 只在准备页扣一次、结算显示一次；局内的 `onHint / onUndo / onReset` 直接调 controller，一分气不花、次数不限 |
| `utils/game.js` | 境界只进 `power / bonus / qiCap` 三个字段，筑基与元婴玩同一门功法，盘面规则一字不差 |
| `minigames/*.js` | 每门玩法都是完整信息的纯技巧游戏：三秀连收诀想的是「哪三连」，循数勘禁诀想的是「哪个有雷」——这些判断换到任何主题下都成立 |

**已经补上的那一半**（表现层，不改玩法）：练功 → 战力 → 破境 这条链原来只有系统知道，现在四处同源地说出来——功法页「再练到入门：战力 +4」、结算「战力 45 → 49（+4）」、主页「还差 30 · 点灯破阵诀到入门 +8」、人物页破境卡同一句。见 `10-systems/10-power.md` 第 4 节。

**已补的第二半**（机制层，2026-11-15）：**本场运功 —— 功法第一次真正出场**。

在此之前，功法对切磋的全部影响是 `effectValue('power')` 把所有 power 类特技加成一个百分比塞进 `rollBattle`：十九门全自动叠加，玩家看不见任何一门出场，十门「非战斗」功法（灵力上限 / 省气 / 回复）在切磋里彻底隐形。

现在：十九门各炼成一式（`data/moves.js`），一场至多运三式，**选中才生效**，结算卡上逐条落位并显示 `运功前 151 → 运功后 181`。三类对应三个出手时机——起手抬战力、守势抬波动下限、养息抵灵力（封顶 3 点，永远不能白打）。

这条改动让换皮测试在**对战这一侧失效**：现在得先想清楚带哪三式，而「带哪三门」正是「我练的是什么」的函数。但它**没有**动 19 门盘面本身 —— 所以下面那半仍然欠着。

**已补的第三小块**（盘面层的第一步，2026-11-15 第二轮）：**石箱归位诀的石图改成每局现抽**。

原来五张手排图按档分配，简单档永远第一张——第三遍开始玩家记的是答案，不是走法。这不算「套壳」，但它让换皮测试更容易通过：一门玩法如果打到第三遍就只剩回忆，那它本来就只有一层壳。
现在档位只给规格（内盘 4×4→5×5、阵位 1/1/2/2/3 处、内墙 0/1/1/2/2 道、最优推数区间），图由生成器**从解反向拉**出来，所以每局都可解、每局都不同。十九门里只有它按档分配固定图（其余都是随机布盘），所以也只改了它。见 `20-minigames/18-tuisuo-pushbox.md`。

这一条**不解决** D6 本身（玩法规则仍不来自设定），但它补上了盘面层的第一块：**可重复挑战 ≠ 同一张盘重复**。

**仍欠的那一半**（盘面层，最硬的那一半）：让玩法规则本身由修仙设定决定。样板：

- 三秀连收诀 → 加「灵田地力」：每格连收三次地力枯，继续收只给半分，三回合才回满。玩家于是会**不消最划算的那一处**——这个决策在任何非修仙主题下都荒谬。
- 循数勘禁诀 → 加「神识」：标一处禁位扣 1 点神识，标错扣 3 点，神识尽了你还能翻格但不能再标。

代价：19 门都要重设计一条规则，且与「三套经典玩法是黄阶入门功课、看一眼就会玩」的定位有冲突（黄阶本来就不该有新花样）。

**未定**：做不做、做几门、还是接受「经典玩法 + 修仙语境」这个定位并把「套壳」当作已知取舍。这条不阻塞开发，但它决定了这个产品到底是「修仙题材的小游戏集」还是「修仙游戏」。

**当前判断**：盘面层暂不动。理由是「黄阶三套经典玩法看一眼就会玩」是刻意定位，往盘面上加第二条规则会同时破坏「一次参悟 3–10 分钟」的节奏与「黄阶没有新花样」的品阶语义。**如果将来要动，从三秀连收诀（灵田地力）与循数勘禁诀（神识）这两门起**，它们是「三消 / 扫雷」最容易被说成套壳的两门，做完拿真机手感说话，再决定铺不铺开。

## D7 关卡的「每 5 关一个小变化」在整秒类玩法上做不到每段都动

- **现象**：毫秒类参数（落石间隔 / 亮起时长 / 翻牌停留）一格是 1ms，四十段够动四十下，
  每段都有变化。以整秒计的时辰一格就是 1 秒：20 秒那一档只有 20 格可动，四十段里只够动二十下，
  于是静心记诵诀 / 踏云连环步 / 阵法·点灯破阵诀这几门隔一段才动一格（约每 10 关一次）。
- **为什么不改成小数秒**：倒计时按秒显示，0.5 秒的变化玩家看不见，改了等于没改；
  真要让每段都动，得把时间收掉一半以上，那是断崖。
- **现在的口径**：界面上写的是「本段变化：…」，真有变化才报；没有变化就写「本段沿用上一段规格」。
  不假装有变化，也不把没动的一行摆出来。
- **待拍板**：要不要给这几门各加一条毫秒级副轴（例如判定窗 / 预算），换取每段都有变化。
  代价是这几门会多一个玩家要理解的数。

  难度轴、界面显示、盘面特效、引导、关卡变化五样，一门一套。
- **已过 4 门**（11 灵纹连线 / 12 落石垒基 / 13 三秀同收 / 15 滑格相合），
