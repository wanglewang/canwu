# 任务（Tasks）· 校验链：verify → test → sim → lint

> `npm run check` 一条命令跑四段。四段各管一类错误：**结构错、行为错、曲线错、风格错**。任何一段红，都不许提交。

## 核心前提：让每一种「红」都有归属感

我把校验拆成四段，不是为了显得严谨，是为了**红了之后立刻知道该往哪看**。一段巨大的检查脚本有两个毛病：慢，而且红了只能对着几千行输出发懵。四段各有语义——verify 说「东西没放对」，test 说「逻辑错了」，sim 说「数值歪了」，lint 说「语法脏了」——玩家（这里是改代码的人）一眼就知道去哪儿修。

这里有个刻意的克制：**曲线和审计不进断言**。sim 的红是「看输出不对」，audit:diff 只出报告。因为数值曲线是「看形状」的，硬卡阈值会逼着人改数据去迁就断言——那就本末倒置了。我只让能非黑即白的事进 `check`，需要人判断的事留给人。

第五段 `audit:diff`（难度区分度审计）我特意放在 `check` 外面。它回答的问题——「五段对这一门究竟改了什么」——静态断言答不了，而硬塞进 CI 只会逼出一堆为过审而加的假参数。

## 1. 概述

| 段 | 命令 | 回答什么问题 |
| --- | --- | --- |
| ① verify | `npm run verify` | 结构完整性（文件在不在、注册没注册、文案与真源同不同源） |
| ② test | `npm run test` | 行为正确性（五个测试文件） |
| ③ sim | `npm run sim` | 数值曲线的形状 |
| ④ lint | `npm run lint` | 语法与死变量 |

一个不起眼的第五段：`npm run audit:diff`（难度区分度审计）——**不进 `check`**，只读、出报告。

## 2. 为什么是四段而不是一段

一段巨大的检查脚本会有两个问题：慢（每次都跑全部）与难读（红了不知道是哪一类错）。

四段咬合的顺序是这样的——前两段把「错」挡在门外，后两段管「对得漂不漂亮、数值合不合理」：

```text
  ① verify ──▶ ② test ──▶ ③ sim ──▶ ④ lint
   结构对       行为对      曲线对     语法净
   (能跑吗)    (算对吗)   (数值歪吗) (有脏吗)
     │           │          │         │
     └───────────┴──────────┴─────────┘
              任一红 → 不许提交

  ⑤ audit:diff（只读、出报告，不进 check）
     ——「五段究竟改了什么」，留给人看
```
*（结构示意，非实测截图；箭头表示执行顺序，不代表命令输出。）*

四段各有明确语义，红了立刻知道该往哪看：

- verify 红 → 少注册了一个页面 / 文案抄了一份字面量；
- test 红 → 逻辑真的错了；
- sim 红（其实是「看输出不对」）→ 数值改歪了；
- lint 红 → 语法或未使用变量。

## 3. ① `verify` —— 11 段，项数见根 README「回归」表

`scripts/verify.js` 是一个纯静态检查器：读文件、正则、比对，不改任何东西。

| # | 段 | 查什么 |
| --- | --- | --- |
| 1 | JSON 可解析 | `app.json` / `theme.json` / 各页 json / `project.config.json` |
| 2 | JS 语法 | 对每个 `.js` 跑 `node --check` |
| 3 | **页面四件套** | `app.json.pages` 里每页的 js / json / wxml / wxss 都在；**磁盘上的 `pages/*` 都已注册**；**代码里写死的 `/pages/x/y` 跳转目标都是注册页** |
| 4 | 组件四件套 | 同 3，针对 `components/` |
| 5 | tabBar 图标 | 图标文件存在 |
| 6 | `theme.json` | 覆盖 `app.json` 里所有 `@变量`；且与 `tokens.wxss` 的令牌**同值** |
| 7 | 关键文件存在 | 一张清单（含 `styles/tokens.wxss`、`utils/store.js`、`data/visual.js`…） |
| 8 | 品阶与段位约定 | 品阶管收益、段位只由走通关数算，两套不许混（另见 8b / 11 段守卫） |
| 9 | **页面规范** | 令牌单一真源、明暗一致性、导航栏标题、**页面样式不写裸色值**、**CSS 变量拼错** |
| 10 | **文案与页面组织** | 文案真源唯一、术语可查、区块标题说人话、`<term>` 引用的 key 存在 |
| 11 | **三页信息架构** | tabBar 与导航真源一致、说明主题覆盖每页、解释性长文不回页面 |

### 3.1 第 3 段的三条，是从真实事故里长出来的

> 漏注册时 `wx.navigateTo` **静默失败**：页面文件齐全、旧断言全绿，也拦不住「点参悟没反应」。

1. 注册页的四件套齐全；
2. **磁盘上的 `pages/*` 都已注册**（新增了目录但忘了加 `pages` 数组）；
3. **代码里写死的 `/pages/x/y` 跳转目标都是注册页**（改了目录名但跳转字符串没改）。

第 3 条最值钱：它把「跳转字符串」和「注册表」绑在了一起。

### 3.2 第 9 段的「CSS 变量拼错」

```js
// CSS 变量拼错在小程序里是静默失效（不会报错，样式直接消失），必须静态兜住。
const tokenDefs = new Set([...tokenSrc.matchAll(/(--[\w-]+)\s*:/g)].map(m => m[1]));
const runtimeVars = new Set(['--acc','--soft','--ink','--bg','--frame','--glow','--deep','--well','--a','--d']);
```

扫所有 wxss 里的 `var(--x)`，只允许「令牌表里有的」+「运行时注入白名单」。**这是整套静态检查里最实用的一条**——小程序不会对未定义变量报错。

### 3.3 裸色值白名单

```js
const TOKENIZED = ['app.wxss', 'styles/immortal.wxss', 'pages/index/index.wxss', ...];
```

12 个文件命中 `#rrggbb` 或 `rgba(r,g,b` 即失败。白名单例外（它们本来就是色板）：`styles/tokens.wxss`、`styles/scene.wxss`、`pages/practice/practice.wxss`。

## 4. ② `test` —— 五个文件，五种职责

`tests/run.js` 顺序 `spawnSync` 五个文件，任一非零即整体失败。

| 文件 | 行数 | 管什么 |
| --- | --- | --- |
| `game.test.js` | — | 引擎：一局一关、耗气、战力、突破、存档迁移 |
| `store.test.js` | 215 | 存档：本地读写、pending、防抖、游客态、冲突 |
| `minigames.test.js` | — | 20 个模块逐门整局驱动、`teach` 走一遍、`lines` 必须导出 |
| `rank.test.js` | — | 逐门复算五段评级线、区分度 |
| `layout.test.js` | — | 页面与样式：令牌、按压反馈、页面名一致、盘面无汉字（运行时探针） |

**为什么用 `spawnSync` 而不是 `require`**：每个测试文件是独立的 Node 进程，一个崩了不影响其余四个的结论。跑完一次能同时看到「哪几个红了」。

### 4.1 `layout.test.js` 有两种检查

- **静态**：读 wxss / wxml，比对类名与断言（例如 `.pressable` 是否存在）；
- **运行时探针**：真的 `createGame()` 起一局，扫开局那一帧的 `vm.cells`，确认没有汉字上屏。

后者是唯一能守住「盘面不放汉字」的手段——静态读代码看不出运行时填了什么。

## 5. ③ `sim` —— 曲线的形状

`scripts/simulate.js` 用固定种子的伪随机模拟三种局面，输出可对比的数字。

### 5.1 它验的三条线

1. **进度** = 走通本门当前关就 `cleared + 1`，一个布尔，不吃品阶 / 难度 / 境界 / 属性 / 评级；失败、回关、没做成目标、已走完 1000 关一律 `+0`。旧版那套「基础点数 + 连 S 倍率 + 回关折减」已整条删除（存档 v10）；
2. **灵力** = 参悟与对战的运功消耗，唯一真源 `economy.practiceQiCost()`；它不产出，只从闭关、份例与灵石兑换来。所以「一局练多久」的度量是**「这一局烧掉的气，要闭关几分钟才回得来」**——或者「值几枚灵石」；
3. **灵石** = 切磋与秘境所得，当日第 n 场按 `0.85^(n-1)` 衰减；支出走功法、破境与兑灵力（`exchangeQi()`，1 枚 = 100 点，只此一向）。

### 5.2 评级分布是经验值

```js
GRADE_DIST = {
  easy:   { S: 0.25, A: 0.40, B: 0.25, C: 0.08, F: 0.02 },
  ...
  desperate: { S: 0.05, A: 0.15, B: 0.35, C: 0.33, F: 0.12 },
};
```

**这是假设，不是事实**。文件头写得清楚：「固定种子的伪随机只用来模拟评级分布，目的是在改数值前后可复现地比较曲线，不是预言真机数据。」

真机数据回来后要回来校准这张表——**它目前没有校准过**。

### 5.3 它出了哪些关键数

| 结论 | 数 |
| --- | --- |
| 走完 1000 关（全 C） | **1000 局 / 22020 灵力 / 734 小时** |
| 走完 1000 关（全 S） | **1000 局 / 22020 灵力 / 734 小时**（与上一条差值恒为 0） |
| 6000 点预算下逐关进 | 推 355 关 / 376 局 |
| 同上，只刷第 1 关 | 推 **1** 关 / 1000 局 |
| 同上，退一章再进 | 推 **1** 关 / 1000 局 |
| 同上，地阶逐关进 | 推 239 关 / 251 局 |
| 同上，黄阶金丹后 | 推 258 关 / 270 局 |

> 这张表在 v10 前后整体换过一次口径：旧表比的是「谁的进度点数多」（全 C 10000 局 / 248760 灵力、84 局 1959 灵力、只刷第 1 关 598 vs 逐关进 7290），那套点数已经不存在。现在比的是**真的往前走了几关**——因为回关恒 `+0`，「只刷第 1 关」与「退一章」都停在 1 关，不需要再靠数值护栏去挡。

这些数进了 `spec/系统设计/03-economy-flow.md` 与 `docs/specs/spec/系统设计/01-currency.md`。

## 6. ④ `lint` —— 六条规则

ESLint 9 flat config，只开六条：

```js
'no-undef': 'error',
'no-dupe-keys': 'error',
'no-dupe-args': 'error',
'no-unreachable': 'error',
'no-constant-condition': ['error', { checkLoops: false }],
'no-unused-vars': ['warn', { args: 'none', caughtErrors: 'none' }],
```

**不收编代码风格**。项目里没有 prettier、没有分号规则、没有缩进规则——`lint` 只抓「一定会出错」的东西。

`no-unused-vars` 是 `warn` 而非 `error`：小程序里有大量「保留参数」（`catch (e) {}`），改成 error 会逼出满屏 `// eslint-disable`。

`globals` 显式列出 `wx` / `App` / `Page` / `Component` / `getApp` / `getCurrentPages` 等微信注入的全局——不列就会满屏 `no-undef`。

## 7. ⑤ `audit:diff` —— 不进 check 的第五段

```bash
npm run audit:diff
```

它回答一个静态断言回答不了的问题：**五段对某一门来说究竟改了什么？**

若只有评级线在变，玩家从第一秒到最后一秒的操作对象、盘面、容错全一样，那一段就只是「结算时乘个数」。

判据两条：

1. 每段至少**两个玩家看得见的参数**在变（盘面 / 预算 / 容错 / 节奏）；
2. 评级线随段变，**或**盘面规格随段变。

```js
// 这三个是内部段位索引 / 系数来源，不是玩家在盘上看得见的东西
const INTERNAL = new Set(['depth', 'gear', 'sBase', 'sStep']);
```

**为什么不进 `check`**：它是「审计」不是「断言」——判据里带「至少两个参数」这种量化的东西，硬卡进 CI 会逼出一堆为过审而加的假参数。它只出报告，人来看。

## 8. ⑥ `audit:alerts` —— 不进 check 的差集告警

```bash
npm run audit:alerts            # 文本报告
npm run audit:alerts -- --json  # 结构化结果，给机器读
```

它回答四段断言回答不了的问题：**规格、测试、真实行为三者对不对得上？**

从 `docs/reviews/` 三张 R 卡的表格段取场景 ID 集合，真跑 `npm run check` 与
`npm run audit:gap`，按 `12-运行覆盖.md` 第 6 节的挂接表匹配输出，产出四类告警：

| 告警 | 集合关系 | 谁裁定 |
| --- | --- | --- |
| 盲区 | 规格有 · 测试无 | 人 |
| 缺陷 | 规格有 · 运行观测无 | 人 |
| 超范围 | D 挂接有 · 规格无 | 人 |
| 失败 | 校验命令跑红 | 机器直接拦下 |

任何一类非空就退出码 1。**D 侧不是 AI 读代码的推断**，是命令真跑出来的绿灯；
挂接表只写「认哪行输出」，命中才算观测到。四类告警各反证过一次，见 `docs/reviews/029-2026-11-24.md`。

**为什么不进 `check`**：它自己就要跑 `check`，塞进去会自递归。它也是目前唯一以 R 卡为输入的脚本——
R 卡改坏了它报红，正好补上 `verify` 只比对 R<sub>S</sub>/R<sub>T</sub> 之外的那一半。

局限：超范围只查「D 挂接表 ⊆ S」，实现偷加了行为而没人给它挂观测，机器看不见。
这条要彻底做，得让 sim / test 输出自带场景 ID。见 `docs/specs/constitution/06-评审方法论.md` §10 与本篇「待验」。

## 8a. ⑦ `audit:fidelity` —— 不进 check 的保真度校验

```bash
npm run audit:fidelity            # 文本报告
npm run audit:fidelity -- --json  # 结构化结果
```

它回答 `audit:alerts` 回答不了的问题：**三份 R 可以完美对齐、同时一起漏掉硬规则**。
差集只比对 R 之间，若 AI 提取 R<sub>S</sub> 时把硬规则写软（或本体被悄悄改了），差集一路绿灯。
所以最前面还有一道「本体 → 覆盖度」的保真度，原理见 `docs/specs/constitution/06-评审方法论.md` §7。

真源是两张 R 卡里的锚点表：每个活 ID 钉一句本体原文短语（`缩写:短语`），锚点必须是本体文件里的可辨字面量（用例标题 / 断言消息 / 源码串）。

**R<sub>S</sub> → 规格本体**（`10-规格覆盖.md`「保真锚点表」）：

| 方向 | 判据 | 红了意味着 |
| --- | --- | --- |
| 正查 | 每个活 ID 都钉了锚点；锚点短语能在对应 S 文件精确找到；锚点表不含退役 ID | R 自己加的，或契约被悄悄改了 |
| 反查 | 六契约「契约与守卫」段每个加粗条目都被某锚点指回 | 契约有承诺、R 漏提取 |

**R<sub>T</sub> → 测试本体**（`11-测试覆盖.md`「测试锚点表」）：只做正查——活 ID 都钉了锚点、锚点能在对应测试文件精确找到、锚点表不含退役 ID。断言被删或改弱，锚点当场失配。反查未做（测试有几百条用例，不可能逐条挂 ID），漏挂由 `audit:alerts` 的盲区间接守。

**R<sub>D</sub> → 运行观测**：挂接表本身就是「指回哪次运行哪行输出」，命中校验由 `audit:alerts` 承担，不在此重复。

任何一项非空就退出码 1。R<sub>S</sub> 五类、R<sub>T</sub> 四类各反证过一次：本体硬规则改一个字、测试断言改弱、锚点短语改错、删一行锚点、给退役 ID 钉锚点、本体加一条没人提的承诺——全部报红并定位到具体 ID，见 `docs/reviews/030`、`031-2026-11-24.md`。

**范围**：宪法 §三 7 条不变量里 4 条已由契约条目 ID 覆盖，只钉 3 条独有 ID 的锚点；六契约 30 个加粗条目走反查。本体自己被删掉一条（锚点也跟着删）不在能力内——那是「本体变更要人审」，不是保真度。

**为什么不进 `check`**：与 `audit:alerts` 同理，它以 R 卡为输入，R 卡改坏了它报红；但本体正文改动不触发 `check` 的项数，单独成段靠提交前手动跑。

## 9. 提交前的最小动作

```bash
npm run check          # 四段全绿
npm run audit:diff     # 改了难度相关的东西才跑
npm run audit:fidelity # 改了规格 / 测试 / R 卡锚点才跑；两类保真度告警必须全 0
npm run audit:alerts   # 改了规格 / 测试 / R 卡才跑；四类告警必须全 0
```

然后一次 `git push` **双推 Gitee 与 GitHub**。

## 10. 被否决的方案

这些否决背后是一个判断：**断言只钉能非黑即白的事，需要人看的东西别硬塞进 CI**。sim 和 audit:diff 都是「看形状」的，卡死会逼出假数据；而 test 拆五个进程、lint 不收编风格，都是为了让每一段各管一类错、不互相污染。把工具选得克制一点，校验链才不会变成新的负担。

| 方案 | 为什么否掉 |
| --- | --- |
| 只跑 test | 结构错（漏注册）test 完全测不出来 |
| 只跑 verify | 它不懂业务逻辑 |
| 把 sim 做成断言 | 曲线是「看形状」的，硬卡阈值会逼着改数据迁就断言 |
| 把 audit:diff 放进 check | 同上，会逼出假参数 |
| 用 jest / vitest | 需要构建链；小程序项目保持「node 直接跑」 |
| 用 prettier | 全项目重排一次，git blame 全废；收益只有格式一致 |
| 一次 `node` 里 require 全部测试 | 一个崩了其余不跑，看不到全局 |

## 11. 代码指路

- `scripts/verify.js` —— 11 段，项数见根 README「回归」表
- `tests/run.js` —— 五个文件的顺序执行器
- `scripts/simulate.js` —— `GRADE_DIST` 与三张曲线
- `scripts/difficulty-audit.js` —— `INTERNAL` 白名单与两条判据
- `scripts/diff-alerts.js` —— 场景 ID 差集、R<sub>D</sub> 挂接表匹配、四类告警
- `scripts/fidelity-check.js` —— 保真度：R<sub>S</sub> 锚点精确匹配 + 六契约条目反查、R<sub>T</sub> 测试锚点精确匹配
- `eslint.config.js` —— 六条规则 + 微信全局
- `package.json` —— `check` 的四段串联

## 12. 待验

- **`GRADE_DIST` 从未用真机数据校准**。v10 起它只决定结算观感与挂机加成，不再影响进度或耗气——「全 S 84 局到顶」「7290 点」那套推算随连 S 一起作废，真值是全 S 与全 C 同为 1000 局 / 22020 点。真机数据回来后要复算的是观感曲线，不是进度线。
- **保真度的反查只做到 R<sub>S</sub>→S**：`audit:fidelity` 守 R<sub>S</sub> 正反双向、R<sub>T</sub> 正向（锚点指回测试文件）。R<sub>T</sub> 反查未做（用例几百条无法逐条挂 ID，漏挂靠差集盲区），R<sub>D</sub> 的命中校验由 `audit:alerts` 承担。三份 R 若一起把某条测试/观测写软，仍看不见。
- 裸色值白名单是按**文件名**列的：新增页面必须记得加进 `TOKENIZED`，否则那一页可以随便写色值而不被拦。
- 按压反馈断言的阈值是 `total >= 5`，而实际已有 48 处——**这个门槛等于没守**，建议改成「每个 wxml 至少一处」或「总数不低于某个更接近现状的值」。
- `verify` 3 段的「跳转目标都是注册页」靠正则抓 `/pages/x/y` 字面量；**拼接出来的跳转**（如 `'/pages/help/help?topic=' + key`）只能抓到前半段，抓不到 `?` 之后。目前够用，但新增动态路径时要小心。
- `layout.test.js` 的运行时探针只扫「开局那一帧」。若某门玩法在开局后才把汉字写进 `label`，探针看不见。
