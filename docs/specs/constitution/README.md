# 宪法（Constitution）· 总纲与目录

> 这是宪法层的入口：一份总纲（本篇）+ 六篇实体（产品定位、设计原则、术语、文案纪律、评审方法论、外部资料）。
> 六份行为契约（`spec/`）各自成文，但都受这里的不变量与原则约束。
> 总纲只列约束本身和「哪一篇讲什么」，正文在实体篇里——同一事实只写一处，这里不抄第二份。

## 一、这份文档的位置

规格驱动开发（Spec-Driven Development，SDD）把规格当作唯一真相源：代码和测试从它派生，
改行为先改这里，再让实现跟上。它与 RDD 的关系见 `docs/specs/constitution/06-评审方法论.md`——
RDD 管需求还在探索的那段，需求稳定后收敛到这里。

**这条链是有向的**：`S → T → D`，三层各派生一层覆盖度 R<sub>S</sub> / R<sub>T</sub> / R<sub>D</sub>。
S 是起点，由**人提出意图、AI 起草成文、人再纠正确认**——AI 不能自己定规格然后自己验收。
T 从 S 派生，D 从 T 派生；链条方向与审核反馈规则见 `docs/specs/README.md`。

四样东西不要混：

| 文档 | 回答什么 |
| --- | --- |
| 本目录六篇（本篇 + 实体篇） | 为什么做、按什么原则做、名词怎么叫、文案怎么写、怎么审——跨契约共性 |
| `spec/` 六契约 | 系统承诺的行为、不变量、禁止项、边界——可测的契约 |
| `plan/` 设计文档 | 这些契约怎么设计出来——机制、参数、依据、被否决方案 |
| `data/*.js` 与 `scripts/verify.js` | 数值的唯一出处，以及守住这些契约的断言 |

本目录 six 篇的分工：`01` 产品定位与体验目标（范围、非目标、三层约束框架）、`02` 十三条设计原则（不变量的原则来源）、`03` 术语表、`04` 文案口吻规范、`06` 评审方法论（维护纪律）、`07` 外部实践资料（设计依据摘录）。编号 `05` 空缺不复用——它曾是本目录之外的编号，保留空位避免历史指代错位。

**规则**：规格里出现数值的地方只写「见真源」，不写具体数字。谁抄了一个数，
下次改 `data/*.js` 时它就过期，规格反而成了误导。唯一例外是纯结构性事实（比如「五段」「十五门」），
因为它们本身写在真源常量里，且由断言钉住。

## 二、范围与非目标

范围（做什么）与明确不做（Non-goals）的实体在 `01-产品定位与体验目标.md`——那里有一整趟参悟的描述、
目标玩家画像，以及按三层约束框架分好的「哪些是真不能动、哪些只是当前默认值」。
非目标不是物理定律，是当前的默认取舍；翻案要走人审。总纲这里不复述，只指向那篇的 §5。

## 三、不变量（无论怎么改都必须成立）

这些约束横切六份契约，任何一份契约改动都不许突破它们：

- 熟练度不为负、不越过硬顶；连击有层数上限；对局退出则连击清零。
- 段位只由走通关数决定；十五门功法各有独立的内核，不做通用特效层（判重见 `tests/minigames.test.js`）。
- 灵力不能反向兑成灵石；参悟不产灵石；灵力最低 1 点，不许扣成负数。
- 「全部 / 集齐」的门槛读 `SKILLS.length`，不写字面量。
- 评级线只有一个出处 `lines()`；有失败态必须给 `fail` 结论。
- 符号一律 CSS 画，不许用会变彩色 emoji 的字符；用色只认令牌真源。
- 每页同步皮肤；新页面必须注册进 `app.json`；判定改一处要同时改所有消费端。

每条不变量的守卫写在对应契约里（`02`~`07`），不在这里重复——这里只列约束本身。

## 四、开放问题（未定，不许实现者替玩家决定）

这些是悬而未决的取舍，实现时**不得自行选一个做掉**，要以人为准。完整清单与背景在
本目录 `08-待拍板清单.md`（D1–D18）；此处只列会造成行为分叉的几条：

- 后三段的关卡密度是否撑得住（D11）——直接决定「熟练度先毕业还是关卡先毕业」。
- 身法属性在中前期是否生效（D1）——决定要不要改属性出口。
- 熟练度封顶后仍要烧气继续练，这条是否保留——决定 `spec/02-成长.md`「到顶后照扣」是否翻案。

## 五、维护纪律（防规格漂移）

SDD 最大的失败模式不是没写规格，是规格和代码悄悄脱节，然后 AI 照着过期规格自信地改错。
因此：

- **改行为先改对应契约**：实现与规格冲突时，先判断是规格错了还是实现错了；改契约要连同守卫一起改，并按 `README.md` §三 走反馈回溯。
- **每条契约都要有会红的守卫**：写一条行为，就问「哪条断言会在它被破坏时报红」；答不出就补断言。
- **写完断言要反证**：故意把实现改坏一次，确认断言真的红；不红说明断言空转（项目铁律）。
- **数值只指真源**：规格不存第二套数字；改数值看 `docs/specs/spec/50-balance/02-numbers-reference.md` 与根 README 三处同步。
- **翻案走人审**：非目标和开放问题的改动要人点头，不能因为「实现起来更顺」就悄悄改口径。
