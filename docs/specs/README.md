# 规格体系（docs/specs/）

> 这个目录管「规格怎么产出、怎么往下传、怎么被审查」。它是规格驱动开发（SDD）在本项目的落地。
> 方法论背景见 `docs/specs/constitution/06-评审方法论.md`，产品意图见 `docs/specs/constitution/01-产品定位与体验目标.md`。

## 目录骨架：SDD 标准四层

业界 SDD 的标准骨架是四份文件——constitution（宪法）、spec（需求）、plan（计划）、tasks（任务）。
本项目内容量大，每一层是一份**文件**的地方在这里扩成**目录**，职责一一对应：

| 标准骨架 | 本目录 | 装什么 |
| --- | --- | --- |
| `constitution.md` | `constitution/` | 项目宪法：产品定位、非目标、十三条设计原则、术语、文案纪律、开放问题、评审方法论——跨契约共性，宪法的实体，不是指针（8 篇） |
| `spec.md` | `spec/` | 需求规格：全部 **what**——六份行为契约（S 本体，带会红的守卫）+ 系统设计 19 + 玩法设计 97 + 界面 13 + 数值 4 + 总目录与自检清单（141 篇） |
| `plan.md` | `plan/` | 技术计划：全部 **how**——6 篇工程实现（目录分层、玩法契约、异常生命周期、隐私、性能、导航）+ 总目录（7 篇） |
| `tasks.md` | `tasks/` | 落地映射：测试规格（T）、实现规格（D）、校验链、测试职责、未修欠账 / 真机验收 / 已修归档（待拍板在 `constitution/`）——每条契约落到哪些测试与真源，以及还剩哪些债（7 篇） |

四层严格按 SDD 的 **"spec says what, plan says how"** 分，不按文件名教条：**凡是讲"范围/底线/怎么审"的进宪法，讲"承诺什么、设计成什么样"的进规格（what），讲"代码怎么实现出来"的进计划（how），讲"落到哪/还剩什么"的进任务**。判断一个文件该在哪一层，问它回答的是哪一类问题，而不是看它历史上被放在哪。

判 what 还是 how 的实操尺子：删掉实现细节（文件名、接口、断言位置）后，剩下的那句若还在回答"这游戏/这段规则是什么样"，就是 spec；若只剩"代码怎么组织、怎么测、怎么兜错"，才是 plan。例：`双货币体系：灵力是油、灵石是钱、单向闸` 是 what（spec）；`目录分层与数据流：五层依赖只能向下` 是 how（plan）。

三份覆盖度 R<sub>S</sub>/R<sub>T</sub>/R<sub>D</sub> 是从这三层提取出来给人审的视图，
按同类归到 `docs/reviews/`，不属于本体四层。链条 S→T→D、审核反馈规则见下文。

## 一、链条是有向的

从人开始，逐层派生：

```
人提出意图
    ↓  AI 起草成文、人纠正确认
S  规格         承诺什么、底线是什么、不许做什么（总纲 + 六份契约）
    ↓  派生（每条契约变成一个测试场景）
T  测试         用哪些场景校验 S
    ↓  派生（每个场景落成一段实现）
D  实现         真正跑出来的代码
    ↓  各层提取一份覆盖度
R<sub>S</sub> / R<sub>T</sub> / R<sub>D</sub>   三层各自的「覆盖了哪些场景」集合，供机器比对
```

方向不可倒过来：**先有 S 才有 T，先有 T 才有 D**。反过来让代码或测试去定义规格，
就是让实现者给自己出题判卷——AI 写的代码看起来天然符合它自己读过的规格，判断与实现同源。

## 二、每一层谁产出、谁认领

| 层 | 谁产出 | 谁点头 | 不许做什么 |
| --- | --- | --- | --- |
| **S 规格** | 人提出意图，AI 起草成文 | **人纠正确认** | AI 自己定规格又自己验收 |
| **T 测试** | AI 按 S 派生场景 | 人认领覆盖范围，尤其「未覆盖风险」 | 按错误实现生成测试；只断言「没抛异常」 |
| **D 实现** | AI 按 T 写代码 | 机器每次校验，人只看差集 | 绕过 S/T 自己加行为 |
| **R 覆盖度** | AI 从本体提取，机器比对 | 人只审三份对不齐的地方 | 读代码猜出来的 R<sub>D</sub>（必须靠跑） |

关键在第一行：**规格的源头是人**。AI 会写规格，但「什么算对」由人定；AI 起草后必须经人纠正。
全链 AI 生成 + AI 自检只能证明三份产物互相自洽，证明不了符合人的要求。

## 三、审核反馈：问题在哪显现，不等于根因在哪

人审的是 R（覆盖度），但**不能直接改 R**——R 是从本体提取的视图，直接改它下次提取又被覆盖。
发现问题要改本体，再重新提取。

关键一条：**问题显现在哪份 R，是表象；根因在 S / T / D 哪一层，要诊断。审任何一份 R，三层都可能要改。**
不要按「审 R<sub>S</sub> 就改 S、审 R<sub>T</sub> 就改 S+T」那种查表法预设根因——问题在哪被看见，和问题从哪来，是两件事：

- 审 R<sub>S</sub> 觉得某条契约不对，根因可能是 S 真写错了，也可能是测试验错让人误读了规格，还可能是实现跑偏暴露出契约本就含糊。
- 审 R<sub>T</sub> 发现覆盖缺口，根因可能是 S 契约不清让测试无从派生，可能是 T 派生漏了，也可能是 D 压根没实现这个场景所以测试没写。
- 审 R<sub>D</sub> 看到行为偏离，根因可能是规格错、测试漏、实现偏——三处任一，或叠加。

所以 AI 每接到一份 R 的意见，都要过一遍 S、T、D，判断这次到底改哪几层（可能只改一层，也可能三层全动）：

| 人审的是 | 表象（在哪看见） | AI 要诊断并可能改的本体 |
| --- | --- | --- |
| R<sub>S</sub> | 契约、底线、禁止项看着不对 | S / T / D 任一或全部 |
| R<sub>T</sub> | 覆盖漏了、验错了 | S / T / D 任一或全部 |
| R<sub>D</sub> | 真实行为偏离契约 | S / T / D 任一或全部 |

改完以后，**三份 R 全部重新生成**——不管这次改的是哪一层。因为 S→T→D 是有向链：
改了 S，T、D 及三份覆盖度全部失效；改了 T，D 与 R<sub>T</sub>、R<sub>D</sub> 失效；改了 D，R<sub>D</sub> 失效。
只重出被审的那一份，另外两份会留着旧视图，下次对照就是假告警。全量重出是保持一致的最省事做法。

闭环：人审任一份 R 提出意见 → AI 诊断 S/T/D 根因、改该改的层 → 重新生成全部三份 R → 交回人再审。
每一轮都重新给全套，人不用记上一轮改了哪层。

**覆盖度单独成目录** `docs/reviews/`，与 `docs/specs/` 平级——R 是从本体提取给人审的视图，不是本体本身，不混放。

| 文件（在 `docs/reviews/`） | 是什么 | 记什么 |
| --- | --- | --- |
| `10-规格覆盖.md` | 从 S 提取的覆盖度 | 规格承诺了哪些场景（方法论 §2.1 七维度）+ 场景 ID 总表 |
| `11-测试覆盖.md` | 从 T 提取的覆盖度 | 测试覆盖了哪些场景、漏了哪些（方法论 §2.2 六维度） |
| `12-运行覆盖.md` | 从 D 提取的覆盖度 | 代码跑出哪些场景、和规格差在哪（方法论 §2.3 六维度，靠跑不靠读） |

**S 的契约不是一份，是六份**：每份管一个行为域，各带会红的守卫。
拆开的判据是「能独立审查」——改对局规则不必重读经济契约，审经济契约的人也不用被教学细节干扰。
但拆开不等于割裂：六份契约共享宪法的不变量与开放问题，任一契约改动都要回到 §三 的反馈规则走全链。

**契约与设计展开都在 spec 层**：六份契约是可测的行为承诺（S 本体），`10-systems/` 等四组 133 篇是这些承诺的设计展开（what 的细节）——按 SDD，两者同属 spec，不放 plan。spec 层的总目录是 `spec/README.md`。

**T / D 只做映射导航**，不复制测试断言细节和代码实现——那样会变成第二套要维护的真相。
具体断言在 `tests/`，真源在 `data/*.js`，三份 R 的提取维度在 `docs/specs/constitution/06-评审方法论.md`，这里都不重复。

## 五、三份覆盖度怎么比对

统一场景 ID 是命门：同一个场景在 S/T/D 里必须叫同一个名字（如 `SC-COMBO-CAP`），
机器才能做差集。当前状态如实记在 `docs/reviews/` 各文件里——**R<sub>S</sub> 的场景 ID 表已建（29 个独立 ID）**，
但 R<sub>T</sub> 只挂了 3 个、R<sub>D</sub> 的运行观测未接入，**差集告警脚本还没建**。
不许把「表建了」当成「三份能对上了」；比对这一层是欠账，不是完成项。

三层对齐模仿编译器前端：源码（S）、测试用例（T）、运行结果（D）互相校验，任何一端改了，
另两端要跟着重算。人只看差集（漏测、代码缺、超范围、跑失败），全齐的部分折叠掉。

## 六、维护纪律

- **改行为先改 S**：实现与规格冲突时，先判断是规格错了还是实现错了；改规格要连同 T、D 一起重算。
- **每条契约要有会红的守卫**：写一条行为就问「哪条断言会在它被破坏时报红」；答不出就补断言。
- **写完断言要反证**：故意把实现改坏一次，确认断言真的红；不红说明空转（项目铁律）。
- **数值只指真源**：本目录不存第二套数字；改数值看 `docs/specs/spec/50-balance/02-numbers-reference.md` 与根 README 三处同步。
- **文档名用中文**：这是给中国人读的规格，文件名一律中文；代码文件（`data/*.js`、`tests/`、`scripts/`）保持英文。
- **S 的改动要人确认**：AI 可以起草，不能自己点头；开放问题的取舍要人拍板。
