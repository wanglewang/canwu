# 需求（Spec）· 难度区分度审计

## 核心前提：五段是真的在变，还是只换了个结算系数

我先摆出这份审计要抓的那个问题：一门功法在存档里明明有五档，玩家玩起来却可能只有一档——后两段只是把结算时乘的数改了，盘面、容错、节奏一动不动。这不是难度，这是「慢一点」或者「少一点」。玩家打一百多关说不出哪变了，问题就出在这。

所以我写了一份脚本，专门回答静态断言回答不了的那句话：**五段对某一门来说，究竟改了什么**。它数「有没有至少两个玩家看得见的参数在变」「评级线或盘面规格有没有随段变」，然后出一份报告让人来看。

但我刻意不让它进 `check`。因为它判的是设计口径，不是代码正确性——「三个参数在变」对、「两个参数在变」也合法（滑格相合就是两个），这是设计意图，不是错。把它挂进 CI，只会让「我就想只改一个参数」变成一次构建失败。它出报告，人来判断，这个分寸很重要。

这篇最值钱的部分在末尾那几个特例：阵灯评级线只有一种照样过、数格辨禁靠放大盘面而不是收紧时间、顺序点格曾经后三段挤在同一个盘上。它们记的都是同一件事被反复验证的教训——**难度要落在「要想的东西变多」上，不是「把秒表调小」**。

## 一句话

用一份脚本回答静态断言回答不了的问题：五段「简单 / 普通 / 困难 / 极难 / 绝境」对某一门功课来说，**究竟改了什么**。

## 目标与非目标

**目标**

- 揪出「五段只换了个结算系数」的功法。这类功法在存档里看起来有五个档，玩家玩起来只有一段。
- 让「新增玩法必须真的分级」这件事有一个可执行的判据，而不是靠写的人自觉。
- 把每门功法「哪两个可见参数在变」写下来，改数值的人一眼知道动哪个键才有意义。

**非目标**

- **不判「变得够不够难」。** 那是收益曲线、真机手感、评级分布的事，静态脚本判不了。
- **不判「变得合不合理」。** 比如顺序点格曾把后三段全放在 6×6 上、只差 1–3 秒 S 线（见下文特例三），审计照样判「过」——因为它确实在变，只是变的幅度小于随机布局的波动，玩家感受不到。这类问题要靠专门的断言与真机，见特例三末尾。
- **不进 `npm run check`。** 见最后一节。

## 判据

脚本 `scripts/difficulty-audit.js` 对 15 门逐一跑，两条同时满足才算「过」：

| # | 判据 | 意图 |
| --- | --- | --- |
| ① | **每段至少两个玩家看得见的参数在变**（盘面 / 预算 / 容错 / 节奏） | 一个参数变，玩家感觉不到那叫难度，只叫「慢一点」或「少一点」 |
| ② | **评级线随段变，或盘面规格随段变** | 否则说明页五段写同一行字，玩家没法对照自己该打多少 |

第 ② 条留了「盘面规格随段变」这个替代出口，是因为有一批功法（九宫、阵灯、神识、滑块、推石、开锋）的难度**写在盘上，不写在数字上**——4×4 变 5×5 没有任何数字参数变化，但玩家一进去就知道紧了。

把这两条判据的判定过程画出来，就是一道两问的闸——第二问有两条路可走：

```text
        一门功法的五段参数
               │
      ┌────────▼────────┐
      │ 问①：≥2 个玩家    │
      │ 看得见的参数在变？ │
      └────┬───────┬────┘
          否       是
           │        │
          ❌      ┌──▼────────────┐
        记「欠」  │ 问②：评级线变？ │
                 │  或盘面规格变？  │
                 └──┬────────┬────┘
                   否        是
                    │         │
                   ❌        ✅ 过
                 记「欠」
```
*（结构示意，非实测截图；菱形是判定节点，不代表界面。）*

**第三列「主轴跨度」不参与判定，只提示。** 跨度小可能是物理限制（时间轴压不动），也可能是设计没做完（时间轴本不该当主轴）——审计分不清这两者，所以只标 `*` 不报错。真正该拦的写在 `tests/rank.test.js` 里，按门逐个标定。

### 参数怎么被判定为「变」

对每门功法调 `practice.buildParams(method, key)` 拿五份参数，逐键去重，只留「五段里出现过两种以上取值」的键。被排除的键只有一类：

```js
const INTERNAL = new Set(practice.INTERNAL_PARAM_KEYS);  // 真源 ['depth']，别在文档里抄第二份
```

`depth` 是「第几段」（0–4），任何按段注入的整表都靠它取行，它必然在变，但它不是玩家看得见的东西。其余三个名字——`gear`（`normal` / `hard` 两值，给玩法分难度用的）、`sBase` / `sStep`（历史遗留的评级线基数与步长）——**在当前 `buildParams` 的返回里都不存在**。实测 15 门所有段位合并起来共 50 个参数键，`gear` / `sBase` / `sStep` 一个都没有。

也就是说 `INTERNAL` 这个集合实际只过滤了 `depth`；另三个是留给「以后真加了这几个键」的保险。这不影响结论（多排除一个不存在的名字不会让任何功法误判为「过」），但名字挂着容易让人以为有机制在背后，属可清理的欠账。

### 五段参数是怎么来的

审计读的是 `buildParams` 的输出，所以必须先知道这个函数的施加顺序，否则会误读表里的数字。顺序是：

1. 复制功法自带的 `params`；
2. **`PACE_KEYS` 十项**（含 `life` 与判定窗 `window`）× `pace`（`1.18 / 1 / 0.88 / 0.78 / 0.7`）；
3. ~~`WINDOW_KEYS` 一项（`life`）× `windowPace`~~ —— 已退役。`life` 并回第 2 步，那个空数组与
   `DIFFICULTIES.windowPace` 字段都删了：五段写了一列数却无人消费，正是「生成了没生效」；
4. **`GOAL_KEYS` 十项** × `goal`（`0.85 / 1 / 1.12 / 1.22 / 1.32`），并夹在 `capFor(key)` 上限内；
5. `duration` / `timeLimit` × `TIME_LEVELS`（`1 / 0.97 / 0.94 / 0.91 / 0.88`），最低 8 秒；
6. 透传 `depth`，再由**六份按段整表覆盖**（三秀 / 阵灯 / 九宫 / 滑块各一份，加上四门「补第二个参数」的单值注入）；
7. `steps` 每段 +1；`speed` 除以 `pace`（越快的段 speed 越大，方向与其他键相反）。

顺序决定了一件事：**整表覆盖发生在缩放之后**，所以三连互换的 `duration`（步数制下是手数预算，段基准 57/53/48/43/38）不是 `base × TIME_LEVELS` 算出来的，而是表里直接写的。改的时候要改表，不是改系数。

`TIME_LEVELS` 的用意也在注释里写着：时辰收紧是「这一段到底紧在哪」最直白的一条，玩家一进局就看见倒计时在少。

灵纹连线这一行是整改后的口径：旧表记的「1.69× `flashMs`」只是提示高亮变短（帮助变差，不是本事要求变高），把它当主轴跨度会让这一门在复杂度 / 信息 / 规模上用了 0 根还躲过提示。现在主轴是真会改盘面的 `kinds` / `cols` / `turns`，`flashMs` 退役为恒定的 `hintMs`，连「会变的字段」里都不再出现。

灵纹连线的 `49.50× hints` 与三秀的 `50.00× goalCount` 别读成「难度涨了五十倍」：前者 `99` 是「不限」的哨兵值，跨度里有一大半是「从无限到有限」；后者是目标株数从少到多，都是真台阶但不是倍数意义上的难度。它是真台阶（玩家确实从「随便重排」变成「只剩三次」），但不是倍数意义上的三十倍。

## 主轴跨度：审计的第三个数

前两列（可见参数、评级线）回答「有没有变」，第三列回答「变了多少」。

原来的判据只有前者，于是 `滑格相合` 的 8 倍和 `顺光扫斩` 的 1.15 倍得到同一个结论「过」——可玩家感受完全不同，前者每段都在换目标，后者五段几乎一个手感。**这是旧审计最大的盲区：它守得住「压根没变」，守不住「变了跟没变一样」。**

### 为什么是 2 倍这条线

玩家的难度可辨阈值约 5%：相邻两段的参数差不到 5%，玩家说不出「这段更难」，只会觉得「差不多」。

- 跨度 **1.7 倍**摊到四段间隔，每段 14%——能明确分辨；
- 跨度 **1.15 倍**摊到四段，每段只有 3.6%——落在阈值下，等于五段一个手感。

所以 `<2 倍` 标 `*`。**这不是报错，是提示**：它说明这一门的承重轴压不出量来，该换一根轴了。

### 2 门标 `*`，都是时间类，不是「等于没变」

现在标 `*` 的只剩 **记序复现**（1.69× `gapMs`）与 **成对翻牌**（1.69× `flipMs`），两门的最大跨度恰好一样，这不是巧合——它们的承重轴都是时间类参数，而时间类统一走 `PACE_KEYS × pace`，`pace` 表本身就是 1.18 → 0.70（1.69 倍）。**这是全站统一的节奏曲线，不是疏漏。**

1.69 倍摊到四段，每段约 10.7%，仍在 5% 可辨阈值之上；标 `*` 是提醒「该考虑换轴了」，不是判错。这两门要不要再补一根复杂度轴，见 `08-待拍板清单.md` D11 与 D16。

真正「等于没变」的是 1.15× 那一段（摊到四段每段 3.6%，顺光扫斩改版前就是这样），现在已换轴到 2.78×。灵纹连线改版前那根 1.50× `kinds`（4→5→6→6→6，整数段位天生压不上去）也已换到 `turns`（2→1 折）与盘面 4×6→10×7。

时间轴压不上去是物理限制，不是设计懒：

| 轴 | 现在的未入门段 | 再压 2 倍会怎样 |
| --- | --- | --- |
| 时限 | 15 秒 | 7.5 秒——连盘都看不完 |
| 间隔 | 1180ms | 590ms——来不及读 |
| 停留 | 826ms | 413ms——只能靠猜 |

**所以时间轴的结论是「够用了，别再往下拧」**，不是「再加把劲」。

真正该动手的是把承重轴换到复杂度 / 信息 / 规模上，这三根轴的物理上限高得多：

| 轴 | 15 门里已用 | 上限 | 为什么高 |
| --- | --- | --- | --- |
| 复杂度 | 5 门 | 6–8 倍 | 加规则不占屏幕、不逼手速 |
| 信息 | 5 门 | 5–6 倍 | 挖洞、缩短观察窗，纯认知 |
| 规模 | 3 门 | 4 倍 | 受屏幕尺寸限制（每格 ≥25px） |
| 速度 | 5 门 | 3–4 倍 | 生理上限（反应 200ms） |

### 四门换轴的对照

这一轮把「看起来没问题、实际压不出量」的四门从时间轴挪到了规模 / 复杂度轴：

| 门 | 改前主轴 | 改后主轴 | 时间轴怎么变 |
| --- | --- | --- | --- |
| 顺光扫斩 | 速度 2.86×（343→120ms） | **盘面 2.78×**（3×3→5×5）+ 刀路 2.67×（3→8 桩） | 2.86 → **2.17×** |
| 数格辨禁 | 禁制 1.60×（5→8） | **盘面 4×**（6×6→12×12，手机上限）+ 禁制 4.80×（5→24）+ 推理 0/0/1/2/3 + 后两段零容错留两难 | 时间线跟着格数**放宽**（25→100 秒） |
| 步法连环 | 段数 1.67×（且两对段位重复） | **段数 + 键位重排**（12→39 步，困难起每段重排） | 时间**放宽**（20→23 秒） |
| 灵纹连线 | 时辰 1.15×（55→48 秒）+ `flashMs` 1.69×（只是帮助变短） | **盘面 4×6→7×6→10×7（12→21→35 对）+ 纹种 4→6 + 折数 2→1（大成起）**；时辰改按「每对预算 × 本段对数」沿 1000 关连续收，每对预算段内走自己一条直线（5.50→2.30 息，段末接下一段段首） | 换段时总时辰随盘变大而**变长**（第 500 关 59 息 → 第 501 关 98 息），但每对只减不增；大成起折数从 2 收到 1，实测每对可连量掉约四成，是盘面没变也让搜索变难的复杂度轴；**布纹偏斜已退役**（它把可连对数从 14.3 抬到 20.0，方向反了），段内只剩两根轴：纹样每 5 关一套（外观）、每对预算逐关收紧（硬度）；`flashMs` 退役为恒定 `hintMs` |

四门的共同点：**没有一门把「后段 = 把秒表调小」当主承重轴。** 多出来的难度全落在「要想的东西变多」上——刀路更长要记路、盘更大推理链更长、键位重排必须读符号、纹种变多让同纹候选变少。灵纹连线甚至把总时辰放长了：盘变大本就该多给息，真正紧的尺子是「一对平均给几息」；它在本轮又补上折数轴（大成起 2→1 折），让盘变大之外的那一段真有玩家察觉得到的台阶——光靠整段一条直线的每对预算（名义 5.50 收到 2.75），逐关差被 `floor` 吞掉，相邻关中位差是 0，玩家只会觉得「盘大了、时间也长了」——现在改成**每段自己一条直线、段末接下一段段首**，段内收缩 8%–23%，逐关差才真的落到盘上。

这也是往下走的模板：**先问这门该练什么，再看哪个轴能体现它**，而不是「后段就把数字调小一点」。

- **`flashMs` / `gapMs` / `shuffleMs` 带 .8 / .6 这类尾数**：它们是 `倍数 × pace × 1000` 取整到三位的结果，比如成对翻牌 850 × 1.18 = 1003，记序复现 560 × 1.18 = 660.8。准备页显示时会折成「1.00 秒」这种，不显示毫秒原值。灵纹连线已把「照纹亮多久」从 `flashMs` 改成恒定的 `hintMs`（900ms）：它不进 `PACE_KEYS`，也不进 `LEVEL_TIME_KEYS`，所以既不按段缩放，也不会在 1000 关里报出「亮起时长 0.75 → 0.74 秒」这种参数动了、盘面没动的假变化。
- **九宫填数的 `timeLimit` 在难 / 极 / 绝三段都是 420 秒**：因为它是整表覆盖，表里就写死 420；这三段的收紧靠 `holes`（32 → 40 → 46）与三条评级线（`tS` 170 → 190 → 210）承担，不靠时钟。
- **`startLen` / `decoys` / `kinds` 这类整数在相邻段重复**：它们过了 `goal` 倍率后被 `Math.round` 折叠，比如 `decoys` 2 × 1.32 = 2.64 → 3，所以只有圆满段真的多出一个。这是刻意的——整数参数天然只有几个台阶，硬要每段都变只会让未入门段变成 1。
- **灵纹连线的 `duration` 换段时变长（第 200 关 44 息 → 第 201 关 77 息）**：换段时盘从 4×6 变 7×6（12→21 对），总时辰按「每对预算 × 对数」现算，本就该多给息。真正只减不增的是**每对时辰** 5.50 → 5.00 → 4.50 → 3.70 → 2.85（段首值；段内继续收到 5.00 / 4.50 / 3.70 / 2.85 / 2.30）。换段时还对取整粒度加了闸：12 对的粒度是 1/12 ≈ 0.083 息、21 对是 1/21 ≈ 0.048、35 对是 1/35 ≈ 0.029 息，名义预算明明在降，实际每对却会因少扣零头看起来松一点；`linkDurationAt` 拿上一段末关的**实际**每对封顶，把这道假回弹堵在生成端，`levelDelta` 也只报每对时辰，不报变长的总时辰。旧版把时辰交给「章内收三成、换章复位」，反倒让第 40 关（39 息）比第 41 关（53 息）还紧，界面自己写出「时辰 39 → 53 秒」；现在 `buildParamsAt` 对这一门跳过通用那一刀，末尾统一用 `linkDurationAt(关号)` 收口。
- **节律判定没有「反向的一对」了**：旧版难度是 `window ÷ speed`（判定带从 ±325ms 收到 ±115ms，2.8×），两列单看各 1.68×，相乘才是难度——那一版五段只动一个轴，玩家打一百多关说不出哪变了。现在难度分在三条轴上：谱型（每拍一下 / 长短交替 / 休止 / 双手 1:2 / 双手 2:3）、提示（全标 / 下一音 / 小节首拍 / 无）、速度（格长 500 → 440ms，BPM 60 → 68）。判定窗统一按「该手最短间隔的四成」封顶，五段的**相对宽度**一致（40%），绝对毫秒随谱走，所以审计不能再拿单列跨度当难度。五个谱由 `minigames/tempo.js` 的 `score()` 复算，见 `spec/玩法设计/05-吐纳周天诀/总览.md` §3 与各段文档。

## 四个特征门

### 特例一：阵灯推演——评级线只有 1 种，仍然判「过」

`lights.lines()` 返回的是**纯步数比例**：

```
S：正好最优步数 | A：多 2 步以内 | B：不超过最优的两倍 | 其余为 C
```

这四句与盘面大小、步数预算都无关，所以五段拼出来是**完全相同的字符串**，`lineVariants = 1`。它靠第 ② 条的替代出口过关：`size` 从 3 变到 5、`capSteps` 从 9 变到 22，盘面规格确实随段变了。

三条判据里它满足两条：

| 判据 | 结果 |
| --- | --- |
| ① 参数 ≥ 2 在变 | ✅ 3 个 |
| ② 评级线随段变 | ❌ 五段同一行 |
| ② 替代：盘面规格随段变 | ✅ `size` 3→5、`minSteps` 2→5、`capSteps` 9→22 |

**这是设计选择，不是漏改。** 阵灯推演是一门「按步数比例评级」的玩法：盘大好办还是盘小好办，取决于最优步数；写成「S ≤ 16 步」反而会在 3×3 盘上给出一个白送的 S 线。用比例表达，五段共用一把尺子，玩家学会的是「贴着最优走」，而不是背数字。

代价是**说明页五段会显示同一段评级文字**。这一点由准备页的 `brief` 补上：阵灯推演的 `brief` 不走通用的「时间类字段」拼装，而是单独说清 `size×size 盘 · 最优 N 步起 · 预算 M 步`（`stageDetail` 里对 `lights` 有专门分支，注释写明「按时间类字段拼 brief 只会拼出一句『入门基准』」）。

### 特例二：数格辨禁——时间线随盘面走，不是五段一张表

评级只看用时，而三条线按格数算（`gradeLine(n)` = 25 秒 × 格数 ÷ 36），所以盘面一变、线就跟着动：

| 段 | 盘面 | 格数 | 禁制 | 密度 | 心神 | S | A | B |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 未入门 | 6×6 | 36 | 5 | 14% | 3 | 25 秒 | 45 秒 | 75 秒 |
| 入门 | 6×6 | 36 | 6 | 17% | 3 | 25 秒 | 45 秒 | 75 秒 |
| 小成 | 8×8 | 64 | 12 | 19% | 2 | 44 秒 | 80 秒 | 133 秒 |
| 大成 | 10×10 | 100 | 18 | 18% | 1 | 69 秒 | 125 秒 | 208 秒 |
| 圆满 | 12×12 | 144 | 24 | 17% | 1 | 100 秒 | 180 秒 | 300 秒 |

旧版盘面恒 6×6，三条线五段一模一样（25/45/75），只有禁制数与心神在变。当时记的疑问是「玩家对照五段会看到时间线完全一样」。这条疑问现在解决了——但**不是靠收紧时间，而是靠放大盘面**：线变长了，是因为要做的事变多了。

这一门的难在推理链长度，而推理链长度由格数、密度与推法决定。36 格 8 处禁制，约束传播两三步就推到底；144 格 24 处禁制，要跑好几轮，中途还得回头补推。后段还要求两数相减 2/3 次、心神只 1 盏、推到卡住留 50/50——**同样的推理能力，在 12×12 上要做的事完全不是同一个量级。**

所以时间绝不能跟着收：12×12 若卡在 25 秒，玩家只剩「猜」。**前 3 段刻意做了无猜保证**（布完禁制用约束传播验过可解）；大成、圆满反过来留两难，但卡住前必须先逼出高阶推理——是推理之后的赌，不是不推理就赌。

密度稳在 14–19% 也是同一个道理：太高是「无处下脚」，太低是空盘。对照竞技扫雷初级 9×9/10、中级 16×16/40、高级 30×16/99，原先的 9×9/12 只是初级盘；12×12/24 是手机每格约 28px 的上限，不冒充触屏做不到的竞技高级盘。

### 特例三：顺序点格——后三段曾挤在同一个 6×6（已修）

审计第一次跑出来的表是 4/5/6/6/6：后三段同一个 36 格，段与段只差 S 线 34 / 32 / 29 秒，
其余全按 `PER_CELL` 的固定倍数现算。它过了审计（可见参数有 `size` 与 `penaltySec`，
评级线也确实五段不同），但三项静态判据都抓不到它真正的问题：

1. **段差小于方差**。同一尺寸换个随机布局，成绩本来就波动 3–5 秒（公开舒尔特参照
   自己也这么写），而这里三段只差 2 秒与 3 秒。三段在体感上是同一局。
2. **困难 34 秒宽于极难 32 秒**。原因是 `PER_CELL` 乘以格子数、而格子数在小成段跳到
   36 后不再变；玩家横向对比会觉得「降段反而更难拿 S」。这不是标定失误，
   是「同一盘面只收秒表」的必然结果——只要两段同盘面，就一定出现这种反向。
3. **一个旋钮，四条线**。`A = 1.45S`、`B = 2.1S`、`时辰 = 1.35B`，改 `PER_CELL`
   等于同时改四个数，五段实际只有一维。

修法不是压 `PER_CELL[2]`（那只把反向差挪到别处），而是**让每段换点东西**：
4 / 5 / 6 / 6 / 7，中间那一对同盘面的段改用规则分开——极难起点过的格不再退场。

| 段 | 盘面 | 点过的格 | 罚时 | S | A | B | 时辰 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 未入门 | 4×4 | 退场 | 2 秒 | 16 秒 | 22 秒 | 28 秒 | 38 秒 |
| 入门 | 5×5 | 退场 | 3 秒 | 24 秒 | 33 秒 | 40 秒 | 54 秒 |
| 小成 | 6×6 | 退场 | 4 秒 | 33 秒 | 44 秒 | 56 秒 | 74 秒 |
| 大成 | 6×6 | **不退场** | 5 秒 | 32 秒 | 43 秒 | 56 秒 | 72 秒 |
| 圆满 | 7×7 | **不退场** | 6 秒 | 43 秒 | 56 秒 | 73 秒 | 95 秒 |

同盘面的困难 → 极难现在只看两件事：S 线紧 1 秒、时辰短 2 秒——都不是难点；
难点全在「盘面不退场」上。这三段的秒表差故意留得很小，因为**同盘面的两段
靠秒表分不开**（方差大于段差），分得开的只有规则。

审计仍然判不出「段差够不够大」——它只数「变了几个参数」。这条得靠
`tests/rank.test.js` 的「同盘面必须差一条规则」与 `verify` 8b-7 的「每格预算
必须递减」两条专门断言兜。

### 特例四：滑格相合——只有 2 个参数、4 种评级线

`target` 128 / 256 / 256 / 512 / 1024 与 `startTiles` 2 / 2 / 3 / 3 / 4。评级线 4 种而不是 5 种，因为困难与普通共用 `target = 256`，评级文字相同。

这一门刚过判据下限（2 个参数）。它的难度其实主要来自「起手块数」——从 2 块起手（每步只有 2 个方向有意义）到 4 块起手（棋盘几乎满，可走的方向极少），这个变化比 `target` 更明显，但只有 4 个台阶。若以后要加码，优先加第三个参数（例如棋盘边长或新块生成概率），不要动 `target`——`target` 一抬，单局时长就跟着涨。

## 四门「补第二个参数」的补丁

`buildParams` 末尾有这么一段注释与四行注入：

```js
// 四门原本只有一个可见参数在变：把第二个数按段注入，玩法层逐个读走（见上方表注释）。
if (method && method.game === 'mines') out.hearts = MINES_HEARTS[d.depth];
if (method && method.game === 'merge') out.startTiles = MERGE_START_TILES[d.depth];
// 顺序点格后来又补了第三个：点过的格退不退场（极难起不退，盘面始终是满的）。
if (method && method.game === 'schulte') {
  out.size = SCHULTE_SIZES[d.depth];
  out.fade = SCHULTE_FADE[d.depth];
  out.penaltySec = SCHULTE_PENALTIES[d.depth];
}
if (method && method.game === 'pushbox') out.capFactor = PUSHBOX_CAP_FACTORS[d.depth];
```

这四门是审计第一次跑出来时的「欠」段门。当时的状况：

| 功法 | 原本只有 | 补上的第二个参数 | 补后可见参数 |
| --- | --- | --- | --- |
| 数格辨禁 | `mines`（5→8） | `hearts` 3/3/2/1/1（后补 `deduce` 0/0/1/2/3 与 `allowGuess` 关/关/关/开/开 当段差主轴） | 3 |
| 滑格相合 | `target` | `startTiles` 2/2/3/3/4 | 2 |
| 顺序点格 | `size` | `penaltySec` 2/3/4/5/6（后又补 `fade` 与 7×7） | 3 |
| 推石入位 | `level` | `capFactor` 2.2→1.6 | 2 |

四条补丁的选型原则一致：**补的那个参数必须改变「容错」「起手条件」或「看得见的盘面」，不许只是让同样的操作变慢。** 心神减一、起手块加一、罚时加一秒、预算系数收紧、点过的格不再退场，都是玩家一进局就感受得到的；如果当初补的是「时长 ×0.9」，审计会过，但玩家感受不到。

这几张表与模块内的兜底值必须同源（`tests/rank.test.js` 逐门复算），改一处要改两处。

## 为什么审计不进 `npm run check`

`check` 的四步（`verify` → `test` → `sim` → `lint`）都必须是**确定性断言**：给定代码，输出恒定，红就是错。审计不是。

- **它判的是设计口径，不是代码正确性。** 「3 个参数在变」是对的，「2 个参数在变」也是合法的（滑格相合就是 2），差别在设计意图。把它挂进 `check`，会让「我就想只改一个参数」变成一次构建失败，逼着人先去改审计。
- **阈值是经验值，且会随玩法增加而调整。** 判据 ① 的 `>= 2` 是下限而非目标；以后一门新功法若天然只有 2 个可用参数，改判据是正常维护，不该牵连提交。
- **它回答的是「有没有变」，静态断言已经回答了「机制是否自洽」。** 两者的失败处理方式不同：前者要人判断，后者要人修代码。

`tests/rank.test.js` 里保留了一份**轻量复算**（内部段位键名单 `INTERNAL_PARAM_KEYS` 与审计脚本同一份真源），用来守住「哪些键算内部键」这个口径本身不被随手改掉；具体某门有几参数在变，仍交给 `audit:diff` 人工看。

跑法：

```bash
npm run audit:diff
```

输出后要人工确认三件事：① 有没有 `★ 欠`；② 新增功法的「会变的字段」是否真的是玩家看得见的；③ 评级线的种数是否符合预期（比例评级类如阵灯会是 1 种，这是对的）。
