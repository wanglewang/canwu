# 组件：四个自造件与八个通用类

> 真正做成 Component 的只有四个：道相、术语、对决结算卡、邮箱登录面板。其余「组件」都是 wxss 里的一组通用类——因为小程序的自定义组件有跨样式隔离的坑，泛化到纯排版层会付出比收益更大的代价。

## 核心前提：什么才配做成一个组件

我先想清楚「组件」在这里的成本：小程序里做成 Component，要处理样式隔离、跨页通信，每多一层还多一次 `setData`。这些代价换来的是什么，决定了它值不值得做。

所以我的门槛只有两条：**带自己状态**，或者**两页必须共用同一份**。道相有编号与配色状态，结算卡两页长得一模一样，邮箱面板有自己的发码倒计时——它们配。而 `.imm-row` 只是一组 flex 规则，做成组件除了多一层开销，什么也没多给。

这条门槛也解释了我为什么否掉「原子组件库」：把 Btn / Card / Tag 全做成 Component 听起来很规范，但每层都是一次 `setData` 成本，而全站通用类在小程序里反而更好用。

## 1. 概述

**只有「带逻辑」或「两页必须共用」的东西才做成 Component；纯排版一律用全局类。**

## 2. 目标与非目标

**目标**

- 同一块 UI 在两页出现时，只有一份实现（`duel-result`）；
- 有自己状态、自己的事件、自己的计算的东西，才独立成件；
- 组件内部能直接用全站通用类（`.modal` / `.imm-btn`），不重复写样式。

**非目标**

- 不做设计系统式的「几十个原子组件」；
- 不给纯排版块做组件（`.imm-row` 只是一组 flex 规则）。

## 3. 四个 Component

先记住这张「地图」，后面所有细节都挂在下面四个格子里。它们与第 4 节那八个通用类之间的分界，正是前面说的那条门槛：

```text
        做成 Component 的四个
   ┌────────┬────────┬────────┬──────────┐
   │ portrait│  term  │duel-   │login-    │
   │  道相   │ 术语   │result  │panel     │
   │  有状态 │ 两页用 │结算卡  │发码状态机│
   └────────┴────────┴────────┴──────────┘
   判据：带自己状态 或 两页必须共用同一份
```
*（设计示意，非实测截图；方框代表「独立成件」，不代表视觉样式。）*

### 3.1 `portrait` —— 道相（纯 CSS 绘制的角色形象）

| 项 | 内容 |
| --- | --- |
| 属性 | `variant`（0–5，编号取模）/ `realm`（0–3，决定光环层数）/ `size`（normal / small） |
| 数据来源 | 存档的 `portrait` 与 `realmIndex`，随云端同步 |
| 画法 | 九个 view：法器 / 双袖 / 袍身 / 领 / 头 / 髻 / 簪 / 底盘 / 印章 |
| 配色 | `PALETTES` 六组：山 / 水 / 火 / 木 / 雷 / 风，各给 `robe / trim / aura / disc / skin / hair / seal` |
| 光环 | `realm + 1` 层同心圆，`scale = 1 + k×0.13`、`opacity = 0.85 − k×0.19` |

**为什么用 CSS 而不用图片**：

1. 不用任何图片资源，包体零增量；
2. 不需要用户授权（`chooseAvatar` 要过内容安全检测、要配 `downloadFile` 域名、云存储还要签名 URL——三份成本换一个小圆头像）；
3. 换一尊道相只是换编号与配色，不需要发新图。

**存档里没有 `avatar` 字段**，`verify` 1b 守着这条：不许再出现 `open-type="chooseAvatar"`。

### 3.2 `term` —— 术语解释

| 项 | 内容 |
| --- | --- |
| 属性 | `termKey` / `label` |
| 行为 | 渲染成「文字 + ?」的小胶囊，点开 `wx.showModal` 给一句大白话 |
| 数据来源 | `data/copy.js` 的 `TERMS`，与指南「名词速查」同一份 |

黑话第一次出现在页面上时给一个「?」入口，解释不写在页面里。`verify` 会扫所有 wxml 里的 `<term term-key="...">`，**引用不存在的术语直接报错**。

### 3.3 `duel-result` —— 对决结算卡

| 项 | 内容 |
| --- | --- |
| 属性 | `show` / `result` |
| 数据来源 | `engine.battle` / `engine.battleMirror` 的原样返回 |
| 关键配置 | `options: { styleIsolation: 'apply-shared' }` |

这是全站唯一必须 `apply-shared` 的组件：它内部用了 `.modal` / `.modal__title` / `.imm-btn` / `.res-line` / `.tag` 这些**全局类**。不共享全局样式的话，弹层会掉成一列没有底色的字。

**为什么抽成组件**：仙门切磋与秘境探索要显示的东西完全一样（我方挥出 / 对方接下、触发特效、资源两行、新称号）。抄成两份的话，下次调结算必然出现「切磋改了、秘境没改」。

组件只负责摆，不碰存档——谁打的、扣了什么，都由 `utils/game.js` 在调用前算完。

七行内容：

| 行 | 说明 |
| --- | --- |
| 标题 | `胜 · 名字` / `首胜 · 名字` / `首过 · 名字` / `惜败 · 名字` |
| 副标题 | 称号 + 「双方各有 ±15% 波动」 |
| 比数 | 我方挥出 / 对方接下，两个大数字 |
| 一句 | `r.line`（风味的判定句） |
| 特效 | 「触发特效」+ 每条一行 |
| 资源 | 灵力 −N、灵石 +N（今日第 n 场 ×0.85）、新功法 |
| 新称号 | 「新称号」+ 胶囊 |

**「首胜」与「首过」分开**：秘境不是「对手」是「地方」，第一次赢下来叫首过，说首胜会跟切磋混成同一件事。

### 3.4 `login-panel` —— 邮箱验证码登录

| 项 | 内容 |
| --- | --- |
| 事件 | `bind:signedin` |
| 位置 | 登录页「使用邮箱验证码登录」展开后才渲染 |

独立成件而不是写在登录页里：它是登录页唯一一段「有独立状态机」的东西（发码 / 倒计时 / 校验 / 错误）。

## 4. 八个通用类（不是组件）

| 类 | 用途 | 关键规则 |
| --- | --- | --- |
| `.imm-panel` | 面板 | 1rpx 描边 + 顶部 240rpx 微亮渐变 + `--r-lg` + 24rpx 内距 |
| `.imm-list` + `.imm-row` | **成组列表** | 一个外框，行间只用发丝线（`--c-imm-line-soft`）；不做一叠各带边框的小盒 |
| `.imm-grid` + `.imm-tile` | 宫格 | 一整块 3×2 细线格；`nth-child(3n)` 收右边框、`nth-last-child(-n+3)` 收下边框 |
| `.imm-attrs` + `.imm-attr` | 属性格 | 2×2 细线格，与宫格同一套语言；第三行写「这一项管什么」 |
| `.help-sec` | 折叠分节 | 说明 / 日志 / 人物页的成就·背包·设置·诸界共用；头 88rpx 高，`+ / −` 切换 |
| `.state` | 状态占位 | 加载 / 空 / 错误三种，`◇` 字形 + 标题 + 说明，绝不让页面白屏 |
| `.modal` + `.mask` | 弹层 | 遮罩 90 层、弹层 100 层；`max-height: 82vh` 自滚 |
| `.sticky-bar` | 吸底条 | 40 层，带 `env(safe-area-inset-bottom)`；`--tools` 变体靠右不铺满 |

### 4.1 为什么 `.imm-row` 不加边框

「一叠各带边框的小盒」会让页面变成一列卡片堆；「一块外框 + 发丝分隔」读起来是一张表。**信息密度一样，视觉噪音少一半**。

代价：行内必须自己撑住多行信息的间距（`.riv-head` / `.riv-meta` / `.riv-drop` / `.riv-note` 这一组就是为此而生）。

### 4.2 `.imm-grid` 的边框数学

3 列 × 2 行排满时：

```css
.imm-tile:nth-child(3n)         { border-right: 0; }
.imm-tile:nth-last-child(-n+3)  { border-bottom: 0; }
```

**不能按「末两格」写**——按末两格会让第二行的第一格留一条悬空下边框。

## 5. 组件为什么不共享盘面样式

`minigames/` 下一行都不许引用 `data/visual.js`，同理，盘面样式（`styles/scene.wxss`）也不做成组件：

- 盘面要的是「按玩法主题注入的 CSS 变量」，而不是结构复用；
- 每个玩法的格子结构都不同（方格 / 河道 / 圆盘 / 灯环 / 卷轴 / 滑块绝对定位）。

**组件解决的是结构重复，盘面解决的是结构差异。**

## 6. 被否决的方案

| 方案 | 为什么否掉 |
| --- | --- |
| 「原子组件库」（Btn / Card / Tag 都做成 Component） | 小程序组件有样式隔离，全站通用类反而更好用；且每层组件都是一次 setData 成本 |
| 道相改用 `chooseAvatar` + 云存储 | 内容安全检测 + downloadFile 域名 + 签名 URL，三份成本换一个小圆头像 |
| 结算卡在切磋、秘境各写一份 | 必然一页先改 |
| `.imm-row` 每行独立成卡片 | 一列卡片堆，视觉噪音大 |
| 宫格按「末两格」收边框 | 第二行第一格会留悬空线 |

## 7. 代码指路

- `components/portrait/portrait.js` —— `PALETTES` / 光环层数 / 编号取模
- `components/term/term.js` —— 取 `copy.termOf()`，`showModal` 单按钮「知道了」
- `components/duel-result/duel-result.js` —— `toView()`（含首胜 / 首过措辞与衰减说明）
- `components/login-panel/` —— 邮箱验证码
- `styles/immortal.wxss` —— `.imm-panel` / `.imm-list` / `.imm-grid` / `.imm-attrs` / `.help-sec` / `.riv-*`
- `app.wxss` —— `.state` / `.modal` / `.sticky-bar` / `.tag` / `.bar`
- `tests/layout.test.js` —— 宫格边框、组件 `apply-shared`、`pressable` 覆盖数

## 8. 待验

- `duel-result` 的 `apply-shared` 一旦被误删，整张结算卡会「掉成没有底色的字」——这个症状与 `.pg--imm` 漏挂一样隐蔽，建议在 verify 里补一条断言（当前靠注释提醒）。
- 道相六组配色在深色背景下，浅色系（水 / 木）的袍身与 `--c-imm-bg` 对比度是否足够。
- `term` 用 `wx.showModal` 而不是自有弹层：好处是无样式成本，坏处是不能放长文、不能带链接。若术语解释再长一段，需要换成 `.modal`。
- `.imm-grid` 现在是 6 格（3×2）；若入口减少到 5 格，`nth-child(3n)` 会让右侧留一道悬空竖线——代码注释里已经记着这件事，但**没有断言守着**。
