# 需求（Spec）· S · 《参悟》设计真源

> SDD 四层中 spec 层的总目录。spec 承载**所有 what（承诺什么、设计成什么样）**：六份行为契约 + 系统设计、玩法、界面、数值的设计文档。
> 技术实现（how）在 `plan/`，范围与不变量在 `constitution/`，落地映射到 `tasks/`。四层职责见 `docs/specs/README.md`。
>
> 一句话：这份总入口不是目录索引，是张地图——这里写的都是「为什么」，而「为什么」，得从那个两站地铁的早晨开始看。

第一次打开这个目录，满屏的文档名会一起压过来。别慌：你不需要读完它们。先按下面的「三条阅读路径」找到自己带着的那个问题，再顺着箭头走——走到哪算哪，比从头翻到尾有用。

这里是《参悟》的**设计真源**，不是使用说明。项目根目录的 `README.md` 面向「怎么跑起来、改哪里」，本目录面向「为什么这样做、改动的边界在哪」。

两条阅读规则：

1. **文档与代码冲突时，代码是事实，文档是欠账。** 发现不一致，先修代码或先修文档，不许放着两套口径。每篇末尾都有「代码指路」，就是为了一眼核对。
2. **能被断言守住的设计才写进来。** 凡是可以量化的（数值、阈值、文案、页面结构、玩法接口），这里写了就应当能在 `npm run check` 里找到对应断言。找不到的，标注为「待验」而不是默认成立。

## 三条阅读路径

满屏文档不按目录顺序推荐，按「你带着什么问题来」分了三条路。先认自己的问题，再上路：

```text
   你带着什么问题来？
        │
   ┌────┼─────────┬──────────┐
   │    │         │          │
 第一次来  加新功法  要改数值
   │    │         │          │
  读五篇  走六步    走五步
   │    │         │          │
   └─→ 懂全貌   └─→ 玩法定稿 └─→ 数值重算
      「是什么」   「怎么守」   「全站一致」
```

**第一次接触这个项目** → `docs/specs/constitution/01-产品定位与体验目标` → `docs/specs/constitution/02-十三条设计原则` → `系统设计/01` → `系统设计/04` → `玩法设计/README.md`。读完这五篇，能回答「这是什么游戏、钱怎么转、练功在练什么、十五门有什么不一样」。**为什么从 `01` 起**：它先把「一个早晨的单局」讲清楚，后面每一条设计都能追回那个场景。

**要加一门新功法** → `系统设计/11`（分类与命名）→ `系统设计/12`（特效）→ `玩法设计/README.md`（判重）→ `00-契约/checklist-puzzle.md`（十二维自检）→ `docs/specs/plan/02`（接口契约）→ `docs/specs/tasks/03-校验链`（校验链）。顺序不能反：先想清玩什么，再想清楚怎么被断言守住。**为什么判重夹在中间**：先命名、再确认跟已有玩法不撞，才轮到写接口；反过来的话，契约写完才发现是换皮，就白写了。

**要改数值** → `数值平衡/02`（总表）→ `数值平衡/01`（节奏）→ `系统设计/03`（收支）→ `npm run sim` → `数值平衡/03`（区分度）。改完必须重跑 `npm run check`，因为多处断言按公式复算，不是按固定值比对。**为什么先读总表**：改数值最怕改一个点、塌一整条曲线；先看总表知道这个数牵着谁，再看节奏和收支，最后才动手跑 sim。

## 每篇文档的固定结构

系统篇按这副骨架写。玩法篇的章节名由各门自己定——同一门五段共用一套，跨门不重样；固定的是「回答什么」，不是「叫什么」：

| 段落 | 回答什么 |
| --- | --- |
| 概述 | 这个系统是什么，一句话说得完 |
| 目标与非目标 | 它要解决什么、明确不负责什么 |
| 机制 | 完整的规则与判定顺序，含边界情况 |
| 参数 | 真实数值表，注明出处常量 |
| 依据 | 为什么这样定：理论依据 + 工程依据 + 被否决的方案 |
| 代码指路 | 文件与函数，便于核对 |
| 待验 | 还没有证据的部分 |

「被否决的方案」这一段是本目录最值钱的部分。只写「现在是什么」，下一个人会把已经踩过的坑再踩一遍；写了「为什么不是另一种」，才算把决策留下来了。**我刻意把它单列成一段**，不塞进「依据」里——塞进去，它会读起来像一条脚注；单列出来，它才像一个当时真的摆在桌上的选择。

## 与其他文档的关系

三处各管一段：本目录讲「为什么」，代码讲「具体写成什么字」，工程手册讲「怎么跑」。分清楚归属，才不会改了一头、漏了另一头。

| 文档 | 定位 | 与这里的分工 |
| --- | --- | --- |
| 根 `README.md` | 工程手册 | 怎么装、怎么跑、改哪里；本目录解释为什么 |
| `docs/specs/spec/00-契约/checklist-puzzle.md` | 交付门槛 | 新玩法的自检清单；本目录的玩法篇是「已交付的样子」 |
| `data/copy.js` | 玩家文案真源 | 本目录 `docs/specs/constitution/04-文案口吻规范` 只讲规范，具体字句以代码为准 |
| `data/help.js` | 解释性长文真源 | 本目录讲「该说什么」，实际字句在代码 |
| `scripts/verify.js` | 静态校验 | 本目录提出的硬约束，多数在这里被断言 |

## 维护约定

这四条不是格式洁癖，是踩过之后留下的规矩：文档一旦和代码分家，它就从「真源」退化成「传说」。

- **改机制必须同步文档**，且同一批提交里完成。历史上有过「代码改了、README 没改」导致难度门槛表与代码差一段的情况，那张表现在已经修过一次。
- **文档里出现的数字必须是可复算的**，写 `7 / 11 / 17 / 24 / 32` 而不是「七到三十二」；写「炼气 174」而不是「一百七十多」。
- **不写旧名。** 系统改名后，旧称一律不留在文档里（校验脚本会扫全项目的 `.md`），需要讲沿革时用「旧版」「原属性名」指代，不写出旧字面。
- **篇幅服从信息密度。** 能一句话说清的不铺成三段；但「被否决的方案」与「边界情况」不许省。
