# 仙门切磋

> 切磋是「赚灵石」的唯一稳定来源，也是唯一有「对手」这个概念的玩法。它不生产熟练度，但消耗同一池灵力——所以「今天练功还是挣钱」这个决策，落点就在这一页。
>
> 同时它是**功法唯一真正出场的地方**：三式运出去，战力当面变。

**核心前提：全局只有一处真正的资源决策——练功还是挣钱——而这一页就是「挣钱」那一端。** 我刻意让它有分量：对手会说话，功法会出场，赢法不止一种。所以切磋不是按个按钮就领钱，它要你先做两个决定——带哪三式、打哪个人。这两个决定都不重，但它们让「挣钱」这件事看起来像在修仙，而不是在点一台老虎机。

---

## 1. 概述

选一位对手（或粘贴战友力码），**从已入门的功法里挑三式运出去**，先运功扣 2–5 点灵力，双方各摇一次战力，赢则按当日第 n 场衰减给灵石，首胜另有 8 枚与功法掉落。

> 战力的算法写在 `10-power.md`，这里我只讲站在这一页时，你眼前会依次发生什么。

## 2. 页面结构

```
┌ 境界 · 灵力 96 / 174 ────────────────┐
│ 仙门切磋                              │
│ 本场运功：三格印（开 / 护 / 敛）        │
│   本场挥出 181 · 运功 4 灵力            │
│   「改换」展开候选池                    │
│ 一张列表：7 位对手                     │
│   名 / 头衔 / 战力 / 胜后得多少灵石     │
│   首胜标记（已胜过的显示「已胜」）      │
│ 战力码：输入框 + 「应战」              │
│ 仙榜推荐：「挑一位最接近的道友」        │
└──────────────────────────────────────┘
```

**运功面板在对手列表之上**，因为它是整页的前置决定（所有对手共用同一套三式），不是某一场的附加选项。首屏显示灵力余量，理由同以前：每场都要运功，玩家要一眼看出「还能打几场」。

## 3. 一场切磋的完整流程

1. **定三式**（开局前，页面上一次性决定）→ `engine.moveBoard(state, ids)`；
2. **点一位对手** → `battle(state, id, moveIds)`；
3. **算运功成本**：`qiCost = max(1, BATTLE_QI − 三式养息合计)`，封顶抵 3 点（见 §9）；
4. **检查灵力**：不足 `qiCost` 直接拒绝，提示「先回洞府打坐」，不扣任何东西；
5. **扣气**（胜负都扣，在判定之后、发奖之前）；
6. **摇点**：`powerAfter = round(power × (1 + 起手合计))`，再 `rollBattle(powerAfter, 敌方战力, 守势合计, 身法下限)`；
7. **发奖**：赢了给灵石（衰减后），首胜再加 8 与掉落；
8. **出结算卡**：胜负、**三式逐条**、`运功前 151 → 运功后 181`、双方点数、灵力 −N、灵石 +N（标明第几场 ×系数）、掉落、对手的一句台词。

**没有战斗过程动画**。这是一个「算一下、看一眼」的动作，不是一局小游戏——它不该占用玩家 30 秒。三式在结算卡上逐条落位（只动位移，不淡入），已经是「释放」的全部表现。

## 4. 结算卡

`components/duel-result`，与秘境共用（`styleIsolation: apply-shared`，否则全局类不生效）。

打完之后玩家从上到下读到的几行，各自在替他确认什么——尤其是「赢在哪」和「扣了多少」这两件他最关心的事：

| 行 | 例 |
| --- | --- |
| 标题 | `胜` / `负` / `首胜` / `首过` |
| 本场运功 | `[开] 开山 起手 +20%` / `[护] 护灯 守势 +2.5%` / `[敛] 敛息 养息 省 1 灵力`，每式带一句门规 |
| 运功前后 | `运功前 151 → 运功后 181` |
| 点数 | `我方挥出 206` 对 `对方接下 37`（赢的一方是金色） |
| 灵力 | `−4 · 余 86 / 174` |
| 灵石 | `+12（第 1 场 ×1.000）` |
| 掉落 | `得《心法·太虚照见诀》` |
| 台词 | `赵砚收剑，盯着你的手腕看了半天，没说话。` |

**台词不是装饰**。七个对手各有 `winLine` / `loseLine`，这是这套系统里唯一的叙事投入——切磋要是只报数字，就退化成一台老虎机。

**旧的「触发特效」一行已撤**（`activeBattleEffects` 整条删除）。它原本只列「到大成」的 power / variance 功法，而这几门的加成无论如何都会生效——列不列都一样，等于一句不出场也要说的话。现在由「本场运功」取代：三式是真出场、真改变掷骰的那三个。

## 5. 灵石衰减的可见性

| 场次 | 系数 | 玄真（120）实得 |
| --- | --- | --- |
| 1 | 1.000 | 120 |
| 2 | 0.850 | 102 |
| 3 | 0.722 | 87 |
| 5 | 0.522 | 63 |
| 10 | 0.232 | 28 |
| 15 | 0.103 | 12 |

结算卡必须写明「第 n 场 ×系数」，否则玩家会以为「怎么这次给少了」是 bug。

**衰减按当日已胜场数计**：输了不消耗额度。连败已经罚了灵力（5 点/场），再罚额度就是双重惩罚。

## 6. 首胜与掉落

- 首胜：另给 **8** 枚（不在衰减内），并解锁对手的 `drop` 功法（若有）；
- 已胜过的对手显示「已胜」，但**仍可重复打**——这是灵石的主要来源；
- 掉落在首胜时判定：若该功法已习得，则只给 8 枚，不掉第二本。

现只剩一门只能靠掉落的功法：太虚照见诀（峰主·玄真首胜）。其余十四门对手首胜只给 8 枚灵石，不带掉落。

## 7. 战力码与镜像

- 「复制战力码」→ `CW1-` 开头的短码（含校验位）；
- 对方粘贴 → 还原战力 → 打一场镜像；
- 不用同时在线，也不需要服务器。

**只有战力进码**：不含灵力、灵石、功法、称号。分享一个码不会泄露进度。

保存码到剪贴板必须过 `utils/privacy.js` 的守卫——未同意隐私指引时剪贴板接口会静默失败，症状是「点了没反应」。

## 8. 仙榜联动

仙榜（`pages/board/`）显示战力前 10 的真实玩家，并自动挑一位战力最接近的供切磋。

- 来源是云数据库的战绩上传，不是实时同步；
- **榜上有人的时候，切磋页会出现「挑一位最接近的道友」**，点击直接打镜像；
- 榜为空（未登录 / 无数据）时这一行不出现。

## 9. 本场运功：功法唯一真正出场的地方

### 一句话

十五门功法各炼成一式，一场至多运三式；**选中才生效**，运出去的那几式当场改写战力、波动下限与运功消耗。

### 为什么要有这一节

在这之前，功法对切磋的全部影响是一行：

```js
rollBattle(power, c.power, effectValue(state, 'variance'), shenFloorBonus(state))
```

`effectValue('power')` 把所有 power 类特技加成一个百分比塞进 `power`，`effectValue('variance')` 再加成一个 floor。于是：

- **玩家看不见任何一门出场**。赢了不知道靠哪门，输了不知道差在哪；
- 十五门的加成**全自动叠加**，练满四门 power 就是 +20%，选不选都一样；
- 九门「非战斗」功法（灵力上限 / 省气 / 回复速度）在切磋里彻底隐形。

把十五门功法的名字换成「第 1 关…第 15 关」，玩法体验不变——这就是「套壳」的可复现判据。三式是让这条判据失效的第一步：**现在你得先想清楚带哪三式**。

### 机制

| 项 | 规则 |
| --- | --- |
| 出处 | `data/moves.js`：十五门各一条，含两字招式名、出手时机、一句门规 |
| 门槛 | 已习得**且**段位系数 > 0（入门即可，不必大成） |
| 上限 | `MAX_MOVES = 3`，超出截断，同一门不重复计 |
| 生效 | **只在选中时生效**；一式不运，加成为 0 |
| 集中系数 | `FOCUS = 2`：单运一式比它被动挂着更足，三式合计约等于把以前那笔全额领回来 |
| 默认 | `pickMoves()` = 起手 / 守势 / 养息三种职能各取最强一式，职能位没满再按强弱补 |
| 记忆 | 记在页面内存（`this.moveIds`），换页即回默认，**不进存档** |

三类与 `effect.type` 一一对应，不是另起一套：

| effect.type | 出手时机 | 在切磋里变成 |
| --- | --- | --- |
| `power` | 起手 | `powerAfter = round(power × (1 + Σ value×scale×2))` |
| `variance` | 守势 | 并入 `rollBattle` 的 floor（与身法下限同一出口，上限仍 0.98） |
| `qiCap` / `qiSave` / `offline` | 养息 | 抵本场运功：`Σ max(1, round(value×scale×20))`，**封顶 3 点** |

后三类原先在切磋里完全没有出口。归到「养息」之后它们才有了出场理由：这一场少烧几口气。

### 为什么养息有硬底线

`BATTLE_QI = 5`，封顶抵 3，所以 `qiCost ≥ 2`。压到 0 的话，「切磋要运功」这条取舍整条失效——赚灵石就变成白给。这条底线由 `tests/rank.test.js` 的「养息能抵灵力，但抵不穿底线」守着。

### 数值影响

改前 `effectValue('power')` 是**全额累加**（四门满额 0.20），改后至多三式（最高 0.06×2 + 0.05×2 + 0.05×2 = 0.32）。

- 只练一门 power：改前 0.06 → 改后 0.12（更强）
- 练满四门：改前 0.20 → 改后最高 0.32（更强，但要自己挑）

**没有任何玩家的出手变弱**，所以不需要存档迁移或补偿。这条是设计约束，不是巧合：换机制不许让老玩家吃亏。

### 被否决的方案

三式这个设计走过来，也踩掉过几条看起来更「省事」的路：

| 方案 | 为什么否掉 |
| --- | --- |
| 保持全额自动叠加，三式只是额外加成 | 那三式就成了第四个 buff 栏，功法仍然「没出场」，换皮测试照样通过 |
| 一门只能运一次、可运 5 式 | 五式意味着没有取舍，玩家会全带 power，守势与养息永远进不了场 |
| 三式写进存档 | 存档多一个字段，还要管迁移；而「这一场带什么」本来就该当场决定 |
| 按对手自动配三式 | 玩家失去唯一的赛前决策，等于系统替他玩 |
| 未入门也能运 | 段位系数 0，运出去是 0% —— 一个什么都不做的按钮比没有更糟 |

## 10. 被否决的方案

这些不是纸上谈兵的选项——每一条都有人真的提议过，有的还做过原型。我留着它们，是因为「为什么不那么做」往往比「为什么这么做」更解释得清这一页的边界。

| 方案 | 为什么否掉 |
| --- | --- |
| 实时 PVP | 要长连接与房间服务，成本远超收益 |
| 打一场小游戏决定胜负 | 切磋的定位是「算一下」，插一局玩法会让「练功」与「挣钱」两个循环混在一起 |
| 输也扣灵石 | 会让玩家只挑稳赢的打，切磋失去「挑战」意义 |
| 首胜走衰减 | 会让玩家不敢打首胜（怕浪费额度） |
| 灵力不足时「先欠着」 | 让「运功」这个成本失效 |
| 战力码带完整存档 | 泄露进度，且码会长到无法分享 |
| 每场都重播战斗动画 | 与「3–10 分钟一次会话」的节奏冲突 |

## 11. 界面约束

- 首屏一行「境界 · 灵力 96 / 174」——不能用 `roleName`（那是人物页的东西）；
- 对手行的灵石数要写「胜后得 N」，不是「N」——否则会被读成「入场费」；
- 结算卡的主按钮走 `--c-imm-gold`，不许写死蓝色（历史上有过 `#2a87ab`）；
- 子页之间不开「去秘境那页」的入口行——指向由「此处说明」承担，返回交给原生导航栏。

## 待验

- 「没有战斗过程」是否让玩家觉得「太随意」——目前靠台词与结算卡撑仪式感，未做真人反馈。
- 战力码在真机上的复制/粘贴链路（含隐私授权三处行为）。
- 仙榜的真实数据与「挑一位最接近的」推荐质量。
- **三式是否真的被读懂了**：玩家会不会一直用默认三式、从不点「改换」？如果真机数据显示改换率极低，说明「选中才生效」这条对玩家不可见，需要把「你现在这套是不是最优」摆到面板上（例如标一句「换守势可少失手」）。
- **`FOCUS = 2` 的手感**：它让满配玩家的出手比改前高约 20%，理论上仍是「不会因更新变弱」，但 pvp 镜像与仙榜的相对位置会整体上移，需要在真人数据里看排行榜是否被拉开。
- **养息式的吸引力**：抵 1–3 点灵力对「每天打十几场」的玩家值不值，还是所有人都会选三门 power？若后者成立，说明养息的数值还不够，或该把它的代价从「省气」换成别的（例如少一次掷骰的重来机会）。
