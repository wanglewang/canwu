# 需求（Spec）· 战力与切磋判定

> 战力是「养成的总分」，只做两件事：决定能不能破境，决定切磋谁赢。它不参与参悟——练得再好也不影响一局游戏的难度。

---

## 核心前提：战力是记分牌，不是操盘手

战力每隔一阵才露一次面：破境时它决定你够不够格，切磋时它决定谁赢。其余时间你在盘面上点灯、连线、推石，它一点都不插手——练得再好也不会让一局变简单。我想让这条边界很清楚：战力是一条并列的成长线，不是主干。你完全可以一辈子不切磋，只把它用在破境上。它唯一要补的，是把「练一门 → 战力涨多少」这段换算摊开给你看，免得十五门功法看起来像十五个互不相干的独立玩法。

## 1. 概述

**战力 = 属性加权和 ×（1 + 境界加成 + 功法特效）**；切磋时双方各在 85%–115% 之间摇一次，比大小。

```text
  练一门 ─► 属性涨 ─► 战力涨 ─┬─► 够门槛 → 破境
                              └─► 切磋：双方各摇 85%–115%
             战力不碰：熟练度 / 关卡 / 耗气
```

## 2. 战力公式

```js
base = Σ(属性值 × 权重)                    体魄 1.0 / 真元 1.2 / 悟性 0.8 / 身法 1.0
total = round( base × (1 + 境界加成 + 功法特效) )
```

| 分项 | 来源 | 开局值 |
| --- | --- | --- |
| base | 四项属性加权 | 45.4 |
| 境界加成 | `realms[].bonus`：0 / .06 / .14 / .24 | 0 |
| 功法特效 | `effectValue(state, 'power')`：刀意 6%、成岳 5%、叠元 5%、归位 4% | 0 |
| **total** | | **45** |

`powerDetail(state, realmIndex)` 可以指定「按哪个境界算」——主页用它预告「突破之后战力多少」，而不是自己再抄一遍公式。

## 3. 五条提升途径

| 途径 | 量级 | 说明 |
| --- | --- | --- |
| 练深一门 | 段位系数 ×1 → ×5 | 最直接，也是「连 S」的经济动机 |
| 多学一门 | 每条 `bonus` 全额叠加 | 新门入门即 ×1，性价比最高 |
| 突破境界 | ×1.06 / ×1.14 / ×1.24 | 乘在总数上，越到后期绝对增量越大 |
| 功法特效 | +4% ~ +6%（按段位兑现） | 入门 25% → 圆满 100% |
| 堆品阶 | 属性系数 ×1.0 / 1.3 / 1.7 / 2.2 | 地阶一门顶黄阶一门半；天阶一格 2026-11 起暂空 |

## 4. 战力增量：把这条链算给玩家看

链路本来是通的：**练一门 → 属性涨 → 战力涨 → 够门槛就破境**。但玩家看不到中间那一步：

- 功法卡写的是「体魄 +0.8」；
- 破境卡读的是「战力 170」，写「还差 2 点」；
- 两个单位对不上，**「练这门到底推不推得动筑基」只能猜**。

十五门功法于是看上去像十五个互不相干的小游戏——这正是「套壳」这个印象的来源。补的不是新机制，是这次换算本身：

```js
// utils/game/profs.js
skillPowerGain(state, id)   // 把 rec.prof 换成下一段门槛，重算属性与战力，取差
nextPowerStep(state)        // 已习得且未大圆满的门里，取「离下一段熟练度最近」的那门
```

两个函数都**只读**（构造浅拷贝，不碰存档），也不新增公式——`skillPowerGain` 就是重算一次 `computeAttributes + powerDetail`。`breakthroughInfo()` 因此多两个字段：

| 字段 | 含义 |
| --- | --- |
| `lack` | `need - power`，页面不许自己再减一遍 |
| `fastest` | `{ id, name, nextName, gain, gap }`，差战力时「今天该练哪门」 |

### 四处必须说的是同一件事

| 位置 | 写什么 |
| --- | --- |
| 功法页卡片 | `大成 12% · 再练到圆满：战力 +9` |
| 参悟结算 | `战力 45 → 49（+4）` + `距离「筑基」还差 30 战力` |
| 主页提示 | `距「筑基」还差 30 战力 · 星罗烛天诀到入门 +8` |
| 人物页破境卡 | `还差 30 点 · 最近：「星罗烛天诀」到入门（+8）` |

### 为什么取「最近」而不是「加成最大」

加成最大的往往是「大成 → 圆满」，差 18000 熟练度，那条路一年走不完。玩家要的是**今天再打几局就能动**的那一步，所以排序键是 `gap`（离下一段的熟练度差），不是 `gain`。

`gap` 相同时才比 `gain`。已大圆满的门不参与；未习得的门也不参与——「还没学」不该显示成「练了能涨」。

已到大境界顶点（元婴）时 `fastest` 为 `null`，页面据此不再说「该练哪门」这句废话。

## 5. 切磋判定

```js
const reach = varianceBonus + shenBonus;
const floor = Math.min(0.98, 0.85 + reach);
playerRoll = playerPower × (floor + Math.random() × (1.15 - floor));
enemyRoll  = enemyPower  × (0.85  + Math.random() × 0.30);
win = playerRoll >= enemyRoll;
```

### 双方不对称，这是刻意的

| | 区间 | 可被玩家影响 |
| --- | --- | --- |
| 玩家 | 85%–115%，下限可抬到 98% | 是（`variance` 特效 + 身法） |
| 对手 | 固定 85%–115% | 否 |

**玩家侧的下限可以被抬高**：`floor` 与 `variance` 特效、`shenFloorBonus` 相加。这给了「功法特效」与「身法」一个可感知的出口——不是提高期望值，而是**减少最差情况**。

语义：**身法高的人失手也失不掉多少。** 上限仍是 115%，所以堆下限不会变成「必胜」，只是把「倒霉」的空间压小。

### 战力差距换算

对手战力与玩家战力之比决定胜率。以玩家下限 85%（无加成）计算：

| 战力比（我/敌） | 大致胜率 | 说明 |
| --- | --- | --- |
| 1.35 : 1 | 接近必胜 | 敌 115% 也压不过我 85% 以下的情形不存在 |
| 1.0 : 1 | 约 50% | 同战力对摇 |
| 0.87 : 1 | 约 30% | 需要敌方差 |
| 0.75 : 1 | 约 10% | 基本靠运气 |

> 精确胜率未做成表，因为 `floor` 会随身法与特效变化。上表只给量级感。

## 6. 奖励结构

| 项 | 规则 |
| --- | --- |
| 运功 | 每场扣 5 点灵力（三式养息最多抵 3 点，实扣 2–5），**胜负都扣**，不够直接拒绝开打 |
| 灵石 | 赢了给 `round(对手奖励 × 0.85^(当日已胜场数))` |
| 首胜 | 另给 **8** 枚（不受衰减管） |
| 掉落 | 首胜且对手带 `drop` 时解锁对应功法（现只剩太虚照见诀，出自峰主·玄真） |
| 日志 | 首胜写「首胜 X，灵石 +N」；重复写「胜/负于 X，战力 A : B」 |

**衰减按「当日已胜场数」算**（`winsBefore`），所以第 1 场胜利系数是 1，第 2 场 0.85…… **输了不消耗额度**——连败不会让后面的胜场更难赚，这是宽松的，也是对的（连败已经罚了灵力）。

首胜的 8 枚**不在衰减里**：它是「打通这条路」的一次性奖励，与「重复刷」是两件事。混在一起会让玩家不敢打首胜（怕浪费额度）。

## 8. 镜像与战力码

没有实时 PVP。替代方案是**镜像**：

1. `battleCode(state)` 把战力编成 `CW1-` 开头的短码（`power.toString(36)` + 校验位）；
2. 对方粘贴后 `parseBattleCode()` 还原战力，`battleMirror()` 用这个数打一场；
3. 不用同时在线，也不需要服务器。

**校验位**（`checkCode`）防止乱改数字：改一个字符就会失败，提示「战力码不对」。

代码里**只有战力**，不含灵力、灵石、功法、称号——分享一个码不会泄露进度。

## 9. 战力不做什么

| 不做 | 原因 |
| --- | --- |
| 不影响参悟熟练度 | 熟练度只由评级与连 S 决定 |
| 不影响参悟关卡 | 关号只由走通当前关推进，不跟战力、也不跟熟练度走 |
| 不减耗气 | 减耗气的是悟性与心法 |
| 不影响秘境奖励 | 秘境奖励固定，只按当日衰减 |

这四条合起来的意思是：**战力是一个「并列的」成长线，不是「主干」**。玩家可以完全不打切磋，把战力只用在破境上。

## 10. 被否决的方案

战力最容易越界——走着走着就想让它去管参悟、去决定胜负。下面每一条都是这类诱惑的现场，否掉是因为试过之后才知道它会把系统拉歪。

| 方案 | 为什么否掉 |
| --- | --- |
| 实时 PVP | 要长连接 + 房间服务，成本远超收益 |
| 战力直接决定胜负（无波动） | 切磋变成查表，没有「打一场」的感觉 |
| 双方都能抬下限 | 身法的价值被对手抵消，堆身法无意义 |
| 战力也影响参悟 | 会变成「先堆战力再练功」的单一路径 |
| 首胜走衰减 | 见第 5 节 |
| 输也扣灵石 | 会让玩家在打不过时不敢试，切磋变成只挑稳赢的 |
| 战力码带完整存档 | 泄露进度，且码会长到没法分享 |

## 11. 数值推导

**为什么波动是 ±15%**：小于 10% 时「战力高 10% 就必胜」，波动形同虚设；大于 20% 时「战力高 30% 也可能输」，玩家会觉得数值没用。15% 下，战力差 30% 基本锁定胜负，差 10% 仍有悬念。

**为什么玩家下限是 85% 而不是 100%**：如果玩家最差也打满，那「摇一次」就没有意义了。85% 让「倒霉」真实存在，才让身法与 `variance` 特效有价值。

**为什么下限封顶 98%**：留 2% 的「意外」空间。100% 会让切磋在后期变成纯查表。

**为什么运功 5 点**：约等于未入门段一局。打十场切磋 = 少练五局——这条让「赚灵石」与「练功」真正争同一池灵力。养息式能把它抵到 2 点，但抵不到 0：见 `15-battle.md` §9。

## 待验

- 「战力比 → 胜率」的精确曲线未做成表，因为 `floor` 随身法与特效变化。若要做平衡调整，需要先写一个蒙特卡洛脚本。
- 仙榜（云函数）的真实数据未验证：榜上是「上传战绩 + 镜像对战」，不是实时同步。
- 战力码分享后的落地体验（对方粘贴 → 打一场）未在真机验证。
