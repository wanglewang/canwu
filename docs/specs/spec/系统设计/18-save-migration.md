# 需求（Spec）· 存档结构、导入导出与版本迁移

> 存档是这个项目里唯一「改坏了就救不回来」的东西。所以它有三层防线：**版本迁移**、**规范化**、**导入即规范化**。

**核心前提：能算出来的都不存——这是我写这篇文档时反复用来做决定的那把尺。** 每多存一个字段，就多一处要迁移、多一条一致性要守。所以战力、气海上限、属性、成就进度全部现算。这把尺也解释了下面为什么大多数迁移都在「换算形状」而不是「换算语义」：形状可以无损地搬，语义一换就会凭空造数。

---

## 1. 概述

存档是一个 `version: 9` 的普通对象，存在本机 `wx.storage` 里；可以导出成 `CANWU1:{...}` 的文本码，导入时强制走一遍迁移与规范化。

把三道防线画出来，你会看到它们其实是同一件事的三个入口（这张图是设计意图，不是截图）：

```text
┌─ 存档的三道防线 ──────────────────────────────────────┐
│                                                       │
│  老档 ──→ migrateState() ──→ 升到 version: 9           │
│           │ 版本迁移                                   │
│           ▼                                           │
│  任意入口 ──→ normalizeState() ──→ 合法存档             │
│           │ 补默认 / 滤非法 / 夹区间 / 夹平灵力          │
│           ▼                                           │
│  存档码 ──→ import：解析后也走 normalize                │
│                                                       │
│  「能算出来的都不存」→ 迁移的担子才压得住                │
└───────────────────────────────────────────────────────┘
```

## 2. 存档结构

一个存档里装了什么、每一格有多大——它是后面所有迁移与规范化的对象清单：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `version` | number | 存档版本（当前 9） |
| `worldId` | string | 世界（当前只有 `xian`） |
| `roleName` | string | 道号（≤12 字） |
| `portrait` | number | 道相编号 0–5 |
| `realmIndex` | number | 境界下标 0–3 |
| `skills` | object | 每门功法 `{ unlocked, cleared, onboarded, teachSeen, lastAt }`；`cleared` 是本门已走通的关数（0–1000），**它也是这门功法的「级」**；`teachSeen` 是五段引导各看过没有，`onboarded` 保留为「首段看过」的旧别名 |
| `resources` | object | `{ qi, stone }` |
| `lastPractice` | object | `{ skillId, at }`，判「换门」与「挂机喂哪门」 |
| `buff` | object | `{ multiplier, until }`，参悟后的闭关加速 |
| `defeated` | string[] | 已首胜 / 首过的对手 id |
| `stats` | object | 计数：参悟、胜场、换门、S 次数、领份例、升段 |
| `records` | object | 每门最佳 `{ score, grade, at }` |
| `twists` | object | 每门被关掉的阶段新法名单 |
| `daily` | object | `{ date, count, claimed, battleWins }` |
| `gifts` | object | 一次性发放的记账：`{ 礼包 id: 发放时间 }`。发过的不再发，所以它是「这笔钱只能拿一次」的唯一凭据；只认当前在架的 id，老档里已下线的 id 读档时丢掉 |
| `equippedTitle` | string | 佩戴的称号 id |
| `titles` | string[] | 已解锁称号 |
| `log` | array | 环形日志（修行日志页） |
| `lastSeen` | number | 闭关结算的时间锚点 |

**不存的东西**：成就进度（实时计算）、战力（每次现算）、气海上限（每次现算）、属性（每次现算）。

这条原则的意义：**能算出来的都不存**。存的越多，迁移与一致性的负担越重。

## 3. 版本历史

每一次版本跳变改了什么，以及老档是怎么被安全搬过来的。后面的「值得记住的迁移决策」是这张表的判决理由：

| 版本 | 变更 | 迁移动作 |
| --- | --- | --- |
| v1 | 初版 | — |
| v2 | 加头像路径 | **已废弃**（道相是唯一形象，没有可补的键，不单独占版本号） |
| v3 | 各门局内最佳纪录 | `records: {}` |
| v4 | 品阶改天地玄黄、难度改由进度解锁 | 只升版本号（字段未变） |
| v5 | 每门连续 S 计数（`sStreak`） | `sStreak: {}` |
| v6 | 三连 S 晋级退役，换连 S 叠倍率（后来也删了，见 v10） | `sCombo: {}`，`delete sStreak` |
| v7 | 经济重做：参悟烧灵力、功法只收灵石、破境备灵石 | 灵力补到 `START_QI`（只补不削）、补 `daily.battleWins` |
| v8 | 难度与进度解耦：五段各 40 关、各记各的进度，走通本段开下一段 | 老档只有 `prof`，按 `legacyLevelFromProf()` 反推全书关号再拆成 `levels`：前面几档记满 40、当前档记「段内关号 − 1」、之后各段留 0 |
| **v9** | 关卡收成一条 1–1000 的线、分五段；没有段位可选，段位只由已走通关数决定 | `levels` 五个数相加得老制的「已走通关数」（0–200），再 ×5 落成 0–1000；更老的档没有 `levels`，先按 `legacyLevelFromProf(prof) − 1` 反推再 ×5。最后 `delete levels` |
| **v10** | 熟练度整条线删除：功法的「级」只由 `cleared` 决定，`TIERS` 六档门槛 = 段界关 | `delete rec.prof`、`delete next.sCombo`。**纯摘字段，不重算**：`cleared` 在 v9 就已经是对的，老档的 `prof` 不再参与任何计算 |

### 值得记住的迁移决策

1. **v5 → v6 不换算旧计数**：`sStreak`（三连 S 的连数）与 `sCombo`（连 S 层数）语义不同，硬换算会给出一个凭空的层数。一律从 0 重数。（这两个字段到 v10 都摘掉了，但这条判断本身仍然成立——**语义不同的两个数不许硬换算**。）
2. **v6 → v7 只补不削**：旧档的灵力常常是 0（那时灵力只在买功法时被顺带扣），直接沿用会导致更新后**第一局都开不了**。补到 160 是最低要求。
3. **v2 不占版本号**：下游 v3/v4/v5 都按「原始版本号」判断，v1 老档照旧一路升上来。少一个空版本，迁移链更短。
4. **v7 → v8 是「把走过的路拆成五条线」**：老档里没有 `levels`，只有一条 `prof`。用旧规则 `levelFromProf()` 反推出全书关号，
   再按段拆：前面几段记满、当前段记「段内关号 − 1」、之后各段留 0。
   **这与第 1 条不矛盾**：这里没有语义换算（关号本来就是关号，只是换了个存放形状），一关都没多给、也没没收。
   已经写过 `levels` 的档（新档、或迁移跑第二遍）一律不动——迁移必须幂等。
5. **v8 → v9 是「把五条线接成一条」**：`levels` 里五个数相加 = 老制下真实走通的关数（0–200），
   乘 5 落成 0–1000。乘 5 而不是「按段重算」，是因为**老 200 关的每一关在新制里都是 5 关的量**
   （旧 40 关段 ↔ 新 5 段里的对应区间），玩家一关都没被没收，也没有白送。
   同理它也不是语义换算：`cleared` 与 `levels` 之和是同一个东西的两种存放形状。
   **幂等靠 `typeof rec.cleared !== 'number'` 判**：新档出厂就带 `cleared: 0`，迁移不会再跑第二遍。
6. **引导标记扩成五格时不升版本号**（`onboarded` → `teachSeen[5]`）：这是**纯补值**，没有语义换算——
   老档那个布尔本来就等于「首段看过引导」，直接映射成 `teachSeen[0] = onboarded`，其余四段留 `false`。
   这么做还有个副作用是**故意的**：升级上来的老玩家会在第 11 / 51 / 201 / 501 关各看到一次段界引导。
   给新版字段补默认值本来就该在 `normalizeState` 里做，占一个版本号只会让迁移链多一环。
7. **v9 → v10 是「摘字段」而非「换算字段」**：删 `rec.prof` 与 `sCombo`，一个数都不改写。
   原因是功法的「级」在 v9 就已经能从 `cleared` 读出来（`stageIndexOfCleared`），`prof` 那条线只是并排躺着没人读。
   凡是「删掉一条并行的记录」都该走这一步——**先确认没人读，再删**，别顺手重算一个可能算错的数。

## 4. 规范化：所有入口的最后一道

`normalizeState(input)` 做四件事：

| 动作 | 例子 |
| --- | --- |
| 补默认值 | 缺 `twists` → `{}`；缺 `daily` → 建一个今天 |
| 过滤非法值 | `defeated` 只留字符串；`titles` 只留字符串；`twists[id]` 最多 8 条 |
| 夹到合法区间 | `realmIndex` 夹到 0…境界数-1；`portrait` 取模 6 |
| **夹平超上限灵力** | `if (qi > qiCap) qi = qiCap` |

**三个入口都走它**：读本机存档、读云端存档、导入存档码。

这里有一条容易踩反的边界：**规范化只补记账，不发钱**。`gifts` 缺省补 `{}`，钱由 `grantGifts()` 在结算（`store.settle`）里发。若把发放写进规范化，登录后 `hydrate()` 用云端那份覆盖 state 时，云端存档里没有记账，就会被当成「没发过」，于是一天冷启动几次就发几份；把这些带记账的档写回云端之后，那一份也就坐实了。发放只在一个「state 已经收敛完」的点上做，才谈得上幂等。

最后那条「夹平」是新加的：旧版灵力没有上限，老档可能攒到几百点，不夹就会显示「660 / 174」——上限在那一天才出现，玩家只会以为算错了。**只夹一次，不反复没收**，之后由「溢出即散」接管。

## 5. 导入导出

```js
exportSaveCode(state) → 'CANWU1:' + JSON.stringify(state)
importSaveCode(code)  → normalizeState(JSON.parse(...))
```

- **不压缩、不加密**：玩家可以自己看懂、自己改（改坏了也是自己的事）。加密只会增加「客服问我为什么导入失败」的成本。
- **导入必须走 normalize**：手改的存档可能缺字段、可能灵力爆表，全部在这里被夹平。
- 格式不对（前缀不符 / JSON 解析失败）分别给两种错误文案，不含糊。

## 6. 本机存储键

| 键 | 用途 |
| --- | --- |
| `canwu_*`（`game.STORAGE_KEY`） | 主存档 |
| `canwu_pending_v1` | 有未同步改动（含 `baseVersion`） |
| `canwu_sync_v1` | 上次同步时间与云端版本 |
| `canwu_sync_error_v1` | 上次同步错误 |
| `canwu_guest_v1` | 游客标记 |

**游客态不写 `pending`**。写了就会出现「有改动待同步」的黄条，而游客根本不会同步——那是纯噪音。

## 7. 三个「不可逆」的边界

| 操作 | 后果 |
| --- | --- |
| 清空存档（设置区） | 不可恢复。会同时清 `pending` / `sync` / `sync_error` |
| 导入别人的存档码 | 覆盖本机，云端版本号仍会推进（可能触发冲突） |
| 云端覆盖本机 | 见 `19-cloud-guest.md` 的冲突流程 |

**没有「后悔药」**。这是有意的：加一个「最近三次存档快照」会让存储翻三倍，而真正需要的玩家会用「导出存档码」这个已有功能。

## 8. 被否决的方案

存档上没有「试一试看」这回事，所以下面每一条否决都花过真金白银的教训。它们记的是：当初是什么把一个看起来合理的方案否掉的。

| 方案 | 为什么否掉 |
| --- | --- |
| 存成就进度 | 老档与导入存档无法自动获得，要写回填 |
| 存档加密 | 增加排障成本，且本机存档本来就在玩家手里 |
| 迁移时把旧字段换算成新语义 | v5→v6 的教训：语义不同就该重数，硬换算会凭空造数 |
| 迁移时「削到上限」 | 会没收玩家已有进度。只补不削 + 读档夹平，损失最小 |
| 每次读档都夹平（而不是一次） | 会反复没收，玩家感觉像被偷 |
| 存档里存一个「最近快照」 | 存储翻三倍，收益有限 |

## 9. 待验

- 存档码的长度（整份 JSON 无压缩）在微信「复制到剪贴板 / 粘贴」链路里是否会被截断。目前 15 门满进度 + 日志的存档可能到几 KB。
- `normalizeState` 对 `log` 数组的处理（环形日志上限）未在文档中固定，需看实现。
- 云端版本号与本机 `pending.baseVersion` 的冲突判定，在「同一账号两台设备先后登录」时是否会误报（见 `19-cloud-guest.md`）。
