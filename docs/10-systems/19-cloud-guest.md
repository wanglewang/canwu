# 云同步、账号隔离与游客态

> 存档有两条命：本机是**权威缓存**，云端是**跨设备的权威存档**。两条命之间靠一个 `pending` 标记缝合——它的全部作用是「保证不会静默丢档」。

**核心前提：这一层存在的唯一理由，是让「关掉、换台设备、再打开」这件事不丢东西。** 我不想让同步变成玩家要理解的功能——它最好是看不见的：页面读写的都是本机，快得像本地；云端在后台慢慢补，补完把标记擦掉。所以下面所有的取舍——防抖、去重、冲突交给玩家选、游客整层停用——都是从「别让人等待，也别让人丢档」这一句推出来的。

---

## 1. 一句话

页面只读 `store.get()`，写一律走 `commit()`；本机同步落盘并留 `pending`，云端异步补写，确认后清标记。不登录则整层停用，落一个游客标记。

## 2. 三层结构

把「看不见的同步」画出来，就是这三层——上面那层是玩家碰得到的，下面两层是他碰不到的（这张图是设计意图，不是截图）：

```text
  页面（同步 API，不阻塞）
       │ 读 get() / 写 commit()
       ▼
  store.js（单一状态源 + 订阅刷新）
       │                    │
       ▼                    ▼
  wx.storage              云适配器
  本机 · 权威缓存          异步 · 跨设备
```

**页面全部用同步 API**。云端读写在后台异步完成，不阻塞交互——这是小程序里唯一能接受的形态（网络慢不能让人点不动）。

## 3. pending：缝合两条命

```js
function saveLocal() {
  game.save(state);          // 本机落盘
  if (!guestMode) markPending();   // 留一个「有改动未上云」的标记
}
```

`pending` 这个标记什么时候被写上、又在哪一刻被擦掉——它就是「不丢档」的全部机制：

| 时机 | 动作 |
| --- | --- |
| 每次写本地 | 写 `canwu_pending_v1 = { at, baseVersion }` |
| 云端写入成功 | `clearPending()` + 记 `canwu_sync_v1 = { at, version }` |
| 启动 | 若 `pending` 存在 → 先补写云端 |
| 云端失败 | 写 `canwu_sync_error_v1`，页面显示同步条 |

**为什么需要 `baseVersion`**：冲突判定要知道「我这次改动是基于云端的哪个版本」。丢了它就只能靠时间戳猜。

**为什么不逐次写云**：写云有 1.2 秒防抖（`DEBOUNCE_MS`），否则连续操作会打出几十个请求。防抖期间切后台可能丢写 —— 所以 pending 必须在**写本地时**就落，而不是在写云时。

## 4. 并发与去重

```js
if (syncingPromise) return syncingPromise;
```

并发的 `flushCloud()` 复用同一个在途请求。既不会丢写，也不会让调用方拿到「正在同步中」这种假失败。

## 5. 冲突

| 状态 | 来源 |
| --- | --- |
| `hasConflict` | 云端版本 > 本机 `pending.baseVersion`（另一台设备先写了） |
| `resolveConflict(choice)` | 玩家选「用云端」或「用本机」 |

冲突弹窗必须给出两个具体选项，而不是「同步失败，请重试」。因为**两边都可能是有价值的进度**，只有玩家知道哪一边更新。

## 6. 游客态：整层停用

「先不登录，本机玩」不是降级模式，而是我把同步这一整层关掉后的正常游戏。关得干不干净，决定了游客会不会一直看到那条假的「待同步」。

`setGuest(true)` 做四件事：

1. `guestMode = true`；
2. 清掉 `lastCloudError` 与 `hasConflict`（游客没有「连不上」这回事）；
3. 取消未触发的防抖定时器；
4. **`clearPending()`**——最关键的一条。

`saveLocal()` 里 `if (!guestMode) markPending()` 是同一个道理：游客每改一次存档都留 pending，主页与人物页那条同步条就会一直说「有改动待同步」。而游客根本不会同步，那是纯噪音。

同理，`flushCloud()` 在游客态返回 `{ ok: true, skipped: true }`——「无事可做」不是失败，别在页面上留一条红线。

### 冷启动不挡回登录页

`canwu_guest_v1` 落盘。冷启动读到它就直接进主页，不弹登录。

**这条不做的话，游客每次杀进程再进都要重新点一次「先不登录」**——那等于把「游客」做成了一个只能玩一次的试玩。

## 7. 登录

- 微信一键登录（`wx.login` + 云服务换取身份）；
- **邮箱验证码兜底**：微信登录失败或用户拒绝授权时不至于完全无法同步；
- 登录后按账号隔离：RLS 策略 + 每行一个 `version` 列，由数据库 trigger 自增并覆盖客户端伪造的时间戳。

账号隔离的验证状态：表结构、trigger、两张表的 RLS、写入读回与探针清理**已验证**；真机登录链路**未验证**。

## 8. 隐私

两条硬规则：

1. `app.json` 的 `__usePrivacyCheck__` 必须为 `true`；
2. **剪贴板与昵称输入必须先过 `utils/privacy.js` 的守卫**。

未同意隐私指引时这些接口会**静默失败**——症状是「点了没反应」，这是最难排查的一类 bug。授权**不做缓存**：撤回同意要能立刻失效。

新增剪贴板调用时按「调用数 ≤ 守卫数」加断言，别只包一半。

## 9. 退出与清空

| 操作 | 行为 |
| --- | --- |
| `signOut()` | 清登录态，**保留本机存档** |
| `reset()` | 清主存档 + `pending` + `sync` + `sync_error` |
| 游客转入登录 | 本机存档保留，登录后与云端合并（走冲突流程） |

**退出登录不清档**：这是最容易被做成「退出即清空」的地方，也是最容易激怒玩家的地方。

## 10. 被否决的方案

同步这一层最容易犯的错，是把「技术上能做」当成「该做」。下面每一条都曾经摆上过桌——记下来，是为了下次别再为「较新的那台说得对」这种直觉争论。

| 方案 | 为什么否掉 |
| --- | --- |
| 逐次写云（无防抖） | 连续操作打出几十个请求 |
| 只在写云时才留 pending | 防抖期间切后台会丢写 |
| 游客也走云端（必然失败） | 同步条会把「没登录」显示成「连不上云端」 |
| 游客冷启动弹登录 | 「游客」变成只能玩一次的试玩 |
| 冲突时自动选「较新的」 | 时间戳不可靠（设备时间可改），且两边都有价值 |
| 退出登录清空本机 | 会激怒玩家 |
| 缓存隐私授权结果 | 撤回同意后无法立刻失效 |

## 11. 已知限制

| 限制 | 说明 |
| --- | --- |
| 离线收益与每日刷新用本机时钟 | 不能防恶意改表。已用「单调日历」（`key <= date` 不重置）挡住「调回过去重复领份例」这一类 |
| 榜单是「上传战绩 + 镜像对战」 | 不是实时同步 PVP |
| 头像 | 不接微信头像。形象由 `components/portrait` 的 CSS 道相承担（编号 0–5） |
| 云服务依赖第三方 | 域名未放行时头像类功能会回退（现已无头像，影响面缩小） |

## 代码指路

- `utils/store.js` —— `commit` / `saveLocal` / `markPending` / `clearPending` / `flushCloud` / `setGuest` / `resolveConflict` / `getSyncStatus`
- `utils/cloud-save.js` —— 云端读写与版本
- `utils/cloud.js` / `utils/cloud-social.js` —— 云服务适配与榜单
- `utils/privacy.js` —— 隐私守卫
- `app.js` —— `enterGuest()`、冷启动读取 `canwu_guest_v1`
- `pages/login/` —— 登录页与「先不登录 · 本机玩」
- `tests/store.test.js` —— 本机/云端合并、pending、游客

## 待验（必须真机）

- 微信一键登录、邮箱验证码兜底的完整链路。
- 云端读写与冲突弹窗（两台设备先后登录）。
- 游客态：杀进程再进是否真的不被挡回登录页；游客期间是否真的不出现「有改动待同步」。
