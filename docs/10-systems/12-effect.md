# 功法特效与段位兑现

> 旧规则是「练到大成（6000 熟练度）才一次性生效」。后果是：从开局到大成的那几十局里，所有特效都等于不存在——**那正是「练了也感觉不到」的来源**。
>
> 现在按段位逐级兑现：入门 25%，小成 50%，大成 75%，圆满起满额。

---

## 1. 一句话

19 门功法各带一个特效，分五类（战力 / 波动 / 省气 / 恢复 / 扩池），效果强度随本门段位线性兑现。

## 2. 五类特效，各管一件事

| 类型 | 作用 | 落点 | 门数 |
| --- | --- | --- | --- |
| `power` | 对战战力 % | `powerDetail` 的 `(1 + 境界 + 特效)` | 6 |
| `variance` | 对战波动下限 | `rollBattle` 的 `floor` | 3 |
| `qiSave` | 参悟省灵力 % | `practiceQiCost` 的 `(1 − 省气)` | 5 |
| `offline` | 闭关养回灵力的速度 % | `idlePending` 的 `(1 + offline)` | 3 |
| `qiCap` | 气海上限 % | `qiCapOf` 的 `(1 + 扩池)` | 2 |

**一类只给一类功法，互不重叠**。同族不重复给同一类，避免「练一族就吃满一项」。

## 3. 段位兑现比例

```js
const EFFECT_TIER_SCALE = [0, 0.25, 0.5, 0.75, 1, 1];
```

| 段位 | 比例 | 例：刀意 6% |
| --- | --- | --- |
| 未入门（0） | **0** | 0%（刚习得，还没练过） |
| 入门（300） | 25% | 1.5% |
| 小成（1500） | 50% | 3% |
| 大成（6000） | 75% | 4.5% |
| 圆满（24000） | 100% | 6% |
| 大圆满（99999） | 100% | 6% |

**未入门是 0 而不是 1/8**：刚习得还没练过，本条特效不该先白给。习得只是「能开练」，不是「已经会了」。

## 5. 累加与三处封顶

| 项 | 满额合计 | 封顶 | 谁管 |
| --- | --- | --- | --- |
| `power` | +35% | 无（乘数） | — |
| `variance` | +15% | floor 最高 98% | `rollBattle` |
| `qiSave` | −43% | **50%** | `PRACTICE_SAVE_MAX` |
| `offline` | +37% | 无 | — |
| `qiCap` | +25% | **30%** | `QI_CAP_SKILL_MAX` |

三个封顶各有理由：

- **`qiSave` 封 50%**：六门全学满也只有一半。不给封顶的话，以后再加功法会把耗气叠到 1 点，整个灵力系统失效。
- **`qiCap` 封 30%**：两门合计 25%，留 5% 余量给以后的心法。
- **`variance` 与身法共用一个 floor，最高 98%**：留 2% 的「意外」空间，否则切磋在后期变成纯查表。

## 6. 为什么 `qiCap` 只给心法

`scripts/verify.js` 断言：`effect.type === 'qiCap'` 的功法必须 `kind === 'main'`。

三个理由：

1. **语义**：心法就是「养气」。把池子挖深，比给战力更贴题。
2. **防止通吃**：如果刀法也能扩池，那「练心法」这条主修线就没有独占价值。
3. **玩家理解**：气海只有一个旋钮（境界 + 真元 + 心法），旋钮太多就没人记得住。

历史上吐纳诀曾给 `offline +10%`，与五行 / 三秀 / 摘魁重复。改 `qiCap` 之后，恢复速度归那三门，扩池归两门心法——**一门只管一件事**。

## 7. 计算方式

```js
// effectValue(state, type)
sum = 0
for each 已习得功法:
    scale = EFFECT_TIER_SCALE[段位]
    if (scale === 0) continue
    if (type 匹配) sum += value × scale
```

返回值是**比例的小数**（0.06），由各调用点自己决定怎么用：

- `powerDetail`：`base × (1 + realmBonus + effectBonus)`
- `rollBattle`：`floor = min(0.98, 0.85 + variance + shenBonus)`
- `practiceQiCost`：`× (1 − min(0.5, qiSave))`
- `idlePending`：`× (1 + offline)`
- `qiCapOf`：`× (1 + min(0.3, qiCap))`

**没有第二处计算特效的地方**，也不在页面里乘。

## 8. 界面表达

| 位置 | 写法 |
| --- | --- |
| 功法卡片 | 不计（卡片只留三行） |
| 图鉴「练成之后」 | 一行「本门特效」+ 当前几成：「刀意：对战战力 +6%（现 50%，满额 1.5%→3%）」 |
| 参悟准备页 | 第一行「属性加成」、第二行「本门特效」 |
| 人物页战力明细 | 只列已生效的（`activeBattleEffects`） |

`effectNoteOf(detail)` 生成那句「已生效 / 习得并练至入门后生效」，避免把未生效的特效写成灰色数字。

## 9. 被否决的方案

| 方案 | 为什么否掉 |
| --- | --- |
| 大成后才生效（旧版） | 中前期所有特效都不存在，玩家自然觉得「练了没感觉」 |
| 未入门也给 1/8 | 习得 ≠ 会。刚拿到就白给，段位就没有意义 |
| 特效乘进熟练度 | 熟练度只由评级与连 S 决定（见 `04-proficiency.md`） |
| 一门给两类特效 | 「一门只管一件事」。玩家要能一句话说出这门练了有什么用 |
| `qiCap` 给非心法 | 见第 6 节 |
| 特效值随品阶再放大 | 品阶已经通过属性系数放过一次，再放大等于双重计 |

## 10. 数值推导

**为什么 power 系给 4%–10%**：满配六门合计 +35%，正好相当于一次大境界突破的加成（+24%）。不让「堆特效」压过「破境」。

**为什么 variance 系只有 4%–6%**：它作用在**下限**上，不是期望值。把下限从 85% 抬到 100% 相当于「永不失手」，所以单门只能给几点，三门合计 +15% 再加身法 10%，正好被 98% 封顶卡住——这意味着**堆满会浪费 7 个百分点**。这处浪费是刻意的：三条路（特效 / 身法 / 都不堆）不该同时最优。

**为什么 qiSave 给 8%–10%**：五门合计 43%，离 50% 封顶还有余量。这样「全学齐」有意义（不满封顶），也不会一次把耗气压死。

**为什么 offline 给 10%–15%**：三门合计 +37%，差不多把「一天两收」变成「一天三收」的量。它不影响单局强度，只影响节奏，所以可以给得慷慨些。

## 11. 一处小不一致（不影响数值）

`activeBattleEffects(state)` 只在 `tierIndex >= 3`（大成）时把特效列进「已生效」清单，而 `effectValue` 从入门起就按 25% 生效。

结果显示上会「少列」：入门到小成期间，特效已经在算，但明细里不显示。这属于**展示口径**问题，不是数值 bug。若要修，把过滤条件改成 `effectScaleOf(rec.prof) > 0` 即可，但会让人物页的明细在前期变长——目前保留现状，记入待办。

## 代码指路

- `data/skills.js` —— 每门的 `effect: { type, value, text }`
- `utils/game.js` —— `EFFECT_TIER_SCALE` / `effectScaleOf()` / `effectValue()` / `activeBattleEffects()`
- `data/economy.js` —— `PRACTICE_SAVE_MAX`（0.5）、`QI_CAP_SKILL_MAX`（0.3）
- `scripts/verify.js` —— `qiCap` 只能挂心法、扩池总和 ≤ 30%
- `tests/game.test.js` —— 特效 25% / 75% / 100%

## 待验

- 图鉴里「现 50%，满额 1.5%→3%」这种写法是否会被读懂。
- 前期明细少列特效（见第 11 节）是否会造成「我明明学了却没生效」的误判。
- 堆满 `variance`（98% 封顶）之后浪费的 7 个百分点，玩家是否会发现并觉得「白练了」。
